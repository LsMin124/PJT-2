SEC 01

프로젝트 정체성과 목표

쉽게 말하면로봇 데모가 아니라, 실제 물류센터가 쓰는 것과 같은 구조의 소프트웨어 시스템을 만듭니다. 다만 진짜 로봇과 창고 대신 컴퓨터 속 가상 공간을 씁니다 — 그래서 비싼 장비 없이도 7주 안에 전체를 완성할 수 있습니다.
ONE-LINE DEFINITION"멀티로봇 시뮬레이션 기반 물류센터를 구축하고 산업 계층 구조로 WMS/WES까지 통합한 스마트 물류 솔루션"

"로봇 프로젝트에 백엔드를 붙인 것"이 아니라 물류 IT/OT 통합 시스템에서 물리 레이어를 시뮬레이션으로 구현한 것. 물리 세계만 가상일 뿐, 데이터 플로우·백엔드·서비스는 실제 스마트 물류센터와 동일한 구조로 구축한다.

이 문서가 처음이라면 안내 문서(DOC 00)를 먼저 읽는 것을 권한다. 처음 보는 용어는 용어사전에서 그래픽과 함께 설명 — A 로보틱스·시뮬레이션 · B 물류센터·표준 · C AI·데이터·서비스

SEC 02

시뮬레이터 선택과 하드웨어 환경

쉽게 말하면가상 공간(시뮬레이터)은 용도별로 세 가지를 씁니다: 가볍고 빠른 개발용(Gazebo), 실사에 가까운 시연용(Isaac Sim), 그리고 "하루치 물류 흐름을 몇 초 만에 계산"하는 흐름 계산용(SimPy). 고사양 그래픽카드가 달린 컴퓨터 한 대가 전용 서버 역할을 하고, 나머지는 원격으로 접속해 씁니다.

SEC 03

시스템 아키텍처 — ISA-95 × WMS/WES/WCS 계층

쉽게 말하면시스템을 층층이 쌓는 설계도입니다. 실제 산업계가 쓰는 표준 구조와 통신 규격을 그대로 따라 만들어서, "학생 프로젝트 구조"가 아니라 "현장 구조"가 되도록 합니다. AI 검수 파트가 특별한 이유도 함께 설명합니다: 진짜 불량품 사진을 못 구하니 가상 카메라로 만들어서 AI를 가르친다는 것.

아래 그림 읽는 법: 위로 갈수록 관리(IT) 계층, 아래로 갈수록 물리(OT) 계층이다. 오른쪽 두 세로선이 이 구조의 핵심 — 명령은 위에서 아래로 내려가고, 상태·실적은 아래에서 위로 올라간다.

SEC 04

SimPy × Isaac Sim 연동 설계

쉽게 말하면두 시뮬레이터는 시간을 다루는 방식이 정반대입니다. 하나는 영화처럼 매 순간을 전부 그리고(Isaac), 하나는 중요한 사건만 골라 빨리감기합니다(SimPy). 억지로 하나로 묶으면 둘 다 망가지므로, 느슨한 연결부터 시작해 세 단계로 점점 깊게 결합합니다.

두 시뮬레이터의 시간 처리 차이

SimPy — 이산사건(DES)

  • 시간: 사건→사건 점프, 사이 구간 미계산
  • 속도: 하루치를 수 초에, 몬테카를로(무작위 조건 반복 실험) 수천 회
  • 관심사: 흐름과 자원 — 처리량·병목·대기열

Isaac Sim — 연속시간 물리

  • 시간: 고정 타임스텝(1/60s 등) 연속 적분
  • 속도: 실시간 ~ 수 배속
  • 관심사: 운동과 상호작용 — 파지·충돌·센서

→ 두 시뮬레이터를 하나의 시계로 묶지 않는다. 묶으면 DES의 장점(초고속·통계 반복)이 물리 시뮬레이션 속도에 묶여 사라진다.

Isaac에서 단위 작업을 반복 측정한다. 예: 피킹 200회 → 평균 12.3초, 표준편차 1.8초, 실패율 4%. 이 수치를 SimPy의 공정 파라미터로 넣는다. 두 시뮬레이터의 실행은 완전히 분리되고 데이터만 한 방향으로 흐른다. 결과는 "물리적 근거를 가진 센터 모델" — 산업 디지털 트윈의 표준 구조와 같다. what-if 실험을 마음껏 돌릴 수 있다(AMR 3대 vs 4대, 배차 전략 A vs B, 슬로팅(상품 보관 위치 배치) 전략 비교).

하이브리드 최종 형태

Isaac에 실제로 만든 셀은 패턴 2로 실행하고, 나머지 셀은 패턴 1의 통계 분포로 가상 처리한다. 물리 셀과 통계 셀이 공존하는 구조다. 그래픽 메모리(VRAM) 예산 문제의 해법이면서, 기존 공장에 디지털 트윈을 부분적으로 입히는 산업 사례(브라운필드)와 구조가 같다. 실기체를 들일 때도 "실물 셀 1개 추가"로 자연스럽게 확장된다.

연동 설계 원칙

  • 시간 권위 단일화 — 라이브 통합에서는 벽시계(Isaac 실시간)가 권위, SimPy가 추종
  • 경계는 이산 사건만 — 오더 발행/완료/실패만 교환. 연속 상태(관절각·좌표)는 Sparkplug B로 DB/Grafana에만
  • 실패 의미론 통일 — Isaac 파지 실패 = SimPy에서 재시도/불량 분기 동일 정의
  • 결정론 포기 + 전 사건 타임스탬프 로깅 — 실행마다 결과가 조금씩 달라지는 것은 받아들이되, 모든 사건에 시각을 남겨 사후에 재구성할 수 있게 한다

SEC 06

단계별 로드맵

쉽게 말하면작은 완성품을 먼저 만들고 살을 붙입니다. 0단계에서 로봇 없이 데이터 흐름부터, 1단계에서 로봇 조종, 2단계에서 전체 연결 — 어느 단계에서 멈춰도 "완성된 무언가"가 남도록 설계했습니다. 3단계부터는 심화(AI 강화학습, 확장)입니다.
PRINCIPLE수직 슬라이스 우선 — "스테이션 1개 + AMR 1대 + 데이터 경로 끝까지"의 최소 구성을 먼저 완성하고, 이후 수평으로 확장한다. 통합 리스크를 초반에 해소하기 위함.

각 단계의 상세 내용은 아래 목록에 있다. 주차 단위 일정은 이 문서가 아니라 TEAM OVERVIEW의 통합 일정이 기준.

PHASE 0

데이터 백본 (Isaac 없이 시작)

SimPy 물류 모델(임시 가정 분포) + Spring WMS/WES-lite + MQTT 브로커 + TimescaleDB/PostgreSQL + Grafana · VDA 5050/Sparkplug B 스키마 설계 · mock(가짜 데이터) publisher 가동 — 로봇이 없어도 데이터가 끝까지 흐르는 것을 먼저 확인

PHASE 1

ROS2 코어 (Gazebo)

AMR+팔 통합 URDF · ros2_control(베이스 velocity/팔 position) · Nav2 + EKF + MoveIt2 · behavior tree로 주행→도킹→피킹

PHASE 2

Isaac Sim 포팅 + 수직 슬라이스 완성

USD(Omniverse의 3D 씬 파일 형식) 변환·ROS2 브리지로 기존 노드 재사용 · 피킹 스테이션 1 + AMR 1 라이브 접속(패턴 2) · Replicator 합성 데이터 → 검수 모델 → 폐루프 · Isaac WebRTC(브라우저 실시간 영상 전송) 스트림 → 관제 포털 임베드 (3D 비주얼 필수 요구)

PHASE 3

Isaac Lab RL

SKU 파지(또는 도킹 정렬) 1태스크: 환경 정의 → 도메인 랜덤화(마찰·조명 등을 무작위로 흔들어 일반화시키는 기법) → PPO(대표적 강화학습 알고리즘) 학습 → 평가 · 실기체 서보 실측 스펙 반영 · 검증 서사 = sim-to-sim 전이(다른 시뮬레이터로 옮겨도 성능 유지) + 랜덤화 민감도 분석 · 소규모(병렬 환경 64~128개) 검증 → 야간 대규모(2048개+) 본 학습

PHASE 4

수평 확장 + 시뮬 CI

스테이션/AMR 추가(하이브리드) · 배차·슬로팅 전략 비교 — consistent hashing, Power of Two Choices 같은 부하 분산 알고리즘 응용 · Jenkins(자동 빌드·테스트 서버) 회귀 CI: 표준 시나리오를 화면 없이 자동 실행 → UPH(시간당 처리 개수)·피킹 성공률 리포트 · 시연 하이라이트 2종 — 장애 주입 버튼(AMR 고장·통로 폐쇄 → 자동 복구) + What-if 예측 화면(SimPy) · (스트레치) 키팅(여러 부품을 세트로 묶는 작업) 스테이션 — 수직 슬라이스 안정 시 착수

PHASE 5 · 선택

Sim-to-Real 사이드

SO-101 + LeKiwi 실기체를 "실물 피킹 스테이션 1개"로 편입 → 하이브리드 디지털 트윈 완성형

주차 단위 통합 마일스톤(통합 #1~#3, 막판 일괄 통합 금지)은 TEAM OVERVIEW의 통합 일정이 기준.

SEC 08

이론 학습 전략 — Just-in-Time

쉽게 말하면수학·이론 공부는 교과서 정주행 대신, 프로젝트에서 그 이론이 실제로 필요해지는 순간에 최소한만 배웁니다. 미리 해둘 것은 딱 하나(모터 제어의 기본인 PID 감 잡기, 2~3일)뿐입니다.

원칙: 교과서 정주행(현대제어·라그랑주 동역학 등)은 과하다. 그 이론이 실제로 필요해지는 시점에 최소 구현으로 학습한다. 별도 학습 트랙은 두지 않는다.

  • 운용 리듬: "이번 주 작업에 등장한 이론 하나를 주말에 최소 구현으로 정리" → 산출물이 그대로 설계 근거 문서/기술 블로그
  • 효과: 담당 트랙의 이론적 근거를 직접 검증·설명할 수 있게 됨 — 파라미터 선택이 "감"이 아닌 "근거"가 된다
  • Modern Robotics 등은 정독이 아닌 사전(해당 챕터만) 용도
SEC 09

핵심 결정 사항 — Decision Log

쉽게 말하면지금까지 정한 중요한 결정들의 목록입니다. "이거 왜 이렇게 했더라?"가 궁금해지면 여기부터 봅니다. 결정이 바뀌면 이 목록에 이력을 남깁니다.
도메인 = 물류센터(풀필먼트) — 상위 시스템은 WMS/WES, 로봇팔 작업은 피스 피킹으로 유지 (REV B 전환)
물류센터 3D 비주얼 = 필수 요구 — Isaac Sim WebRTC 스트리밍을 관제 포털에 임베드, Three.js 자체 트윈은 스트레치
MES(제조실행시스템) = 별도 구축 없음(옵션 A 확정) — WMS/WES가 물류 도메인의 L3(MES 계층) 시스템임을 발표 자료의 기능 대응표로 서술. 키팅 스테이션(경공정 추가로 MES 실체화)은 수직 슬라이스가 5주차 전 안정되면 착수하는 스트레치
시연 하이라이트 = 장애 주입(AMR 고장·통로 폐쇄 → 자동 복구) + What-if 예측 화면(SimPy) 2종을 필수 시연 요소로 채택 — 신규 개발을 최소화하면서 기존 기능을 보여주는 장치
프로젝트 정체성 = 시뮬 기반 물류 IT/OT 통합 시스템 (로봇 단독 프로젝트 아님)
