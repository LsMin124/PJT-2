합성 데이터Synthetic Data

실제 세계에서 수집한 것이 아니라 시뮬레이터가 생성한 학습 데이터. 라벨이 자동으로 붙고, 희귀한 상황(불량)도 원하는 만큼 만들 수 있다.

물류 검수의 근본 난제는 예외 샘플(파손·오피킹)의 희소성과 수천 종에 달하는 SKU 다양성이다 — 잘 돌아가는 센터일수록 파손 사진이 없고, 신상품은 계속 늘어난다. 합성 데이터는 이 문제를 푸는 산업계의 실전 해법으로, 시뮬레이터에서 SKU·파손·라벨 변형을 의도적으로 만들어 학습시킨다. 시뮬과 실사의 차이는 도메인 랜덤화(REF A 참조)로 극복한다.

이 프로젝트에서 — AI 파트의 핵심 차별화. 공개 데이터셋 베이스라인과 합성 데이터 학습 모델의 성능을 정량 비교하는 것이 발표의 핵심 슬라이드다.

객체 탐지 · YOLOObject Detection · You Only Look Once

이미지 안에서 "무엇이 어디에 있는지"를 박스로 찾아내는 AI 태스크와, 그 대표 실시간 모델 계열. 한 번의 신경망 통과로 모든 객체를 동시에 찾는다.

대상의 종류와 위치를 알아야 할 때(어떤 SKU가 어디에, 파손이 어느 부위에) 적합하다. 학습에는 박스 라벨이 필요한데, 합성 데이터에서는 라벨이 공짜로 나온다는 점에서 궁합이 좋다.

이 프로젝트에서 — 검수 스테이션의 후보 모델. SKU 인식(주문 품목과 일치하는가)과 파손 위치 특정에 쓰고, 이상 탐지 계열과 비교 평가한다.

이상 탐지Anomaly Detection · PatchCore · PaDiM

"정상"만 학습한 뒤, 정상 분포에서 벗어나는 것을 전부 이상(결함)으로 잡아내는 접근. 불량 샘플이 아예 없어도 학습할 수 있다.

객체 탐지와 철학이 반대다. YOLO는 "이런 결함을 찾아라"(결함을 알아야 함), 이상 탐지는 "정상이 아닌 걸 찾아라"(정상만 알면 됨). 실제 공장에서는 예상 못 한 새로운 불량이 계속 나타나므로, 두 접근을 병행하는 것이 실무적이다.

이 프로젝트에서 — YOLO와 함께 비교 평가하는 축. "합성 데이터로 학습한 YOLO vs 정상만 학습한 PatchCore"의 파손 검출 성능·미검출 비교가 흥미로운 실험 포인트다.

MVTec AD산업 이상 탐지 표준 벤치마크

공업 제품(나사·캡슐·직물 등 15종)의 정상/결함 이미지를 모은 공개 데이터셋. 산업 이상 탐지 논문·모델의 표준 시험대다.

AI 분야에서 벤치마크 데이터셋은 "공용 모의고사"다. 새 기법의 성능은 대부분 MVTec AD 점수로 보고되므로, 이 데이터셋으로 베이스라인을 잡으면 우리 모델이 세계 수준 대비 어디쯤인지 가늠할 수 있다.

이 프로젝트에서 — Isaac 환경이 준비되기 전(Phase 0~1) AI 파트가 이걸로 모델 파이프라인을 선구축한다. 이후 합성 데이터로 교체하며 "베이스라인 대비 얼마나"를 정량 비교한다.

ONNXOpen Neural Network Exchange

학습된 AI 모델의 공용 파일 포맷. 어떤 프레임워크로 학습했든 ONNX로 내보내면, 학습 환경 없이 어디서든(서버·엣지·브라우저) 실행할 수 있다.

웹 개발의 빌드에 비유하면: TypeScript(학습 코드)로 개발하고 JS 번들(ONNX)로 배포하는 것이다. 실행에는 ONNX Runtime이라는 가벼운 엔진만 있으면 되고, GPU 학습 환경 전체를 배포 서버에 설치할 필요가 없다.

이 프로젝트에서 — 검수 모델을 ONNX로 내보내 추론 서비스로 배포한다. 검수 카메라 이미지 → ONNX 추론 → 판정 결과가 WMS로 회신되는 구조다.

Human-in-the-Loop사람이 개입하는 AI 운영 구조

AI의 판정을 사람이 승인·정정(오버라이드)할 수 있게 하고, 그 정정 기록을 다시 모델 개선에 쓰는 운영 구조.

AI가 100% 정확할 수 없는 현장에서 책임 소재를 만들고(최종 판단은 사람), 동시에 사람의 정정을 가장 값진 학습 데이터로 회수하는 실무 패턴이다. MLOps에서 말하는 "데이터 플라이휠"의 최소 구현이기도 하다.

이 프로젝트에서 — 검수 화면에서 운영자가 AI 판정(오피킹·파손)을 승인/오버라이드하고, 오버라이드된 이미지는 재학습 데이터셋으로 자동 축적된다.

EMQXMQTT 브로커

MQTT 메시지를 중계하는 서버(브로커) 제품. 발행자와 구독자 사이에서 메시지를 받아 올바른 구독자들에게 배달한다.

MQTT가 프로토콜(규약)이라면 EMQX는 그 규약을 구현한 서버다 — HTTP와 Nginx의 관계와 같다. 대안으로 가벼운 Mosquitto가 있으며, EMQX는 웹 대시보드·클러스터링·WebSocket 지원이 잘 되어 있어 관제 서비스와 궁합이 좋다. 규칙 엔진으로 "특정 토픽 메시지를 DB에 적재" 같은 파이프라인도 브로커 단에서 처리할 수 있다.

이 프로젝트에서 — 데이터 인프라의 중심. 로봇·설비·WMS·웹 관제가 전부 EMQX를 경유해 대화하며, docker compose로 로컬에서 즉시 띄운다.

TimescaleDB시계열 데이터베이스

PostgreSQL의 확장으로 만든 시계열 특화 DB. "시간 + 측정값" 형태로 끝없이 쌓이는 데이터를 자동 파티셔닝·압축하며 빠르게 조회한다.

설비 텔레메트리는 일반 트랜잭션 데이터와 성격이 다르다 — 초당 수십 건씩 영원히 쌓이고, 수정은 없고, 조회는 늘 시간 범위 기준이다("지난 1시간 셀1 온도"). 일반 테이블로 받으면 금방 느려지는 이 패턴을, TimescaleDB는 하이퍼테이블(시간 기준 자동 분할)로 처리한다. SQL을 그대로 쓸 수 있다는 것이 학습 비용 측면의 장점이다.

이 프로젝트에서 — 설비·AMR 텔레메트리(시계열)는 TimescaleDB, 주문·재고·실적(트랜잭션)은 일반 PostgreSQL로 분리 저장한다. 같은 SQL 생태계라 운영 부담이 적다.

Grafana관측 대시보드 도구

DB에 쌓인 시계열 데이터를 쿼리해 차트·게이지로 보여주는 오픈소스 대시보드. 코드 없이 패널을 조립해 모니터링 화면을 만든다.

DevOps의 서버 모니터링(CPU·메모리 그래프)에 널리 쓰이는 그 도구다. 제조에서도 동일하게 설비 가동률·사이클 타임·배터리 추이를 그린다. 단, 이것은 엔지니어의 관측 도구이지 최종 사용자 서비스가 아니다 — 운영자용 화면은 별도의 웹 서비스로 만든다는 것이 이 프로젝트의 구분선이다.

이 프로젝트에서 — 팀 내부 관측·디버깅용. "공장을 운영한다"는 경험은 React 관제 포털이 담당하고, Grafana는 개발 중 데이터 흐름 확인과 성능 분석에 쓴다.

MQTT over WebSocket브라우저에서 MQTT 직접 구독

브라우저는 MQTT TCP 연결을 직접 못 열지만, WebSocket 위에 MQTT를 실어 보내면 웹 페이지도 브로커의 토픽을 직접 구독할 수 있다.

일반적인 구조라면 "로봇 → 브로커 → 백엔드 → (폴링/SSE) → 브라우저"로 중계 API를 만들어야 한다. MQTT-WS를 쓰면 "로봇 → 브로커 → 브라우저"로 한 단계가 사라지고, 백엔드는 실시간 중계 코드를 만들 필요가 없어진다. 관제 화면이 로봇 위치를 지연 없이 그릴 수 있는 이유다.

이 프로젝트에서 — 관제 맵이 VDA 5050 state·Sparkplug B 토픽을 브라우저에서 직접 구독해 실시간 렌더링한다. "표준 토픽 = 프론트 API"가 되는 구조라 전용 실시간 API가 불필요하다.

PWAProgressive Web App

웹 앱에 홈 화면 설치·오프라인 캐시·푸시 알림 능력을 더해, 네이티브 앱처럼 쓰게 만드는 웹 표준 기술 묶음.

앱스토어 배포 없이 URL 하나로 모바일 경험을 제공한다. 핵심 재료는 Service Worker(백그라운드 스크립트)와 Web Push(서버발 알림). 별도 iOS/Android 코드베이스를 만들 필요가 없어, 소수 팀이 모바일 요구를 감당하는 표준 해법이다.

이 프로젝트에서 — 네이티브 앱 대신 관제 포털을 PWA로 제공한다. 오피킹·파손 Andon 발생 시 웹 푸시로 모바일 알림을 보내는 것이 대표 시나리오다.

OpenAPI · 데이터 계약API 명세 표준 · Data Contract

REST API의 요청·응답 형식을 기계가 읽을 수 있는 문서(YAML/JSON)로 정의하는 표준. 넓게는 "파트 간 인터페이스를 문서로 동결하는 것"이 데이터 계약이다.

Swagger로 익숙한 그 명세다. 이 프로젝트에서 계약은 세 종류다: REST는 OpenAPI로, AMR 통신은 VDA 5050 JSON 스키마로, 설비 텔레메트리는 Sparkplug B 네임스페이스로. 계약을 1~2주차에 동결하면 각 파트는 상대의 완성을 기다리지 않고 계약만 보고 병렬 개발할 수 있다 — 6인 팀이 7주 안에 완주하는 유일한 방법이다.

이 프로젝트에서 — "FROZEN CONTRACTS v1.0"이 협업의 기준 문서. 변경은 2-키(아키텍트+PM) 승인을 거친다. mock publisher가 이 계약대로 가짜 데이터를 발행해 계약의 실효성을 즉시 검증한다.

ADRArchitecture Decision Record

"왜 이렇게 결정했는가"를 짧은 문서로 남기는 관행. 결정의 배경·대안·근거를 기록해, 나중에 "이거 왜 이렇게 했지?"에 답할 수 있게 한다.

형식은 간단하다: 상황(Context) → 결정(Decision) → 근거와 결과(Consequences). 코드 주석이 "어떻게"를 남긴다면 ADR은 "왜"를 남긴다. 팀원이 바뀌거나 기억이 흐려져도 결정의 맥락이 보존되고(버스 팩터 완화), 발표·면접에서 "의사결정 과정"을 보여주는 최고의 재료가 된다.

이 프로젝트에서 — 주요 기술 결정을 ADR로 기록한다(서기는 주간 순환). 계획서의 Decision Log 습관을 팀 차원으로 확장한 것.
