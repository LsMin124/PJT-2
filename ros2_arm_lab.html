SEC 01

전체 지도 — 우리가 만든 것

이 노트는 코딩 에이전트가 대신 수행한 작업을 결과가 아니라 과정으로 복기하는 문서입니다. 각 절은 쉽게 말하면 직접 해보기 스스로 점검 순서로 구성했습니다. 읽기만 하면 부채는 그대로입니다 — SEC 08의 재현 과제까지 스스로 마쳐야 상환 완료입니다.

완성된 시스템은 파이프라인 두 개입니다. 하나는 로봇을 보이게 하고, 하나는 움직이게 합니다.

SEC 02

워크스페이스와 빌드 — colcon

ROS2 개발의 시작은 "내 코드를 ROS가 찾을 수 있는 형태로 설치"하는 것입니다. 그 규칙이 워크스페이스이고, 도구가 colcon입니다.

빌드 상세 — 오버레이 개념 · 패키지 구성 · 실습 · 점검
쉽게 말하면 /opt/ros/humble은 공장에서 출고된 밑그림, ~/ros2_ws는 그 위에 얹는 내 덧그림(오버레이)입니다. 터미널에서 source를 밑그림 → 덧그림 순서로 하면, 같은 이름의 패키지는 내 것이 우선합니다. UR 공식 description을 apt 대신 소스로 클론해 워크스페이스에 둔 것도 이 원리 — 언제든 내가 고칠 수 있는 쪽이 이깁니다.

ament_python 패키지의 최소 구성

구성물왜 필요한가
package.xml"나는 arm101이고 rclpy·sensor_msgs가 필요하다"는 선언. 빌드 순서·의존 설치의 근거
setup.py — data_filesURDF·launch 파일을 install/arm101/share/…로 복사. launch가 get_package_share_directory('arm101')로 찾을 수 있는 이유
setup.py — entry_points'joint_wave = arm101.joint_wave:main' 한 줄이 ros2 run arm101 joint_wave를 만든다
resource/arm101(빈 파일)ament 인덱스용 마커 — "이 패키지가 설치되어 있음"의 표식
직접 해보기 빌드 산출물을 전부 지우고 백지에서 다시 빌드해보세요. 이게 되면 빌드는 이해한 겁니다.
cd ~/ros2_ws && rm -rf build install log
source /opt/ros/humble/setup.bash && colcon build --symlink-install
source install/setup.bash && ros2 pkg list | grep arm101
--symlink-install은 파이썬 파일을 복사 대신 링크로 설치 — .py를 고쳐도 재빌드 없이 반영됩니다(단, setup.py를 고치면 재빌드).
스스로 점검 ① 새 터미널에서 ros2 run arm101 joint_wave가 "package not found"로 실패한다. 무엇을 빼먹었나?
② conda (base)가 켜진 터미널에서 ROS를 실행하면 왜 위험한가?
답 보기 ① source ~/ros2_ws/install/setup.bash — source는 터미널마다 매번 필요. ② #!/usr/bin/env python3이 conda의 파이썬을 잡아 시스템에 설치된 ROS 파이썬 모듈(lxml 등)을 못 찾는다. 실제로 TurtleBot3 스폰이 이걸로 죽었다. ROS 터미널에서는 conda deactivate.
SEC 03

로봇을 그리다 — URDF · joint_states · TF

로봇팔은 "강체(link)를 관절(joint)로 이어붙인 나무"입니다. URDF가 그 나무를 적는 형식이고, 우리 arm101.urdf는 링크 5개·회전 관절 3개짜리 최소 예제입니다.

URDF 해부 · joint_wave · 실습 · 점검 
<joint name="base_yaw" type="revolute">   ← 회전 관절 (J1)
  <parent link="base_link"/>              ← 어느 강체에서
  <child  link="shoulder_link"/>          ← 어느 강체로 이어지나
  <origin xyz="0 0 0.05"/>                ← 부모 기준 관절의 위치(= 베이스 위 5cm)
  <axis   xyz="0 0 1"/>                   ← 회전축 (z축 = 좌우로 도는 yaw)
  <limit lower="-3.14" upper="3.14" …/>   ← 가동 범위(rad)
</joint>
쉽게 말하면 URDF는 구조만 있고 자세가 없습니다. "팔꿈치가 지금 몇 도인가"는 /joint_states 토픽이 실시간으로 채웁니다. robot_state_publisher가 이 둘을 곱해 모든 링크의 3차원 위치(/tf)를 계산합니다. Foxglove에서 좌표축만 보이고 팔이 안 보였던 날 — 그게 바로 "TF는 있는데 URDF 레이어를 안 붙인" 상태였습니다.

joint_wave — 각도를 지어내는 노드

joint_wave.py는 30Hz 타이머로 사인파 각도를 만들어 /joint_states에 발행합니다. 진짜 로봇이라면 모터 엔코더가 할 일을 흉내내는 것 — 같은 자리에 SEC 05에서는 mock hardware가, 최종 프로젝트에서는 Isaac Sim이 들어옵니다. joints·amplitudes_rad·periods_sec·offsets_rad를 파라미터로 받도록 일반화해서 자작 팔에도 UR5e에도 같은 노드를 씁니다.

직접 해보기 ① ros2 launch arm101 view_arm.launch.py 후 다른 터미널에서:
ros2 topic echo /joint_states --once · ros2 topic echo /tf --once — 각도(rad)와 변환(translation·rotation)을 눈으로 대조.
② urdf/arm101.urdf에서 upper_arm 길이 0.30을 0.45로 바꾸고 재실행 — Foxglove에서 팔이 길어졌는지 확인. (visual의 origin z도 절반만큼 같이 움직여야 하는 이유를 생각해볼 것: 박스는 중심 기준으로 그려진다.)
스스로 점검 joint_wave를 끄고 robot_state_publisher만 켜면 Foxglove에 무엇이 보일까?
답 보기고정(fixed) 관절의 TF만 발행되고 회전 관절 3개의 TF가 끊겨, 팔이 그려지지 않거나 링크들이 연결되지 않은 채 남는다. "구조 × 자세 = 화면"에서 자세가 빠진 상태.
SEC 04

원격에서 보다 — Foxglove 파이프라인

이 PC는 SSH로만 접근하는 헤드리스 환경입니다. Gazebo GUI 대신 "PC는 계산만, 그림은 노트북에서"로 갔고 — 이 구조는 최종 프로젝트의 Isaac 헤드리스 + 원격 뷰와 같은 패턴의 예행연습입니다.

브리지 특성 · 전송 메커니즘 3종 · xacro · 실습 · 점검
쉽게 말하면 foxglove_bridge는 ROS 토픽 ↔ 웹소켓(포트 8765) 번역기입니다. 중요한 특성: 클라이언트가 구독을 요청한 토픽만 ROS 쪽 구독을 만듭니다. "invalid topic" 사건 때 서버에서 Subscription count: 0을 보고 "브리지는 멀쩡하고 뷰어가 요청을 안 했다"고 판정할 수 있었던 근거입니다.

세 가지 전송 메커니즘

무엇이어떻게 노트북까지 가나
로봇 구조(URDF)/robot_description 토픽. latched(TRANSIENT_LOCAL) — 발행이 한 번뿐이어도 늦게 접속한 구독자가 마지막 메시지를 받는다
실시간 자세/tf · /joint_states 스트리밍
메시 파일(.dae)URDF 속 package://ur_description/… 경로를 뷰어가 보고, 브리지의 fetchAsset 기능으로 파일 자체를 받아간다

UR5e 재사용 — xacro

정밀 모델은 그리지 않고 제조사 공식 Universal_Robots_ROS2_Description을 클론했습니다. UR은 URDF를 직접 주지 않고 xacro(변수·매크로가 있는 URDF 템플릿)를 줍니다 — 같은 파일에서 ur_type:=ur3e/ur5e/ur10e로 다른 로봇이 나오는 방식. view_ur.launch.py에서는 launch가 실행되는 순간 Command로 xacro를 돌려 URDF 문자열을 만들어 robot_state_publisher에 넘깁니다.

직접 해보기 ① ros2 launch arm101 view_ur.launch.py 후: ros2 topic info /robot_description --verbose — Durability가 TRANSIENT_LOCAL인지 확인.
② xacro가 뭘 만드는지 직접 보기: xacro $(ros2 pkg prefix ur_description)/share/ur_description/urdf/ur.urdf.xacro ur_type:=ur5e name:=ur | head -50
③ 노트북 Foxglove → 3D 패널 → Custom layers → Add URDF → Source: Topic → /robot_description
스스로 점검 브리지를 재시작해도 Foxglove를 재접속만 하면 URDF가 다시 뜨는 이유는?
답 보기robot_state_publisher가 살아있는 한 /robot_description은 latched로 유지되고, 새 브리지·새 클라이언트가 구독을 다시 만들면 마지막 메시지를 즉시 받는다. 반대로 robot_state_publisher를 재시작하면 그 발행자의 latch도 사라진다.
SEC 05

움직이게 하다 — ros2_control × MoveIt2

201의 핵심은 계층입니다. 계획(어디로 어떻게 갈까)과 실행(그 궤적을 시간에 맞춰 재생)이 분리되어 있고, 그 사이를 컨트롤러 이름이 잇습니다.

계층 구조도 · ros2_control 등장인물 · goal 해부 · 실행 명령 · 실습 · 점검
쉽게 말하면 ros2_control은 "모터 추상화 계층"입니다. 진짜 UR이든, mock이든, Isaac이든 hardware interface만 갈아끼우면 위쪽(컨트롤러·MoveIt·우리 코드)은 그대로입니다. 오늘 mock으로 배운 코드가 그대로 시뮬레이터·실기로 이어지는 이유이고, 이것이 Sim-to-Real의 소프트웨어적 토대입니다.

ros2_control 등장인물

구성요소역할

spawnerlaunch 시 컨트롤러를 로드·활성화해주는 일회성 도우미

moveit_demo — 액션 goal의 해부

라이브러리 없이 MoveGroup 액션을 직접 조립했습니다. 핵심만 보면:

goal.request.group_name = 'ur_manipulator'      # SRDF에 정의된 계획 그룹(= 팔 전체)
constraints.joint_constraints = [               # "관절 목표" — 각 관절이 이 각도(±0.01rad)면 성공
    JointConstraint(joint_name='shoulder_pan_joint', position=0.0, …), … 6개 ]
goal.planning_options.plan_only = False         # 계획만 하지 말고 실행까지

플래너 선택·충돌 검사·시간 파라미터화는 전부 move_group이 대신한다 — 클라이언트는 "무엇을"만 말하고 "어떻게"는 위임하는 구조.

실행 명령 (터미널 4개 · 각각 한 줄 그대로)

ros2 launch ur_robot_driver ur_control.launch.py ur_type:=ur5e robot_ip:=127.0.0.1 use_fake_hardware:=true initial_joint_controller:=scaled_joint_trajectory_controller launch_rviz:=false
ros2 launch ur_moveit_config ur_moveit.launch.py ur_type:=ur5e launch_rviz:=false
ros2 run foxglove_bridge foxglove_bridge
ros2 run arm101 moveit_demo          # ← 이 터미널만 ~/ros2_ws/install/setup.bash 소싱 필요
직접 해보기 ① moveit_demo.py의 PRESETS에 자세를 하나 추가하고 CYCLE_ORDER에 끼워 넣어 4자세 순환으로 만들기.
② 컨트롤러 상태 확인(ros2controlcli 미설치 시): ros2 service call /controller_manager/list_controllers controller_manager_msgs/srv/ListControllers
③ 일부러 -4 재현: switch_controller 서비스로 jtc를 활성화해 데모를 돌려보고, 다시 scaled로 복구 — SEC 07 사건 4를 몸으로 익히는 실습.
스스로 점검 ① joint_wave와 이 스택을 동시에 켜면 어떤 증상이 나타날까? ② "계획은 성공했는데 실행이 실패했다"는 것을 로그의 어떤 문장으로 구분할 수 있나?
답 보기 ① /joint_states에 발행자가 둘이 되어 TF가 두 자세 사이를 널뛰듯 튄다. 실제로 pkill 잔존 프로세스 때문에 겪었다(SEC 07 사건 5). ② move_group 로그의 "Solution found but controller failed during execution" — Solution found(계획 성공)와 controller failed(실행 실패)가 한 문장에 있다.
SEC 06

인터랙티브 IK — 202: 클릭 · 타이핑 · 조그

201의 moveit_demo는 관절 공간 목표("각 관절을 이 각도로")였습니다. 202는 작업 공간으로 올라갑니다 — "툴 끝을 저 좌표에"를 사람이 실시간으로 지시하고, 관절 각도는 IK가 풀게 합니다.

FK/IK 비교 · 두 경로 구조도 · ik_goto/servo_jog 상세 · 실습 · 점검

FK · IK · 미분 IK — 한 표로

문제입력 → 출력우리 코드에서
FK (정기구학)관절값 q → 툴 자세 xrobot_state_publisher가 TF를 만들 때 (SEC 03)
위치 IK목표 자세 x → 관절값 qik_goto가 /compute_ik 서비스로 한 방에 풀이
미분(속도) IK툴 속도 ẋ → 관절 속도 q̇servo_jog → MoveIt Servo가 4ms마다 자코비안 역산
쉽게 말하면 클릭 IK는 "저기로 가"(목표 하나 → 계획 → 실행, 이산적), 조그는 "누르는 동안 계속 이동"(속도 스트림, 연속적)입니다. 조그는 FK처럼 느껴질 수 있지만 — 버튼이 지정하는 건 관절이 아니라 툴의 이동 방향·속도이고, 6개 관절의 협조 비율은 매 주기 자코비안(관절이 조금 움직일 때 툴이 어느 방향으로 얼마나 움직이는지를 담은 변환표)을 역산해 구합니다. +z 버튼 하나에 툴이 수직 직선으로 올라가는 것이 그 증거입니다(관절 조그였다면 호를 그림). 산업 로봇 티치펜던트의 3단 구성과 대응: 관절 목표(moveit_demo) · 포즈 목표(ik_goto) · 카르테시안 조그(servo_jog).

ik_goto — 목표 입력 규칙

입력 경로z 처리방향(orientation)
3D 패널 바닥 클릭 (z=0으로 수신)fixed_z(기본 0.25m)로 치환 — 클릭은 바닥 평면에만 떨어지므로tool_down=true면 클릭의 yaw만 유지한 채 툴이 아래를 보게 재구성

피드백: /ik_goto/target_marker 구체 — 주황(계산 중) · 초록(도달) · 빨강(실패). 리치 밖 목표는 error_code=-31(NO_IK_SOLUTION)로 거절된다.

servo_jog — 모드 전환이 핵심

UR 서보 설정(ur_servo.yaml)은 forward_position_controller로 출력합니다. 그래서 조그 모드는 컨트롤러를 갈아타야 하고, servo_jog가 시작 시 전환(scaled→forward + start_servo)과 Ctrl+C 종료 시 원복을 자동으로 합니다.

클릭 모드 — ik_goto조그 모드 — servo_jog
방식목표 1개 → 계획 → 실행 (위치 IK)속도 스트림 → 연속 미분 IK

동시 실행 금지 — 조그 모드 중 MoveGroup 실행은 전부 CONTROL_FAILED(-4). SEC 07 사건 9·10 참조.

직접 해보기 ① 클릭: ros2 run arm101 ik_goto → 3D 패널 우상단 Publish pose 도구 → 바닥 클릭-드래그(드래그 방향 = 툴 yaw).
② 타이핑 3D: Publish 패널 추가 → 토픽 /goal_pose · PoseStamped → position에 x·y·z 입력(frame_id는 base_link).
③ 도달 불가 재현: x=1.5를 보내 -31 로그와 빨간 마커 확인 — UR5e 리치는 0.85m.
④ 조그: ik_goto를 Ctrl+C로 끄고 ros2 run arm101 servo_jog → Teleop 패널 2개(패널1: linear-x/y ±0.1 · 패널2: linear-z ±0.1과 angular-z ±0.5 · 10Hz) → 누르는 동안 이동, Ctrl+C 종료 후 list_controllers로 원복 확인.
스스로 점검 ① 클릭만으로는 왜 z를 지정할 수 없나? ② 서보 조그는 왜 FK가 아니라 IK인가?
답 보기 ① Foxglove의 Publish 클릭은 3D 장면의 바닥 평면(z=0)에 레이캐스트되는 도구라, 클릭 한 번에 높이를 담을 수 없다. 그래서 z는 fixed_z 치환 또는 타이핑으로 받는다. ② 버튼이 주는 것은 작업 공간의 속도 ẋ이고, 서보는 q̇ = J⁻¹(q)·ẋ로 관절 속도를 역산한다. 방향이 작업공간→관절공간이므로 정의상 역문제. FK에는 없는 특이점(자코비안 조건수) 감속 설정이 서보에 있는 것도 방증.
SEC 07

장애 복기 — 삽질이 진짜 교재

이번 실습에서 만난 장애 10건. 각각 "증상 → 원인 → 챙길 교훈"으로 정리했습니다. 프로젝트 본편에서 같은 부류의 문제를 다시 만납니다.

장애 10건 전체 — 증상 → 원인 → 교훈
사건 1 · 환경 오염

Gazebo 스폰 노드가 lxml ModuleNotFoundError로 사망

conda (base)의 파이썬이 ROS 노드의 셔뱅을 가로챔 → 시스템 파이썬에만 있는 모듈 실종. 교훈: ROS 터미널과 conda는 격리. 프롬프트의 (base)부터 확인.

사건 2 · 프로토콜 버전

Foxglove 접속이 handshake failed로 반복 거부

브리지 3.4.3은 서브프로토콜 foxglove.sdk.v1만 수락, 구버전 앱은 옛 이름을 제시. curl로 서버에 두 이름을 직접 보내 어느 쪽이 101/400인지 확인해 판정. 교훈: "연결 안 됨"은 양쪽 버전 합의부터 의심 — 서버에 직접 물어보면 확실하다.

사건 3 · 계층 분리 진단

URDF 레이어에서 invalid topic

서버 점검 결과 발행 정상·스키마 정상·Subscription count 0 → 뷰어가 요청을 안 한 것. 클라이언트 설정(Source=Topic 선택)이 원인. 교훈: 파이프라인 장애는 "어느 계층까지 정상인가"를 한 단계씩 자르며 내려간다.

사건 4 · 이름 매칭

MoveIt 실행이 CONTROL_FAILED(-4)

계획은 성공했지만 실행 대상이 비활성 컨트롤러(scaled가 기본인데 jtc를 활성화해 둠) → goal 거부. switch_controller로 해결. 교훈: MoveIt과 ros2_control은 "컨트롤러 이름"으로 약속한다. 드라이버의 initial_joint_controller를 MoveIt 기본과 맞출 것.

사건 5 · 프로세스 수명

pkill 후에도 옛 노드가 살아서 두 로봇이 섞임

launch 부모만 죽고 자식 노드 생존 → /joint_states 발행자 2개, robot_description 충돌. 교훈: launch 종료는 Ctrl+C(SIGINT)로 정상 전파. 강제 종료했다면 pgrep으로 잔존 확인.

사건 6 · 유일 자원

스택을 두 벌 띄우자 spawner가 죽고 데모가 -4

/controller_manager는 이름 고정 — 두 개가 뜨면 서비스 콜이 아무 쪽에나 가서 꼬임. 부가 발견: 멀티라인 명령 붙여넣기로 인자가 깨지면 실물 로봇 모드로 뜬다(ur_ros2_control_node·dashboard_client가 뜨면 그 신호). 교훈: 스택은 한 벌만, 긴 명령은 한 줄로.

사건 7 · 잔재 청소

강제 종료 뒤 새 CLI들이 "A message was lost" · SHM 에러

Fast DDS 공유메모리 파일이 /dev/shm에 잔존해 새 프로세스의 전송 초기화를 방해. 교훈: 비정상 종료 후 통신이 이상하면 fastdds shm clean.

사건 8 · 이름 가림

ik_goto 노드 생성이 AttributeError: __enter__로 즉사

클래스에 만든 handle(msg) 메서드가 rclpy Node의 handle 프로퍼티를 가림 → 부모 __init__의 with self.handle:이 메서드 객체를 만나 실패. 맨 노드·기존 노드·새 노드를 같은 환경에서 비교하는 이분 탐색으로 고립. 교훈: Node 상속 시 부모 속성명(handle·context·executor 등)과 겹치는 이름 금지. "환경 탓 vs 코드 탓"은 최소 재현으로 가른다.

사건 9 · 컨트롤러 점유

servo_jog가 떠 있는 동안 ik_goto가 전부 -4

조그 모드가 forward_position_controller를 활성화하며 scaled_jtc를 내림 → MoveGroup의 실행 대상이 비활성. 사건 4와 같은 -4지만 원인 계층이 다름(이름 불일치 vs 모드 점유). 교훈: -4가 나오면 list_controllers부터 — 지금 활성인 컨트롤러가 무엇인지 확인.

사건 10 · Ctrl+Z ≠ 종료

정지(T 상태)된 프로세스가 컨트롤러·구독을 쥔 채 잔존

Ctrl+Z는 종료가 아니라 suspend — 프로세스가 자원을 쥔 채 얼어붙고, 그 상태에선 SIGTERM도 큐잉만 될 뿐 재개(SIGCONT) 전엔 처리되지 않는다. 정지된 servo_jog는 종료 루틴(컨트롤러 원복)을 실행할 기회조차 없었다. 교훈: 노드 종료는 Ctrl+C. ps의 STAT 열에 T가 보이면 kill -CONT 후 종료 신호.
