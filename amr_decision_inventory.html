이 문서를 읽는 법

이 문서는 AMR 견적 시뮬레이션 서비스를 실제로 만들기 전에 팀이 합의해야 할 결정 항목 60여 개를 컴포넌트별로 모은 목록입니다. 각 항목에는 선택지와 함께 "권고"를 달아 두었는데, 권고는 논의를 시작하기 위한 기본값 제안일 뿐 확정이 아닙니다. 2026-08-19 전체 개괄(MAIN 02 전체 조망) 확정으로 상당수 권고가 팀 방향으로 승격되었습니다 — 이 문서와 개괄의 서술이 다르면 개괄이 우선합니다.

  • 표의 ★ 표시는 크리티컬 패스 — 이 결정이 먼저 정해져야 다른 결정들을 진행할 수 있다는 뜻입니다. 아래 SEC 00에 7건을 모아 두었습니다.
  • 회의에서 쓸 때: SEC 00의 6건부터 확정 → 이후 각 파트 담당자가 자기 섹션(A~J)을 읽고 담당 항목을 결정합니다.
  • 결정이 끝난 항목은 ADR(Architecture Decision Record, "무엇을 왜 그렇게 정했나"를 남기는 짧은 기록 문서)로 저장소에 남깁니다(J3 참조).

시스템 지도 — 각 섹션(A~J)이 시스템의 어디를 결정하는가

아래 그림이 만들려는 시스템의 전체 모습입니다. 상자 안 괄호의 알파벳이 이 문서의 섹션 번호와 일치하므로, 자기 파트의 상자를 찾으면 읽어야 할 섹션이 보입니다.

실선은 데이터가 흐르는 방향, 초록 점선은 3D 검증 결과가 시뮬레이션의 속도 계수를 보정하는 되먹임입니다. 실험 규칙(H)·검증(I)·운영(J)은 특정 상자가 아니라 이 그림 전체에 걸리는 규칙입니다.

SEC 00

크리티컬 패스 요약 — 1~2주차에 반드시 확정

다른 결정들이 줄줄이 걸려 있는 결정 7건입니다. 이것부터 팀 합의로 동결해야 나머지 항목들을 파트별로 병렬 진행할 수 있습니다. 각 항목이 왜 크리티컬한지 이유를 함께 적었습니다.

CP 1 · A1–A3

맵 표현 · 셀 크기 · 좌표계

맵을 격자로 볼지 그래프로 볼지, 칸 하나를 몇 m로 할지, 좌표의 기준 원본을 무엇으로 삼을지. 이 셋이 정해져야 맵 에디터·시뮬레이션·3D 검증이 같은 세계를 두고 말할 수 있다. 여기가 흔들리면 전 컴포넌트를 다시 고친다.

CP 2 · B1

시간 모델 — 고정 틱

시뮬레이션 시간을 1초 단위 틱으로 끊을지 연속으로 흘릴지. MAPF의 예약 테이블, 재계획 주기, 통계 수집이 전부 이 선택 위에 세워진다.

CP 3 · F1

경로 지시 방식 — 중앙 하달

경로를 중앙에서 계산해 로봇에 내려보낼지, 로봇이 알아서 찾게 둘지. 두 계층(SimPy·Isaac)이 서로 다른 방식을 쓰면 "빠른 결과를 3D로 검증한다"는 구도 자체가 무너진다.

CP 4 · C4

RL 일반화 전략

고객마다 다른 맵에서도 통하는 강화학습 디스패처를 만들 수 있는가. 이 프로젝트에서 유일하게 "실패할 수도 있는" 연구 요소라서, 실패 시 휴리스틱으로 후퇴한다는 합의를 미리 해 둔다.

CP 5 · E2/E5

잡 오케스트레이션 · 저장 정책

수백 개의 시뮬레이션 잡을 어떤 방식으로 병렬 실행하고, 결과를 어느 수준까지 저장할지. 인프라 파트가 골격을 잡는 데 필요한 첫 결정.

CP 6 · F5

RTF 실측

3D 시뮬레이터가 이 프로젝트 장비에서 로봇 몇 대까지 실시간 속도를 유지하는지 초반에 실측한다. 이 숫자가 검증 계층이 감당할 수 있는 범위의 물리적 상한이 된다.

CP 7 · J1

4대 계약 동결

입력 JSON 스키마 · Kafka 이벤트 스키마 · 디스패처 인터페이스 · VDA 5050 서브셋. 이 네 가지가 팀 간 경계이므로 주 1~2 안에 동결해야 4개 트랙이 병렬로 달릴 수 있다(개괄 §12·14).

SEC A

데이터 모델 / 입력 스키마 — 시스템 전체의 계약

맵·주문·로봇을 어떤 형식의 데이터로 표현할지 정하는 곳입니다. 여기서 정한 스키마가 맵 에디터·시뮬레이션 엔진·3D 검증이 공유하는 "계약"이 되기 때문에, 한 번 정하면 바꾸는 비용이 가장 큰 섹션입니다.

#결정 항목선택지 / 쟁점권고

SEC B

SimPy DES 엔진

견적 엔진의 본체인 SimPy 시뮬레이션을 어떻게 굴릴지 정합니다. 모든 항목에 공통으로 깔린 긴장은 "현실을 얼마나 충실히 담을까"와 "수백 번 돌릴 만큼 빠를까" 사이의 절충입니다.

#결정 항목선택지 / 쟁점권고
B1 ★시간 모델고정 틱(예: 1초) vs 연속 이벤트고정 틱. MAPF 예약 테이블이 이산 타임스텝 전제라 정합. 틱 크기 = 셀 통과 시간과 일치시키면 "1틱 = 1셀 이동" 단순화
B2이동 모델셀 단위 이벤트(틱마다) vs 구간 단위 이벤트셀 단위 — 예약 테이블·경합·데드락이 자연 창발. 성능 문제 시 무경합 구간만 벌크 스킵 최적화
B3가감속 반영무시(등속) vs 구간 평균 유효속도 vs 프로파일유효속도 보정 계수(에뮬레이션 실측으로 캘리브레이션). 프로파일 시뮬은 DES 목적에 과잉
B4 ★재계획 주기이벤트 트리거(작업 완료 시) vs 고정 윈도우(RHCR 방식 W틱마다)RHCR 스타일 고정 윈도우 + 작업 발생 이벤트 병행. 윈도우 크기 h는 실험 파라미터
B5데드락 처리발생 불가 설계(예약 보장) vs 탐지 후 재계획예약 테이블 기반이면 원천 차단 가능. 단 "탐지 카운터"는 남겨서 버그 검출용으로
B6확률 분포 선택픽 시간, 주행 변동: 상수 / 정규 / 로그정규 / 삼각픽 시간 로그정규(현장 데이터 관례), 주행은 v1 결정적 + 유효속도 보정. 분포 가정을 리포트에 명시 (VDI 3633)
B7 ★워밍업 기간없음 vs 초기 과도상태 절단필수. 빈 창고에서 시작하는 초기 구간은 통계에서 제외. 절단 시점 결정 방법(Welch 그래프 or 고정 30분) 문서화
B8런 길이 / 반복 수고정(8시간 × 20시드) vs CI 폭 기준 적응적v1 고정 (8h × 20시드), CI 폭이 목표(예: ±5%) 초과 시 시드 추가하는 룰 명시
B9통계 수집 방식전 이벤트 로그 vs 온라인 집계이중화: 집계 지표는 항상, 상세 이벤트 로그는 플래그로 (리플레이/디버깅용, 용량 문제 → E5)
B10성능 목표—1런(8h, 로봇 10대) < 10초 목표 설정 후 프로파일링. what-if 응답성의 상한 결정

이 표의 용어

  • 틱(tick) — 시뮬레이션 시간의 최소 단위. "1틱 = 1초 = 로봇이 한 칸 이동"으로 맞추면 계산이 크게 단순해진다
  • 워밍업 — 시뮬레이션 초반, 텅 빈 창고가 정상 가동 상태로 차오르기까지의 구간. 이 구간을 통계에 포함하면 결과가 실제보다 나쁘게 왜곡된다
  • Welch 그래프 — 지표 곡선이 언제부터 안정되는지를 눈으로 확인해 워밍업의 끝을 판단하는 방법
  • 로그정규 분포 — 대부분은 짧고 가끔 매우 긴 값이 나오는 치우친 분포. 사람의 피킹 시간처럼 "가끔 오래 걸리는" 작업의 관례적 모형
SEC C

디스패처 / AI

"어느 로봇이 어느 작업을 맡을지"를 정하는 두뇌입니다. 규칙 기반 → 헝가리안 → 강화학습 순으로 갈아끼우며 성능을 비교하는 것이 서비스의 차별점이므로, 교체 가능한 인터페이스(C1)와 강화학습이 실패했을 때의 대비선(C4)이 이 섹션의 핵심입니다.

#결정 항목선택지 / 쟁점권고
C1인터페이스 시그니처assign(pending_tasks, robot_states, map_ctx) -> allocations전략 패턴 고정 (기결정). 반환에 "할당 보류"도 표현 가능해야 함
C2할당 시점즉시(작업 발생 시) vs 배치(주기적 일괄)배치 주기와 B4 재계획 윈도우를 동기화 — 헝가리안이 배치 전제이므로
C3헝가리안 비용행렬순수 거리 vs 거리+대기 vs 경합 페널티 포함단계적: v1 거리+대기, v1.5 경합 페널티 (TAPF 절충안)
C4 ★RL 일반화 전략(a) 맵별 재학습 (b) 맵 불변 관측 설계로 zero-shot (c) RL을 옵션 연구로 축소최대 함정 — 견적 서비스는 고객마다 맵이 다름. 맵 특정 정책이면 서비스 성립 불가. 권고: 관측을 맵 불변 특징(작업까지 경로비용, 로봇 부하, 구역 혼잡도)으로 설계 + 랜덤 레이아웃 학습. 실패 시 (c)로 후퇴하고 리포트에는 휴리스틱을 기본 탑재
C5RL 관측/행동 공간가변 로봇/작업 수 문제최대 N 고정 + 마스킹, 또는 (작업,로봇) 쌍 스코어링 방식. 후자가 일반화에 유리
C6RL 알고리즘/프레임워크PPO(SB3) vs DQN vs RLlibPPO + Stable-Baselines3. 팀 학습 곡선 최소화
C7학습/평가 분리—학습용 시드·레이아웃과 평가용 완전 분리. 평가 시나리오는 스윕과 동일 조건
C8보상 설계-makespan vs 처리량 vs shaped(대기 페널티 등)처리량 기반 + 대기시간 페널티. makespan은 lifelong 설정에 부적합

이 표의 용어

  • 헝가리안 알고리즘 — 로봇×작업의 비용표에서 총비용이 최소가 되는 짝짓기를 찾는 고전 할당 알고리즘
  • RL / PPO / SB3 — 보상을 최대화하도록 스스로 정책을 학습하는 방법(RL, 강화학습), 그 대표 알고리즘(PPO), 널리 쓰이는 구현 라이브러리(Stable-Baselines3)
  • zero-shot 일반화 — 학습 때 본 적 없는 새 맵에서도 재학습 없이 통하는 것. 고객마다 맵이 다른 견적 서비스에서는 이게 안 되면 RL 자체가 무용지물
  • 마스킹(masking) — 로봇·작업 수가 상황마다 달라지는 문제를, 최대 개수를 고정해 두고 "빈 자리는 무시"로 처리하는 기법
  • makespan — 마지막 작업이 끝나는 시각. 작업 목록이 고정된 일회성 문제에는 맞지만, 작업이 끝없이 들어오는 창고에는 부적합한 지표
SEC D

경로계획 — MAPF 구현

SimPy 안에 들어갈 경로계획기(MAPF)의 구현 수준을 정합니다. v1 방식 — 우선순위 순차 계획 + 시공간 예약 테이블 — 은 이미 정해져 있고, 여기서는 그 세부 규칙만 남았습니다.

#결정 항목선택지 / 쟁점권고
D1v1 플래너Prioritized Planning + 시공간 예약 테이블기결정. 우선순위 규칙(작업 긴급도? 선착?)만 추가 결정
D2예약 테이블 구조dict[(cell, t)] vs 인터벌 기반dict 기반으로 시작, 성능 병목 시 개선
D3로봇 점유 모델1로봇 = 1셀 vs 풋프린트 다셀1셀 (A2와 연동). 이기종 크기 로봇은 v2
D4회전 비용무시 vs 회전 시간 반영반영 (틱 단위 근사). 차동구동 AMR은 회전이 실측 시간의 유의미한 비중
D5대기(idle) 로봇 위치현 위치 정차 vs 지정 대기 구역 복귀지정 대기 구역 — 통로 점거 방지. 대기 구역 배치가 what-if 변수가 됨
D6벤치마크 검증—Stern 2019 공개 벤치마크 소규모 인스턴스로 플래너 정합성 확인 (V&V 스토리)

이 표의 용어

  • 시공간 예약 테이블 — "(칸, 시각)" 조합을 먼저 찜한 로봇이 임자가 되는 장부. 뒤 순번 로봇은 찜된 조합을 피해서 경로를 찾는다. 충돌이 원천적으로 안 나는 이유
  • 우선순위 순차 계획(Prioritized Planning) — 로봇에 순번을 매기고 1번부터 차례로 계획하는 방식. 빠르지만 뒤 순번일수록 손해를 본다

알고리즘별 원리와 비교(예약 테이블·CBS·RHCR)는 MAIN 04 이론 기반 SEC 02에 풀어 두었습니다.

SEC E

백엔드 / 인프라

수백 개의 시뮬레이션 런을 실제로 돌리고 결과를 저장하는 기반 설비입니다. 목표는 화려함이 아니라 "스윕 한 번 = 잡 한 벌"이 실패 없이 도는 것입니다.

#결정 항목선택지 / 쟁점권고
E1API 패턴동기 vs 비동기 잡(제출→폴링/푸시)비동기: POST /scenarios → jobId → WebSocket 진행률 + GET 결과
E2 ★잡 오케스트레이션K8s Job 직접 생성 vs 큐(Redis/Celery류) 경유 vs K8s Indexed JobScenario API가 K8s Indexed Job 생성(스윕 1개 = Job 1개, 인덱스 = 시나리오 조합). 별도 큐 시스템 추가는 과잉
E3잡 실패 정책재시도 횟수, 타임아웃, 부분 실패 시 결과 처리재시도 2회, 런 타임아웃 5분, 부분 실패는 결과에 "미완료 조합" 명시 (투명성)
E4Kafka 메시지 스키마JSON vs Avro + Schema Registryv1 JSON + 스키마 문서화. Avro/Registry는 학습 가치 있으나 팀 부하 고려해 선택
E5 ★결과 저장 정책전 이벤트 로그(런당 수십 MB × 360런) vs 집계만집계 + 시계열 다운샘플 기본, 상세 로그는 "대표 런"(중앙값 시드)만 보존 — 리플레이 시각화용
E6DB 스키마scenario / sweep / run / metric 계층 설계run은 (sweep_id, param_combo, seed) 유니크. 지표는 hypertable
E7로컬 개발 환경docker-compose vs 로컬 k3d/k3s vs 클라우드개발은 docker-compose, 스윕 데모는 k3d(로컬) — 클라우드 비용 리스크 회피. 발표용 클러스터는 막판 결정
E8멀티테넌시/인증없음 vs 세션 수준 vs 완전 격리데모 수준: 프로젝트(견적 건) 단위 스코프만. 진짜 인증은 범위 외 명시
E9저장소 구조모노레포 vs 멀티레포모노레포 + 스키마/공용 타입을 shared 패키지로 — 계약(A6) 관리가 쉬움
E10CI/CD—GitLab CI (SSAFY 자산 재사용): 스키마 검증 + 단위 테스트 + 소규모 스모크 시뮬

이 표의 용어

  • K8s(쿠버네티스) / Indexed Job — 컨테이너 작업을 여러 서버에 자동 배치하는 오케스트레이터. Indexed Job은 "같은 잡을 번호만 바꿔 N개 병렬 실행"하는 기능이라, 조합 번호별로 도는 스윕과 정확히 맞아떨어진다
  • Kafka — 컴포넌트 사이에 이벤트를 순서대로 흘려보내는 메시지 버스. 시뮬레이션 진행 상황·결과 이벤트가 이 위로 흐른다
  • Avro / Schema Registry — 메시지 형식을 엄격하게 버전 관리하는 도구 세트. 학습 가치는 있으나 v1은 JSON + 문서화로 충분
  • hypertable — 시계열 DB(TimescaleDB)에서 시간 기준으로 자동 분할되는 큰 테이블. 시계열 지표 저장용
  • k3d — 개인 PC의 도커 안에 가벼운 쿠버네티스를 띄우는 도구. 클라우드 비용 없이 스윕 병렬 실행을 시연할 수 있다
SEC F

에뮬레이션 계층 — ROS2 + Isaac Sim

빠른 SimPy 결과를 믿어도 되는지, 물리엔진이 있는 Isaac Sim에서 소수의 로봇을 실제처럼 굴려 확인하는 검증 계층입니다. 두 계층이 "같은 시스템"을 시뮬레이션하도록 만드는 것(F1)이 이 섹션의 전부라고 해도 과언이 아닙니다.

#결정 항목선택지 / 쟁점권고
F1 ★경로 지시 방식(a) VDA 5050 노드/엣지 경로 하달(중앙 계획) (b) 목적지만 주고 Nav2 자율 경로(a) 필수. SimPy는 중앙 플래너 세계인데 Isaac에서 Nav2가 제멋대로 경로를 고르면 두 계층이 서로 다른 시스템을 시뮬레이션하는 것 — 정합성 비교가 무의미해짐. VDA 5050 표준 자체가 (a) 모델. Nav2는 노드 간 구간 주행만 담당
F2VDA 5050 서브셋order/state/connection 필수, instantActions/factsheet/visualization 선택필수 3종 + instantActions(정지/재개, 데모용). 버전은 2.0 기준 명시
F3맵 → USD 변환수동 씬 제작 vs 시맨틱 그리드에서 자동 생성 스크립트자동 생성 (랙=박스 프리미티브 수준). "고객 맵이 곧 검증 환경"이 되는 것 자체가 데모 포인트
F4검증 대상 로봇iw.hub 메인 + MiR 250 서브 (기결정)Nova Carter로 파이프라인 스모크 테스트 먼저
F5 ★RTF 실측—프로젝트 극초반에 RTX 5080 기준 "RTF ≥ 0.9 유지 최대 대수" 실측 → 검증 스코프 확정. 센서(라이다 레이 수) 최소화 설정 포함
F6시간 기준sim time vs wall clock, VDA 5050 timestampROS 노드는 use_sim_time 통일, VDA 5050 timestamp는 sim time 사용 + FMS 쪽 타임아웃을 RTF 보정
F7정합성 오차 지표무엇을 비교?3단: ①구간(엣지) 주행시간 분포 ②작업 사이클 타임 ③시간당 처리량. ①이 보정 루프의 입력, ③이 리포트 헤드라인
F8보정 루프 절차—에뮬레이션 실측 엣지 주행시간 → SimPy 유효속도 계수 갱신 → 재스윕. 1회 이상 왕복을 일정에 명시
F9어댑터vda5050_connector 계열 오픈소스 이식 (기결정)자작 금지. 포크 후 필요 수정만

이 표의 용어

  • FMS(Fleet Management System) — 여러 AMR을 지휘하는 중앙 관제 소프트웨어. 본 프로젝트에서는 SimPy 세계의 중앙 플래너가 이 역할을 겸한다
  • USD — Isaac Sim이 쓰는 3D 장면 파일 형식. 고객이 그린 맵 데이터에서 이 파일을 자동 생성하는 것이 F3
  • 스모크 테스트 — 본격 검증 전에 "일단 켜지고 한 바퀴 도는지"만 확인하는 가벼운 시험
  • RTF ≥ 0.9 — 시뮬레이터가 실제 시간의 90% 이상 속도를 유지한다는 뜻. 이 밑으로 떨어지면 시간 왜곡이 커져 검증 데이터로 쓰기 어렵다
SEC G

프론트엔드

고객이 맵을 그리고 결과를 읽는 화면입니다. 모든 결정의 판단 기준은 한 가지 — 견적 리포트가 설득력 있게 보이는가.

#결정 항목선택지 / 쟁점권고
G1스택React + 캔버스 라이브러리(Konva/SVG/deck.gl)React + Konva (2D 탑뷰 기결정). deck.gl은 과잉
G2에디터 검증저장 시 검증 vs 실시간실시간: 연결성(모든 스테이션 도달 가능), 최소 통로 폭, 충전소 개수 경고. 잘못된 맵이 시뮬 오류로 늦게 발견되는 것 방지
G3결과 화면 우선순위곡선/히트맵/리플레이①대수–처리량–TCO 곡선(선택 UI) ②병목 히트맵 ③대표 런 리플레이 애니메이션 — 이 순서로 구현
G4리포트 출력웹 뷰 vs PDF 생성웹 뷰 우선, PDF는 인쇄 CSS로 저비용 대응. 전용 PDF 생성은 여유 시
G5진행률 UX스피너 vs 스윕 매트릭스 실시간 채움스윕 조합별 완료 상태가 채워지는 매트릭스 — "수백 개 시뮬이 병렬로 도는 중"이 보이는 것 자체가 임팩트

이 표의 용어

  • Konva — 웹 캔버스에 도형을 그리고 드래그하게 해주는 자바스크립트 라이브러리. 2D 탑뷰 맵 에디터의 그리기 엔진
  • TCO(Total Cost of Ownership) — 구매비 + 운영비를 합친 총소유비용. "몇 대가 최적인가"의 경제성 축
  • 히트맵 — 정체가 심한 칸일수록 진하게 칠한 지도. 병목이 어디서 생기는지 한눈에 보여준다
SEC H

실험 설계 / 통계

시뮬레이션 결과를 "통계적으로 믿을 수 있는 주장"으로 만드는 실험 규칙입니다. 같은 조건이라도 시드에 따라 결과가 흔들리므로, 몇 번 반복하고 어떻게 비교할지를 미리 정해 둡니다.

#결정 항목선택지 / 쟁점권고
H1스윕 격자대수 범위 자동 결정 방법하한: 총 수요/로봇 처리능력 추정치, 상한: 포화 감지(증분 <2% 시 중단)로 적응적 확장
H2신뢰구간t-분포 기반 95% CI (시드 간)기결정. 리포트에 CI 항상 병기
H3민감도 분석OAT(one-at-a-time) vs 전역(Sobol)v1 OAT: 픽 시간 ±20%, 수요 ±30%, 유효속도 ±10%에 대한 최적 대수 안정성. Sobol은 과잉
H4디스패처 비교 프로토콜—동일 시드 쌍대 비교(paired) — 분산 줄고 통계 검정 명확
H5최적점 선정 규칙처리량 목표 충족 최소 대수 vs ROI 최대점둘 다 제시하고 선택은 고객에게 — "선택하게 하는" 제품 철학과 일치

이 표의 용어

  • OAT(One-At-a-Time) — 변수를 하나씩만 흔들어 결과가 얼마나 민감한지 보는 방식. 간단하지만 변수 간 상호작용은 못 본다
  • Sobol — 모든 변수를 동시에 흔드는 전역 민감도 분석. 정밀하지만 계산량이 커서 v1에는 과잉
  • 쌍대 비교(paired) — 디스패처 A와 B를 같은 시드(= 같은 주문 흐름)에서 맞붙여 우연에 의한 차이를 제거하는 비교 방법
SEC I·J

검증(V&V — VDI 3633) · 프로젝트 운영

만든 시뮬레이션이 맞다는 근거를 어떻게 남길지(V&V)와 팀 운영 규칙입니다. VDI 3633은 시뮬레이션 프로젝트의 검증 절차를 정리한 독일 공학 지침으로, "가정을 명시하고 검산한다"는 이 문서 전체 원칙의 출처입니다.

  • Verification(검증) — "모델을 설계대로 올바르게 구현했는가". 예: 생성한 주문 수와 완료+미완료 수가 정확히 맞아떨어지는지 확인
  • Validation(타당성 확인) — "모델이 현실을 충분히 닮았는가". 예: SimPy 결과를 Isaac 실측·공개 벤치마크와 비교

I — 검증

#결정 항목내용
I1Verification보존 법칙 체크(생성 주문 수 = 완료+미완료), Little's Law 검산(L=λW), 로봇 1대 극한 케이스의 해석해 대조
I2ValidationMAPF 공개 벤치마크 소규모 대조(D6), SimPy vs 에뮬레이션 정합성(F7-8), 문헌 처리량 수치와의 자릿수 비교
I3문서화모든 가정·분포·보정 계수를 리포트 부록에 — "가정 명세서"가 투명성 주장의 실체

J — 프로젝트 운영

#결정 항목권고
J1인터페이스 경계팀 간 계약 = ①입력 JSON 스키마 ②Kafka 이벤트 스키마 ③디스패처 인터페이스 ④VDA 5050 서브셋. 이 4개를 1주차에 동결
J2데모 폴백라이브 실패 대비: 스윕은 사전 실행 결과 캐시, 에뮬레이션은 녹화 영상 준비. what-if만은 라이브 사수
J3결정 기록본 문서의 각 결정을 ADR(Architecture Decision Record) 경량 포맷으로 저장소에 — 면접에서 "왜"를 답하는 원천
이 문서를 쓰는 법 각 표의 "권고"는 논의 기반 기본값 제안이지 확정이 아니다. 팀 회의에서 ★ 6건(SEC 00)부터 순서대로 확정하고, 확정된 결정은 J3에 따라 ADR로 저장소에 남긴다.
