## 0. 한 줄 정의

3PL(제3자 물류)이 AMR 도입을 결정할 수 있도록, 창고·물류 조건을 받아 시뮬레이션으로 **권장 대수·기종, KPI, 검증 영상**을 담은 견적서를 만들어 보내는 **요청 접수형 서비스**다.
셀프서브 SaaS가 아니다. 요청은 큐에 쌓이고, 운영자가 검토·검수하며, 결과는 나중에 발송된다.

## 2. 서비스 흐름 8단계

| 단계 | 이름 | 주체 | 인터페이스 | 무엇을 |
|---|---|---|---|---|
| ① | 견적 요청 접수 | 고객 → 견적 BE | REST `/api/requests` | 창고·물류 조건 입력. 큐 순번·예상 소요 회신 |
| ② | 운영 검토·시나리오 컴파일 | 운영자 | 웹 콘솔 | 요청을 정제해 시나리오 패키지(zones.json·맵·분해 규칙·수요)로 컴파일 |
| ③ | 스윕 잡 소비 | RabbitMQ → 계산 엔진 워커 | AMQP, 우선순위 큐, DLQ | 잡 = 시나리오 패키지 + 스윕 범위. 워커는 수평 확장 |
| ④ | 구성 탐색·θ 추론·DES | 계산 엔진(EC2 k3s Job) | in-process | trial마다 AI 모델이 θ 11개 추론 → 통행 비용 → FMS 커널로 가상 시간 실행 × 시드 반복 |
| ⑤ | Isaac 물리 검증 런 | 런 오케스트레이터 → 시뮬 스택 + GPU | k8s API, MQTT `sim/control` | 상위 구성만 GPU 런 큐에 적재. 시뮬 WMS·FMS 파드 기동, Isaac·에이전트 스폰 |
| ⑥ | KPI 집계·아티팩트 | sim-runner → MinIO, 워커 → BE | S3 API presigned PUT, AMQP 결과 이벤트 | 배속 영상(MP4)·리플레이(JSON)·히트맵(PNG). PG에 KPI·아티팩트 메타 |
| ⑦ | 리포트 작성 | LLM 초안 + 운영자 검수 | 웹 콘솔 | 권장 구성·곡선·영상 임베드 |
| ⑧ | 견적서 발송 | 견적 BE | 이메일·다운로드 | 발송 후 요청 종료 |

운영자 개입은 ②와 ⑦ 두 곳이다. ①과 ⑧ 사이는 전부 내부 배치다.

## 3. 시스템 아키텍처

### 3.1 웹 인프라 2층

| 층 | 구성 | 수명 | 저장소 |
|---|---|---|---|
| 상시 견적 서비스 | React 웹 콘솔 + nginx(:443 단일 인그레스), 견적 BE(Spring), PostgreSQL, RabbitMQ, MinIO, 견적 산출 | 상시 | PostgreSQL(영속), MinIO(아티팩트) |
| 런 단위 시뮬 스택 | 시뮬 WMS(Spring + H2 인메모리), FMS 코어(Python), 수요 생성기 | 런마다 기동·폐기 | H2(런과 함께 소멸) |
| 공용 | EMQX(MQTT 브로커)는 상시. 제어 채널이 런보다 먼저 있어야 함 | 상시 | 없음 |

원칙: **영속은 견적 도메인, 휘발은 시뮬 도메인.** H2는 프로파일 전환으로 PG 승격이 가능하도록 JPQL만 쓴다(네이티브 쿼리 금지, PG 호환 모드).

### 3.2 기기 배치

| 기기 | 사양 | 올라가는 것 |
|---|---|---|
| EC2 t3.xlarge | 4 vCPU · 16 GB · IAM 불가 → 관리형 AWS 서비스 0, 전부 k3s 자체 호스팅 | 상시 견적 서비스, 시뮬 스택 파드, 계산 엔진 Job, 런 오케스트레이터, EMQX. 이미지는 GHCR, 인증서는 certbot |
| GPU 서버 ×1 | RTX 5080 16 GB, 홈서버, Isaac Sim 6.0.1 | amr-agent(ROS 2) ×N, Isaac, sim-runner 데몬. 네이티브 실행 |
| 연결 | 홈서버 → EC2 tailscale 아웃바운드(캠퍼스 UDP 차단 시 DERP 릴레이) | |

확장: GPU 노드 추가 = GPU 런 큐 소비자 추가. 임대 GPU(L40S 등)면 Isaac을 컨테이너 Job으로 바꾸고 시뮬 스택 파드를 GPU 노드로 옮기며, 큐 깊이 기반 오토스케일을 붙인다. 5080 1대는 그 그림의 N=1이다.

### 3.3 큐잉 2단

| 큐 | 브로커 | 소비자 | 목적 |
|---|---|---|---|
| 요청 잡 큐 | RabbitMQ | CPU 워커 ×N | 스윕 잡. 우선순위·DLQ·재시도 |
| GPU 런 큐 | RabbitMQ | GPU 수 = 소비자 수 | Isaac 검증 런 직렬화. 큐 순번·ETA 회신의 근거 |

스윕 루프와 정지 규칙(무릎 판정)은 계산 엔진이 소유한다. 견적 BE는 대수 n을 반복 호출하지 않고 스윕 범위만 잡에 싣는다. 팀 백엔드↔AI API 초안의 요청·응답 스키마(run_id·seed·warehouse·amr·orders → kpi)는 **trial 단위 어댑터 계약**으로 그대로 채택한다.

### 3.4 스택

React · nginx · Spring Boot · PostgreSQL · H2 · RabbitMQ · EMQX · MinIO · Python · ROS 2 Humble · Isaac Sim 6.0.1 · Docker/k3s · GHCR · certbot · tailscale. 다이어그램 표기: Docker 배지 = k3s 파드, EC2 파랑 실선 / GPU 초록 실선, 견적 도메인 보라 점선 / 시뮬 도메인 앰버 점선, 두 WMS 청록 관계선.

## 4. FMS

### 4.1 2-트랙 구조 (팀 FMS 파트)

| 트랙 | 산출물 | 인터페이스 |
|---|---|---|
| A안 AI | 창고 생김새·짐 흐름·통로 구조 텐서 + 운영 조건 → 통행 규칙 파라미터 θ 11개(연속 8 + 범주 3) | `3_FMS/contracts/guidance_types.py` (스키마 v2, 합의 진행 중) |
| B안 알고리즘 | PIBT 이동 계층. θ → 통행 비용(from_theta). 대수 스윕 벤치마크 | 같은 계약. 벤치 결과는 `3_FMS/docs/` |

θ는 trial마다 추론되고, DES와 Isaac 검증 런이 **같은 θ**를 쓴다.

### 4.2 PIBT 헤딩 모델 (인터페이스 수준)

- 격자 1.0 m 유지. 로봇 상태 = (칸, 방향). 차체(iw.hub 1.44 m)가 셀보다 길어 **자기 칸 + 뒤 칸 2칸 점유**.
- 액션 = 대기 · 전진 · 좌/우 회전(틱 소모, 스윙 칸 예약) · 후진. 거리장은 θ 가중 다익스트라.
- Isaac에서의 회전 중 충돌 실측이 발단. 셀 확대(2.0 m)는 도킹칸 겹침으로 기각.
- 회전을 모델에 넣으면 권장 대수의 포화점이 한 단계 이동한다(팀 벤치 문서). 회전 시간 상수는 Isaac 실측(2026-09-06, `sil/calibration/turn_probe/`)으로 확정: 회전 중심 = 구동축 = 포즈 원점(이탈 ≤ 1.3 cm), 차체는 축 기준 앞 0.40 m·뒤 1.03 m 돌출 → 뒤 칸 1개 점유, 스팟턴 스윙 반경 1.09 m(주변 8칸에 걸침), 90° 폐루프 회전 1.9 s(T4 한계 1.2 rad/s) → 1 s 틱 기준 회전 2틱.

### 4.3 결정 커널 + 실행 셸 2종

FMS 코어는 시계·난수를 주입받고 I/O가 없는 순수 결정 커널이다. `step(world, now, events) → decisions`.

| 셸 | 시계 | 용도 |
|---|---|---|
| 하네스 | 가상 시계, 동기 in-process | DES(④) |
| MQTT 데몬 | 틱 기반. 배리어 동기 여부는 FMS 파트 확인 중 | Isaac 검증 런(⑤) |

### 4.4 WMS 공유 원칙 (C안)

**측정 대상은 공유, 환경은 모델링.** FMS 커널은 DES와 검증 런이 공유한다. WMS는 DES에서 확률 모델(WMS 라이트: 주문 생성·라인 합침·배차·서비스 타이머)로, 검증 런에서는 실제 Spring 시뮬 WMS로 돈다. 두 WMS는 ②에서 컴파일된 **하나의 시나리오 패키지**의 두 소비자다. 골든 시나리오 패리티 테스트로 둘의 정합성을 지킨다.

### 4.5 미션 범위

팀 FMS 구현 범위 문서 기준: 입고(인바운드 버퍼 → 통로 입구 버퍼) + 출고(통로 입구 버퍼 → 패킹 직행), 멀티라인 주문은 같은 통로 라인 묶음이 토트 1개. 배터리·적재 용량·피커 작업 시간 모델은 서빙 준비 단계 로드맵. SIL은 주행·혼잡 + 리프트 도킹 1장면.

### 5.1 T4 에이전트: FMS 틱 ↔ VDA 5050

| PIBT 액션 | VDA 5050 | 에이전트 |
|---|---|---|
| 전진 1칸 | 다음 노드 released | 헤딩 정렬(스팟턴) → 직진 → 셀 중심 정지 |
| 후진 1칸 | 엣지 orientation π, TANGENTIAL | 헤딩 유지, 후진 |
| 회전 ±90° | 같은 좌표 노드 + 새 theta | 제자리 회전 |
| 대기 | 새 노드 없음 | 정지 |
| ack | `state.lastNodeId` 변화 즉시 발행 | FMS는 전 로봇 ack 후 다음 틱 |

E2E(가짜 로봇): 7틱 계획 통과, 정지 오차 4 mm, 헤딩 1.2°. **1 m 틱당 2.2 s, 90° 회전 2.3 s** (램프 1.0 m/s², 최고 0.8 m/s). FMS의 틱 1 s 가정보다 길다. 배리어 틱이면 Isaac 런은 실시간의 절반 이하다.

### 5.2 FMS 파트가 넘긴 Isaac 실행 요구사항

| 경유점 오차 ≤ 0.1 m | T4 구현(4 mm) |
| 틱 배리어 동기 | 에이전트 ack 구현. 방식은 FMS 파트 재확인 중 |
| 후진 1칸 프리미티브 | T4 구현 |
| iw.hub 앞축 위치·회전 각속도 실측 | 완료(2026-09-06). 구동축 = 포즈 원점, 앞 0.40 m·뒤 1.03 m 돌출, 회전 중심 편차 ≤ 1.3 cm, 각속도 지령 대비 95~97 %, 90° 폐루프 1.9 s(정착 포함 2.5 s), 회전 중 위치 표류 ≤ 1.4 cm. `sil/calibration/turn_probe/` |

## 6. 계산 엔진과 시나리오

- DES의 현재 실체는 팀의 틱 시뮬(sim_v2). SimPy·Optuna 표기는 후속 계획이다.
- Isaac 검증 런은 분 단위 미니 시나리오다. 갭 캘리브레이션은 검증 대상 구성에 한해 DES도 같은 시간창으로 재실행해 비교한다.
- 시나리오 패키지 = zones.json · 맵 · 주문 분해 규칙 · 수요 프로파일 · rack_id ↔ 시뮬 좌표 매핑. 재현성 키 = 시나리오 해시 + 시드.

## 8. 런 오케스트레이터

EC2 k3s 위 단일 파드. GPU 런 큐 소비 → 시뮬 WMS·FMS 파드 기동 → WMS 시나리오 주입 완료 대기 → sim-runner에 `start`/`go` → 하트비트·시뮬 시각 감시 → `stop` → 아티팩트 키 수집 → 결과 이벤트 발행·ack → 파드 삭제. 상태: QUEUED → PROVISIONING → LOADING → RUNNING → COLLECTING → DONE / FAILED. 런 ID 기준 멱등, DLQ, 재기동 시 조정 단계.
