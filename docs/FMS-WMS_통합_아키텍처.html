설계 원칙 — 웹 인프라는 두 층으로 분리한다: 견적 서비스(FE·견적 BE·PG)는 상시 가동이고 고객·운영자 대면이며, 시뮬 스택(시뮬 WMS·EMQX·FMS)은 런 단위로 기동·리셋되는 내부 엔진이라 런 스코프 상태가 영속 DB와 섞이지 않는다 — 시뮬 WMS의 주문·재고 상태는 H2 인메모리(런과 함께 소멸, Spring 프로파일 전환으로 실물 PG 승격 가능)이고, 영속이 필요한 결과물만 parquet·S3와 견적 PG로 빠진다. 접수(①)와 발송(⑧) 사이는 전부 내부 배치이고, 검토(②)·검수(⑦) 두 곳에 운영자가 개입한다. MAPF는 고정 솔버(v1 = PP+시공간 예약, 슬롯만 유지)이며 스윕이 탐색하는 것은 구성(AMR 대수 × 기종)이다. FMS 코어는 시계·난수를 주입받고 I/O가 없는 순수 결정 커널(step(world, now, events) → decisions)이고, 동기(DES)·비동기(라이브)의 차이는 실행 셸 2종이 흡수한다 — SimPy 하네스는 가상 시계로 즉시 호출하고, MQTT 데몬은 비동기 state를 인박스에 모아 500ms 틱마다 스냅샷으로 호출한다. 명령 반영 지연·슬립은 결함이 아니라 물리 런에서 재서 DES에 넣는 캘리브레이션 대상이며, 이것이 성립하려면 오히려 코어가 같아야 한다. 공유의 경계는 "측정 대상은 공유, 환경은 모델링"이다: FMS는 견적 숫자를 만드는 측정 대상이라 커널을 공유하고, WMS는 환경이라 DES에서는 확률 모델(주문→TO 분해 규칙 + 피킹 시간 분포)로 대체하며 검증 런에서만 실제 Spring WMS가 실제 인터페이스(biz/order · fms/event)로 붙는다 — 검증 런이 현장 배포 형태(FMS ↔ 고객 WMS)와 동형이 되고, 통합 자산은 Spring WMS에 남는다. 두 WMS는 완전 독립이 아니라 같은 환경 정의의 두 소비자다: ②에서 컴파일된 하나의 시나리오 패키지(zones.json · 맵 · 분해 규칙 · 수요 프로파일)를 DES 워커는 잡 페이로드로, 시뮬 WMS는 런 기동 시 주입으로 받는다. 구현 드리프트는 골든 시나리오 패리티 테스트(같은 주문 스트림 → 동일 TO 목록)로 막는다. SimPy DES가 구성별 분포를 만들고 Isaac 물리 검증 런이 갭을 보정하며, 같은 FMS 코어가 DES·검증 런·라이브 데모 세 곳에서 돌기 때문에 견적과 시연이 한 몸이다. 런 오케스트레이션은 계산 엔진 워커가 전담한다: EC2 측 시뮬 파드는 k8s API로 생성·삭제하고, GPU 측은 상주 sim-runner 데몬에 MQTT sim/control로 start/stop을 지시한다(헬스비트 감시·타임아웃 강제 정리, GPU 1대라 Isaac 런은 직렬 큐). 이 제어 채널이 런보다 먼저 있어야 하므로 EMQX는 상시 가동이다. 큐잉 정책은 2단이다: 요청 잡 큐(RabbitMQ — 우선순위·DLQ, CPU 워커 수평 확장)와 GPU 런 큐(GPU 수 = 소비자 수, 직렬). GPU가 병목이므로 접수 시 큐 깊이로 대기 순번·ETA를 회신하고, 운영자 콘솔에서 우선순위를 조정한다 — 확장은 GPU 서버를 붙이는 것으로 끝난다. 런 아티팩트는 견적의 증거물이다: 검증 런마다 배속 영상(MP4, MJPEG 프레임 허브→ffmpeg NVENC) · 인터랙티브 리플레이(odom 로그→JSON) · 궤적 히트맵을 수집해 MinIO(S3 호환 단일 파드 — EC2 내부, AWS 계정·과금 없음)에 적재하고 presigned URL로 웹 견적서에 임베드·PDF에 QR로 연결한다 — "물리 검증"이라는 주장에 고객이 눈으로 확인하는 실체를 붙인다. 인프라 제약: EC2는 t3.xlarge(4 vCPU · 16 GB) 1대이고 IAM 접근이 없다 — 관리형 AWS 서비스는 0, 전부 k3s 자체 호스팅(PG·RabbitMQ·EMQX·MinIO·BE·시뮬 파드 합산 상주 메모리 ≈ 5 GB로 여유), 이미지는 GHCR, 인증서는 certbot, 외부 노출은 nginx :443 하나, 홈서버↔EC2는 tailscale 아웃바운드. DES 워커는 EC2 k3s Job으로 둔다 — 버스트형 CPU지만 적립 크레딧(2,304 ≈ 4 vCPU 풀가동 16 h)이 산발적·비동기 견적 배치에 충분하고, 고갈돼도 40%로 느려질 뿐 멈추지 않으며, 홈서버 가용성에 견적 계산이 묶이지 않는다. 대형 스윕이 필요하면 같은 워커 이미지를 홈서버에서 추가 소비자로 띄우는 탈출구만 열어둔다.
