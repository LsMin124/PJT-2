SEC 00 · 한눈에

컨테이너 아홉, 프로토콜 다섯, 브로커 둘. 경계를 넘는 방법은 메시지뿐이다

이 시스템에는 함수 호출로 이어진 구간이 하나도 없다. 웹과 시뮬레이터가 같은 서버에 있어도 서로를 직접 부르지 않는다. 모든 경계는 큐 아니면 토픽이고, 그래서 각 조각을 따로 재시작·재배포·수평 확장할 수 있다. 대신 "이 메시지가 누구한테서 왔고 무슨 형식인가"를 모르면 어디도 읽을 수 없다. 이 문서가 그 표다.

HTTP · REST브라우저 → 백엔드. 요청 5종. 전부 JSON snake_case, 응답은 {isSuccess, code, message, result} 봉투
SSE백엔드 → 브라우저 단방향 푸시. 견적 3종 + 검증 2종. 같은 URL 을 Accept 로 가른다
AMQP · RabbitMQ웹 ↔ FMS 잡 큐 4개. durable · prefetch 1 · 발행 후 ack. 유실되면 안 되는 것
MQTT · Sparkplug B런 제어·텔레메트리. protobuf. 생사(NBIRTH/NDEATH) · 델타(NDATA) · 명령(NCMD)
MQTT · VDA 5050로봇 제어 표준. JSON. order 내려가고 state 올라온다
왜 이렇게 나눴나RabbitMQ 로 가는 메시지는 잃어버리면 사용자가 결과를 못 받는 것이라 durable 큐 + ack 로 보장한다. EMQX 로 가는 메시지는 초당 수십 건 쏟아지는 상태 보고라 하나쯤 놓쳐도 0.5초 뒤 또 온다 — QoS 0 로 가볍게 간다. 성격이 반대라 브로커를 합칠 수 없다.

SEC 02 · HTTP

브라우저 ↔ 백엔드 — 요청 5종의 전문

진입은 호스트 nginx :443 하나뿐이다. 프론트 컨테이너의 nginx 는 / 와 /assets/ 만 서빙하고 /api 프록시가 없다 — API 라우팅은 전적으로 호스트 nginx 몫이다. 개발 환경에서는 Vite 프록시가 /api → localhost:8080 으로 대신한다.

공통 규약

  • 요청·응답 모두 snake_case. 프론트는 수동 매핑, 백엔드는 @JsonNaming(SnakeCaseStrategy).
  • 응답은 항상 봉투에 담긴다: { isSuccess, code, message, result }. result 가 null 이면 키 자체가 생략된다.
  • 에러도 같은 봉투다. ResponseEntity 가 아니라 HttpServletResponse 에 직접 쓴다 — SSE 라우트에서 컨텐트 협상 실패를 피하기 위함.

SEC 03 · SSE

SEC 04 · AMQP

RabbitMQ 큐 4개 — 웹과 FMS 의 유일한 접점

큐 선언은 백엔드만 한다(4개 모두 durable). 워커와 host-orch 는 선언하지 않고 소비만 한다 — 브로커가 먼저 떠 있고 백엔드가 큐를 만들어 둔다는 전제다.

발행 방식

fms-core 는 견적과 완전히 같은 DES 커널을 쓰고, 실 로봇을 그 상태에 맞춘다. 커널이 진실이고 셸이 따라가는 구조다. 그래야 견적 KPI 와 검증 KPI 의 차이가 전부 "물리 때문"임이 보장된다.

if (서비스 처리됨) and (fleet.pending() 비었음) and (now - tick_started >= tick_s):
    cmds = planner.step(t)                       # DES 커널 한 스텝
    for cmd in cmds:

상황동작
order 발행pending = k+1, sent_at = now, states_since_send = 0
state 의 lastNodeId == "n{pending}"settle() → pending 해제

state 10건 지나도 미반영런 실패 — 로봇이 명령을 무시하고 있다
ack_timeout_s 30초 초과런 실패 — 재발행해도 이 타이머는 리셋되지 않는다
WAIT(제자리) 로봇Command 자체가 생략 → pending 이 안 생겨 기다리지 않는다

--tick-s 1.0 은 틱의 최소 벽시계 길이다(상한이 아니다). 로봇 도착이 늦으면 틱이 그만큼 늘어난다. 그래서 벽시계 600초 창이 DES 118틱밖에 안 되는 것이다.

host-orch 가 biz/v1/# 를 QoS 1 로 구독해 이 한 건을 받아, sim.verify.result 의 kpi 와 verify.fms 에 그대로 싣는다. KPI 가 웹으로 돌아오는 유일한 경로다.

SEC 07 · ACL

계정별 권한 행렬 — 누가 어디에 쓸 수 있나

공통 규칙

  • retained 는 세 곳에만 — connection · factsheet · spBv1.0/STATE/+. 그 외 토픽의 retained 발행은 어느 규칙에도 안 걸려 마지막 {deny, all} 로 떨어진다.

  • 규칙은 위에서 아래로 첫 일치, 마지막은 전부 거부.
  • deny_action = disconnect 는 구독 위반에도 적용된다.
  • 익명 접속 거부. 계정은 bootstrap_users.sh 로 주입하고, users.csv 는 컨테이너가 읽도록 644 여야 한다.

SEC 09 · 끊긴 곳

지금 메시지가 흐르지 않는 여섯 지점

1단계(견적)는 끝까지 흐른다. 2단계(물리 검증)는 아래 때문에 완주하지 못한다. 전부 통신 계약의 구멍이다 — 로직 버그가 아니라, 한쪽이 보내지 않거나 받는 쪽이 없는 문제다.

1 전원 → EMQX 모든 publish 가 거부된다. ACL 테스트 pub 28건 전부 실패, sub 전부 통과. 사실이면 SEC 05·06 구간 자체가 돌지 않는다 2026-09-10 실측
2 GPU → MinIO 영상을 올리는 쪽이 없다. artifacts 가 null 하드코딩. 녹화·업로드 코드가 GPU·host-orch 어디에도 없다. 받는 쪽(BE→FE)만 완성돼 04 섹션이 영원히 안 보인다 orchestrator.py:391
3 BE → host-orch scenario 를 안 보낸다. 6키만 실어서 fms-core 가 orders=[] 로 받는다 → 주문 0건짜리 검증 런 VerifyRequest.java:15-22
