SEC 02 · 수명주기

상시로 떠 있는 것과 런마다 생겼다 사라지는 것

이 구분이 장애 대응을 가른다. 상시 프로세스가 죽으면 서비스가 멈추고, 런 단위 프로세스가 죽으면 그 런만 실패한다.

수명무엇죽으면
상시 nginx · frontend · backend · db · rabbitmq · minio · emqx · 견적 워커 ×2 해당 기능 전체 정지. compose restart: unless-stopped
상시 host-orch 물리 검증 전체 정지. 두 브로커를 잇는 유일한 프로세스
상시 fms-core · sim-runner-gpu01 Sparkplug LWT 로 NDEATH 가 자동 발행 → host-orch 가 런을 실패 처리
런 단위 Isaac Sim · t4_agent ×N sim-runner 가 감지해 런 실패. 다음 Start 에서 새로 뜬다
일회성 DES 서브프로세스 (sim_v2_tasks.py) rc≠0 → 워커가 status:"failed" 로 정상 보고

런 하나의 상태 전이

host-orch (잡)     STARTING ──▶ RUNNING ──▶ STOPPING ──▶ 결과 발행 · ack
sim-runner         IDLE ─▶ STARTING ─▶ RUNNING ─▶ STOPPING ─▶ IDLE | ERROR
fms-core           IDLE ─▶ STARTING ─▶ RUNNING ─────────────▶ IDLE | ERROR
                                                   ↑ STOPPING 상태가 없다

검증 창은 sim-runner 와 fms-core 가 동시에 RUNNING 으로 관측된 tick에 시작한다. 하나만 떠 있는 시간은 측정에 넣지 않는다.

종료 사다리 — 순서가 정해져 있다

DDEATH ×N 발행           (로봇이 죽는다고 먼저 알림)
  → 에이전트 SIGINT
  → 5초 후 SIGTERM (프로세스 그룹)
  → 3초 후 SIGKILL
  → 에이전트가 전부 죽은 것을 확인한 뒤에야
      Isaac SIGINT → 20초 → SIGTERM → 3초 → SIGKILL

Isaac 을 먼저 죽이면 에이전트가 /odom 을 못 받아 에러를 뿜으며 남는다. 그래서 순서가 고정이다.

SEC 03 · 실행 흐름

트랙 둘이 각각 어떻게 도는가

메시지 형식은 TECH 05 통신 구조에 전문이 있다. 여기서는 무엇이 언제 일어나는가만 본다.

트랙 1 · 견적 (DES) — 사용자 버튼 1회

#주체동작비용
1프론트버튼 → POST /warehouses → POST /estimates 순차 2건즉시
2backend창고·견적·run 13행 저장 → 큐 13건 발행 → 202즉시
3워커 ×2한 건씩 소비 → 주문 500건 생성 → 출고창으로 매핑 → 잘라내기런당 ~1초
4DES서브프로세스 실행. 헤딩 PIBT · 충전 존 · 차선 · 양보 · 배터리 OFF런당 3~37초
5워커[SUMMARY] 한 줄 파싱 → KPI 14키 → 결과 큐즉시
6backendrun 갱신 → SSE run 이벤트 (13회)즉시
7backend13개 다 끝나면 판정 → SSE estimate.done즉시

전체 약 2분 (워커 2개 기준). 판정 규칙은 "처리율 ≥ 목표 and 가동률 ≥ 목표 and 비용 ≤ 예산"을 만족하는 최소 대수.

주의 — 조기 종료가 없다목표를 만족하는 대수를 이미 찾았어도 13런을 끝까지 돌린다. 배치 발행도 없다. 설계 문서가 "(설계 검토, 미구현)"으로 남아 있다.

#주체동작상한

틱 배리어 — 두 트랙을 잇는 장치

fms-core 는 견적과 완전히 같은 커널을 쓰고, 실 로봇을 그 상태에 맞춘다. 커널이 진실이고 셸이 따라간다.

if (fleet.pending() 비었음) and (now - tick_started >= tick_s):
    cmds = planner.step(t)                  # 커널 한 스텝
    for cmd in cmds: 로봇에 order 발행       # pending = k+1
    t += 1
                        ↑ 전 로봇이 lastNodeId 로 도착을 알릴 때까지 대기

--tick-s 1.0 은 최소 벽시계 길이다(상한이 아니다). 로봇이 늦으면 틱이 늘어난다. 그래서 벽시계 600초 창이 커널로는 118틱 정도밖에 안 된다 — 이 비율이 두 트랙을 잇는 환산 계수다.

왜 커널을 공유하나두 트랙이 다른 알고리즘을 쓰면, 결과 차이가 물리 때문인지 알고리즘 때문인지 분리할 수 없다. 커널을 하나로 두면 "결정은 같고 물리만 다르다"가 보장된다. 재동기화가 깨지지 않게 test_des_parity.py 가 기준을 견적 워커 코드 자체에서 읽어와 대조한다.

주문은 지금 PG에 없다워커가 요청을 받을 때마다 그 자리에서 500건을 생성한다. 시드가 고정(101)이라 결정론이지만, 프로파일 파일이 이미지에 있어 숨은 입력이 된다 — 이미지를 바꾸면 같은 시드인데 다른 주문이 나오고 아무 에러도 안 난다. 롤링 배포 중이면 같은 견적의 13런이 서로 다른 주문으로 갈릴 수도 있다. 그리고 검증 런은 주문을 넘겨받을 방법이 scenario.orders 뿐이라, 지금은 주문 0건으로 돈다.

MinIO — 비어 있다

컨테이너는 9002(S3 API, 9000은 SonarQube가 씀)로 떠 있고 백엔드에 verify_video_url 컬럼과 수신 코드도 있다. 그런데 올리는 쪽이 없다 — 녹화도 업로드도 GPU·host-orch 어디에도 코드가 없고 artifacts 는 null 하드코딩이다. 버킷·정책 설정도 없다.

EMQX 가 모든 publish 를 거부하고 있다

요청 파싱 실패 결과를 백엔드가 버린다

잘못된 요청에 대한 결과 JSON 에는 estimate_id 키 자체가 없다. 백엔드는 null 로 보고 조용히 폐기하므로 사용자는 실패했다는 사실조차 모른다.
