SEC 00 · 한눈에 보기

요청은 큐에 쌓이고, 런은 기동했다 사라진다

"창고·물류 조건을 받아 시뮬레이션으로 권장 대수·기종, KPI, 검증 영상을 담은 견적서를 만들어 보내는 요청 접수형 서비스." 셀프서브 SaaS가 아니다. 요청은 큐에 쌓이고, 운영자가 검토·검수하며, 결과는 나중에 발송된다.

  • ① 요청 하나가 견적서가 되기까지의 8단계와 사람이 개입하는 곳 — SEC 01
  • ② 웹 인프라 2층과 기기 2대에 무엇을 올리고, 어떻게 늘리는가 — SEC 02 · 03
  • ③ 잡과 런이 거치는 큐·계약·저장소, 런 하나의 관리 — SEC 04 ~ 07
  • ④ 실제로 무엇이 몇 개 떠서 어디서 도는가, GPU·EC2·네트워크 제약 — SEC 08

SEC 02 · 웹 인프라 2층

영속은 견적 도메인, 휘발은 시뮬 도메인

상시 가동하는 견적 서비스와, 런마다 기동·폐기하는 시뮬 스택을 층으로 나눈다(웹 인프라 2층). 런 하나의 상태가 영속 DB와 섞이지 않는다. EMQX만 두 층의 공용이다.

층구성수명저장소
상시 견적 서비스React 웹 콘솔 + nginx(:443 단일 인그레스), 견적 BE(Spring), PostgreSQL, RabbitMQ, MinIO, 견적 산출상시PostgreSQL(영속), MinIO(아티팩트)
런 단위 시뮬 스택시뮬 WMS(Spring + H2 인메모리), FMS 코어(Python), 수요 생성기런마다 기동·폐기H2(런과 함께 소멸)
공용EMQX(MQTT 브로커). 제어 채널이 런보다 먼저 있어야 한다상시없음
왜 시뮬 WMS 저장소가 H2인가 — 이유 3개 — 펼쳐 보기
이유내용
런 스코프시뮬 WMS의 주문·재고는 런 하나의 상태다. 런이 끝나면 함께 사라져야 한다. 인메모리 DB는 수명이 런과 같다
격리런 상태가 견적 PG에 섞이지 않는다. 영속이 필요한 것(KPI · 아티팩트 메타)만 결과 이벤트로 견적 PG에 들어간다. 작업 이벤트 로그는 H2 밖에 둔다(JSONL → MinIO)
인프라 여유EC2 1대에 전부 자체 호스팅한다. 런마다 DB 파드를 따로 띄우지 않고 시뮬 WMS 파드 안에서 끝낸다

H2 → 실물 PG 승격 경로와 두 DB의 방언이 무관한 이유는 SEC 06.

SEC 03 · 기기 배치와 확장

EC2 한 대와 GPU 서버 한 대, 관리형 서비스는 0

기관 제공 EC2에는 IAM(Identity and Access Management, AWS 권한 관리)이 없다. 관리형 AWS 서비스를 하나도 쓰지 못하므로 전부 k3s 위에 자체 호스팅한다. GPU 서버는 홈서버 1대다.

두 기기 사이 세 채널(MQTT 제어·상태 · presigned PUT · VDA 5050)은 전부 TCP라서 DERP 릴레이 경유에도 끊기지 않는다. ROS 2 DDS 트래픽은 GPU 서버 안에서만 돈다. 프로세스 전수와 채널별 정리는 SEC 08.

기기사양올라가는 것
EC2 t3.xlarge4 vCPU · 16 GB · IAM 불가 → 관리형 AWS 서비스 0, 전부 k3s 자체 호스팅상시 견적 서비스, 시뮬 스택 파드, 계산 엔진 Job, 런 오케스트레이터, EMQX. 이미지는 GHCR, 인증서는 certbot
GPU 서버 ×1RTX 5080 16 GB, 홈서버, Isaac Sim 6.0.1amr-agent(ROS 2) ×N, Isaac, sim-runner 데몬. 네이티브 실행
연결홈서버 → EC2 tailscale 아웃바운드. 캠퍼스 UDP 차단 시 DERP 릴레이

GHCR(GitHub Container Registry)은 컨테이너 이미지 저장소, certbot은 Let's Encrypt 인증서 자동 발급 도구, tailscale은 WireGuard 기반 사설망, DERP는 tailscale의 중계 서버다.

IAM 불가의 의미S3 대신 MinIO, 관리형 DB·큐 대신 PostgreSQL·RabbitMQ 파드. 외부 노출은 nginx :443 하나
계산은 EC2, 물리는 GPUDES 워커는 EC2 k3s Job이다. 견적 계산이 홈서버 가용성에 묶이지 않는다
GPU 1대 = N=1확장 표의 첫 칸이다. GPU 노드를 붙이면 GPU 런 큐 소비자가 하나 늘어난다

SEC 04 · 큐잉 2단

스윕 루프는 계산 엔진이, 런 직렬화는 GPU 런 큐가

큐는 두 개다. 요청 잡 큐는 CPU 워커가 수평 확장하고, GPU 런 큐는 GPU 수만큼만 소비자를 둔다. CPU 일과 GPU 일의 병목이 다르기 때문이다.

주황 상자가 스윕 루프를 소유하는 계산 엔진이고, 초록 점선이 결과가 견적 BE로 되돌아가는 경로다.

큐브로커소비자목적
요청 잡 큐RabbitMQCPU 워커 ×N스윕 잡. 우선순위 · DLQ · 재시도
GPU 런 큐RabbitMQGPU 수 = 소비자 수Isaac 검증 런 직렬화. 큐 순번 · ETA(예상 완료 시각) 회신의 근거. 운영자 콘솔에서 우선순위 조정
소유 원칙 스윕 루프와 정지 규칙(무릎 판정)은 계산 엔진이 소유한다. 견적 BE는 대수 n을 반복 호출하지 않고, 스윕 범위만 잡에 싣는다.

SEC 05 · 메시징·계약

프로토콜 4개, 각자 한 가지 일만 한다

REST는 고객·운영자 대면, AMQP는 잡·결과, MQTT는 제어·상태, DDS는 로봇 내부다. Kafka는 없다. 도메인 이벤트는 AMQP 결과 이벤트로 충분하다.

규약뜻브로커·구현
RESTRepresentational State Transfer. HTTP 요청·응답 API견적 BE(Spring), nginx :443
AMQPAdvanced Message Queuing Protocol. 잡 큐용 메시지 규약RabbitMQ
MQTTMessage Queuing Telemetry Transport. 가벼운 발행·구독 메시징EMQX
DDSData Distribution Service. ROS 2가 쓰는 실시간 발행·구독 미들웨어ROS 2 Humble (GPU 서버 안)

in-process계산 엔진 내부④ θ 추론 → 통행 비용 → FMS 결정 커널 step(world, now, events) → decisions. 하네스 셸이 가상 시계로 호출

VDA 5050은 독일 자동차산업협회의 AGV/AMR–관제 표준 인터페이스다. FMS 틱과 VDA 5050의 대응표는 WORKING · T3·T4 진행에 있다.

EMQX는 상시sim/control이 런보다 먼저 있어야 한다. 시뮬 스택은 런마다 새로 뜨지만 브로커는 남는다
커널 하나, 셸 둘DES는 하네스(가상 시계, 동기), 검증 런은 MQTT 데몬(틱 기반). 같은 step()을 부른다(실행 셸)
같은 θ, 같은 시나리오 패키지DES와 검증 런은 같은 θ와 같은 패키지를 쓴다. WMS 라이트와 시뮬 WMS는 한 패키지의 두 소비자다
SEC 06 · 데이터

PG는 견적, H2는 런, MinIO는 파일

저장소는 셋이다. 성격이 다르므로 섞지 않는다. 런이 끝나면 H2는 사라지고, 남겨야 할 것은 결과 이벤트로 PG에, 파일은 MinIO에 남긴다.

두 DB의 방언이 무관한 이유 — 펼쳐 보기
  • JPQL만 쓴다 — JPQL(Java Persistence Query Language)은 JPA 객체 질의어다. 시뮬 WMS는 네이티브 SQL 쿼리를 금지한다
  • PG 호환 모드 — H2를 PostgreSQL 호환 모드로 띄운다. 함수·타입 차이를 미리 줄인다
  • 프로파일 전환으로 승격 — Spring 프로파일만 바꾸면 H2 → 실물 PG로 승격된다. 코드 변경 없음
  • 참조 없음 — 견적 PG와 시뮬 H2는 조인하지 않는다. 방언이 달라도 서로 영향이 없다
SEC 07 · 런 오케스트레이터

런 하나는 상태 6개를 지나고, 어느 쪽으로 끝나든 파드는 지운다

EC2 k3s 위 단일 파드다. GPU 런 큐를 소비해 시뮬 스택을 띄우고, sim-runner에 시작·정지를 지시하고, 아티팩트 키를 모아 결과를 발행한다.

상자 위 회색 라벨이 각 상태에서 상대하는 인터페이스이고, 주황 점선이 실패 경로다.

형태 기준 — 왜 EC2는 파드이고 GPU 서버는 네이티브인가 — 펼쳐 보기
기기이유
EC2 = k3s 파드IAM이 없어 관리형 서비스를 못 쓴다. 전부 자체 호스팅이라 기동·폐기·재시작을 k3s에 맡기는 편이 낫다. 런 단위 파드는 k8s API로 만들고 지운다
GPU 서버 = 네이티브Isaac Sim은 GPU 드라이버와 직접 붙는다. ROS 2 DDS는 같은 호스트 안에서 공유메모리로 도는 편이 단순하다. 컨테이너화는 임대 GPU로 갈 때 한다(SEC 03 확장 표)

GPU 슬롯 — 5080 한 대 = 소비자 하나. 둘 띄우기는 실측 후에만

기본 규칙GPU 1대 = 소비자 1. Isaac은 호스트당 동시 1인스턴스. 런은 직렬
둘 띄우기 조건nvidia-smi로 이용률·VRAM을 런 중에 재서 둘 다 여유가 확인될 때만
MIG 없음RTX 5080은 소비자용이라 하드웨어 분할(MIG)이 없다. 시간 분할만 가능
기준확인 방법판단
GPU 이용률nvidia-smi utilization.gpu, 런 중 주기 샘플단일 런에서 이미 높으면 둘 띄워도 총 처리량은 늘지 않는다. 각 런만 느려진다
VRAMnvidia-smi memory.used / 16 GB단일 런 사용량의 2배가 16 GB를 넘으면 불가
호스트 RAM런 중 free, 커널 OOM 로그Isaac은 호스트 메모리도 많이 쓴다. 둘 띄우기의 첫 실패 지점은 보통 여기다
NVENCMP4 인코딩 동시 세션 수관전·영상 인코딩이 Isaac 렌더와 같은 GPU를 쓴다. 런 수만큼 인코더 부하도 는다
실측 런 여부런 목적 확인회전 시간 상수·정지 오차 같은 실측 런은 단독 실행. 다른 런과 겹치면 수치가 오염된다
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 5
운영 규칙둘 띄우기가 통과해도 GPU 런 큐 소비자는 여전히 1로 둔다. 두 번째 인스턴스는 개발·리허설용이다. 소비자를 2로 올리는 것은 GPU 노드를 추가할 때다(SEC 03).

EC2 제약 — t3.xlarge 한 대, IAM 없음, 크레딧은 기관 제공 형태에 달렸다

제약내용대응
크기4 vCPU · 16 GB. 상시 서비스, 런 파드, 계산 Job이 전부 여기서 돈다계산 Job에 CPU limit을 걸어 상시 서비스 몫을 보존한다. 런 파드는 런이 끝나면 지운다
IAM 불가관리형 AWS 서비스를 하나도 못 쓴다S3 → MinIO 파드 · RDS → PostgreSQL 파드 · ECR → GHCR · ACM → certbot. 전부 k3s 자체 호스팅
버스트 크레딧t 계열은 베이스라인 이상으로 CPU를 쓰면 크레딧을 소모한다(AWS 문서). 실제 인스턴스 타입과 크레딧 모드(standard / unlimited)는 기관 제공 형태에 따라 다르다인스턴스 안에서 IMDS로 타입을 확인하고, 크레딧 모드는 기관에 확인한다(기준선 §9). 고갈돼도 느려질 뿐 멈추지 않는다. 요청 접수형이라 허용된다

TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-type

IMDS(EC2 인스턴스 메타데이터 서비스)로 타입은 확인되지만 크레딧 모드는 IMDS에 없다. 콘솔 권한이 없으므로 기관 담당자에게 확인한다.

네트워크 — 홈서버가 EC2로 나가는 tailscale 한 줄. 캠퍼스가 UDP를 막으면 DERP로 돈다
