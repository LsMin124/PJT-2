요청은 큐에 쌓이고, 런은 기동했다 사라진다

"창고·물류 조건을 받아 시뮬레이션으로 권장 대수·기종, KPI, 검증 영상을 담은 견적서를 만들어 보내는 요청 접수형 서비스." 셀프서브 SaaS가 아니다. 요청은 큐에 쌓이고, 운영자가 검토·검수하며, 결과는 나중에 발송된다.

SEC 01 · 서비스 흐름 8단계

접수와 발송 사이는 전부 내부 배치다

요청 하나는 8단계를 지난다. 운영자는 ② 검토와 ⑦ 검수 두 곳에만 개입한다.

단계이름주체인터페이스무엇을
①견적 요청 접수고객 → 견적 BEREST /api/requests창고·물류 조건 입력. 큐 순번·예상 소요 회신
②운영 검토·시나리오 컴파일 운영자운영자웹 콘솔요청을 정제해 시나리오 패키지(zones.json · 맵 · 분해 규칙 · 수요)로 컴파일
③스윕 잡 소비RabbitMQ → 계산 엔진 워커AMQP, 우선순위 큐, DLQ잡 = 시나리오 패키지 + 스윕 범위. 워커는 수평 확장
④구성 탐색·θ 추론·DES계산 엔진(EC2 k3s Job)in-processtrial마다 AI 모델이 θ 11개 추론 → 통행 비용 → FMS 커널로 가상 시간 실행 × 시드 반복
⑤Isaac 물리 검증 런런 오케스트레이터 → 시뮬 스택 + GPUk8s API, MQTT sim/control상위 구성만 GPU 런 큐에 적재. 시뮬 WMS·FMS 파드 기동, Isaac·에이전트 스폰
⑥KPI 집계·아티팩트sim-runner → MinIO, 워커 → BES3 API presigned PUT, AMQP 결과 이벤트배속 영상(MP4) · 리플레이(JSON) · 히트맵(PNG). PG에 KPI·아티팩트 메타
⑦리포트 작성 운영자LLM 초안 + 운영자 검수웹 콘솔권장 구성 · 곡선 · 영상 임베드
⑧견적서 발송견적 BE이메일 · 다운로드발송 후 요청 종료

KPI(Key Performance Indicator)는 처리량 같은 핵심 성과 지표다. AMQP·MQTT·DLQ 같은 계약 이름은 SEC 05에서 풀어 쓴다.

운영자 개입 2곳② 검토·컴파일, ⑦ 리포트 검수. 나머지는 사람 없이 돈다
①~⑧ 사이 = 내부 배치고객은 접수 시 큐 순번과 예상 소요만 받는다. 결과는 발송으로 돌아온다
산출물 = 견적의 증거영상 · 리플레이 · 히트맵이 견적서에 들어간다. 그래서 ⑤ 물리 검증 런이 파이프라인 안에 있다
쉽게 말하면 고객은 조건을 내고 순번표를 받는다. 시스템이 계산과 물리 검증을 마치면, 운영자가 리포트를 확인하고 보낸다.
SEC 02 · 웹 인프라 2층

영속은 견적 도메인, 휘발은 시뮬 도메인

상시 가동하는 견적 서비스와, 런마다 기동·폐기하는 시뮬 스택을 층으로 나눈다. 런 하나의 상태가 영속 DB와 섞이지 않는다.

층구성수명저장소
상시 견적 서비스React 웹 콘솔 + nginx(:443 단일 인그레스), 견적 BE(Spring), PostgreSQL, RabbitMQ, MinIO, 견적 산출상시PostgreSQL(영속), MinIO(아티팩트)
런 단위 시뮬 스택시뮬 WMS(Spring + H2 인메모리), FMS 코어(Python), 수요 생성기런마다 기동·폐기H2(런과 함께 소멸)
공용EMQX(MQTT 브로커)상시없음

MinIO는 S3 호환 오브젝트 저장소, H2는 자바 인메모리 DB, EMQX는 MQTT 브로커다. 셋 다 EC2 안의 k3s 파드로 돈다.

원칙 영속은 견적 도메인, 휘발은 시뮬 도메인. 견적 서비스는 고객·운영자를 대면하고, 시뮬 스택은 내부 엔진이다. EMQX만 두 층의 공용이다. 제어 채널이 런보다 먼저 있어야 하므로 상시 가동한다.
왜 시뮬 WMS 저장소가 H2인가 — 이유 3개 — 펼쳐 보기
이유내용
런 스코프시뮬 WMS의 주문·재고는 런 하나의 상태다. 런이 끝나면 함께 사라져야 한다. 인메모리 DB는 수명이 런과 같다
격리런 상태가 견적 PG에 섞이지 않는다. 영속이 필요한 것(KPI · 아티팩트 메타)만 결과 이벤트로 견적 PG에 들어간다. 작업 이벤트 로그는 H2 밖에 둔다(JSONL → MinIO)
인프라 여유EC2 1대에 전부 자체 호스팅한다. 런마다 DB 파드를 따로 띄우지 않고 시뮬 WMS 파드 안에서 끝낸다

H2를 실물 PG로 승격하는 경로와 두 DB의 방언이 무관한 이유는 SEC 06에 있다.

SEC 03 · 기기 배치

EC2 한 대와 GPU 서버 한 대, 관리형 서비스는 0

기관 제공 EC2에는 IAM(Identity and Access Management, AWS 권한 관리)이 없다. 관리형 AWS 서비스를 하나도 쓰지 못하므로 전부 k3s 위에 자체 호스팅한다. GPU 서버는 홈서버 1대다.

기기사양올라가는 것
EC2 t3.xlarge4 vCPU · 16 GB · IAM 불가 → 관리형 AWS 서비스 0, 전부 k3s 자체 호스팅상시 견적 서비스, 시뮬 스택 파드, 계산 엔진 Job, 런 오케스트레이터, EMQX. 이미지는 GHCR, 인증서는 certbot
GPU 서버 ×1RTX 5080 16 GB, 홈서버, Isaac Sim 6.0.1amr-agent(ROS 2) ×N, Isaac, sim-runner 데몬. 네이티브 실행
연결홈서버 → EC2 tailscale 아웃바운드. 캠퍼스 UDP 차단 시 DERP 릴레이

GHCR(GitHub Container Registry)은 컨테이너 이미지 저장소, certbot은 Let's Encrypt 인증서 자동 발급 도구, tailscale은 WireGuard 기반 사설망, DERP는 tailscale의 중계 서버다.

IAM 불가의 의미S3 대신 MinIO, 관리형 DB·큐 대신 PostgreSQL·RabbitMQ 파드. 외부 노출은 nginx :443 하나
계산은 EC2, 물리는 GPUDES 워커는 EC2 k3s Job이다. 견적 계산이 홈서버 가용성에 묶이지 않는다

SEC 04 · 큐잉 2단

스윕 루프는 계산 엔진이, 런 직렬화는 GPU 런 큐가

큐는 두 개다. 요청 잡 큐는 CPU 워커가 수평 확장하고, GPU 런 큐는 GPU 수만큼만 소비자를 둔다.

주황 상자가 스윕 루프를 소유하는 계산 엔진이고, 초록 점선이 결과가 견적 BE로 되돌아가는 경로다.

큐브로커소비자목적
요청 잡 큐RabbitMQCPU 워커 ×N스윕 잡. 우선순위 · DLQ · 재시도
GPU 런 큐RabbitMQGPU 수 = 소비자 수Isaac 검증 런 직렬화. 큐 순번 · ETA 회신의 근거

DLQ(Dead Letter Queue)는 처리에 실패한 메시지를 따로 모으는 큐다. ETA(Estimated Time of Arrival)는 예상 완료 시각이다. GPU가 병목이므로 접수 시 큐 깊이로 순번·ETA를 회신하고, 운영자 콘솔에서 우선순위를 조정한다.

소유 원칙 스윕 루프와 정지 규칙(무릎 판정)은 계산 엔진이 소유한다. 견적 BE는 대수 n을 반복 호출하지 않고, 스윕 범위만 잡에 싣는다.

SEC 05 · 메시징·계약

프로토콜 4개, 각자 한 가지 일만 한다

REST는 고객·운영자 대면, AMQP는 잡·결과, MQTT는 제어·상태, DDS는 로봇 내부다. Kafka는 없다. 도메인 이벤트는 AMQP 결과 이벤트로 충분하다.

규약뜻브로커·구현

AMQPAdvanced Message Queuing Protocol. 잡 큐용 메시지 규약RabbitMQ
MQTTMessage Queuing Telemetry Transport. 가벼운 발행·구독 메시징EMQX
DDSData Distribution Service. ROS 2가 쓰는 실시간 발행·구독 미들웨어ROS 2 Humble (GPU 서버 안)

SEC 06 · 데이터

PG는 견적, H2는 런, MinIO는 파일

저장소는 셋이다. 성격이 다르므로 섞지 않는다.

저장소테이블 · 파일성격
PostgreSQL(견적)customer, quote_request, amr_model, scenario, sweep_job, trial, verify_run, kpi_result, artifact, quote_report, operator, review_log, event_log영속 계층 request 1:N job 1:N trial 1:0..1 verify_run
H2(시뮬 WMS)run_context, zone, location, station, sku, inventory, order, order_line, task런 스코프 작업 이벤트 로그는 H2 밖(JSONL → MinIO)
MinIO시나리오 파일, MP4 · 리플레이 · 히트맵 · 로그영속 파일
재현성 키시나리오 해시 + 시드. 같은 키면 같은 결과가 나와야 한다
두 DB는 서로 모른다견적 PG와 시뮬 H2는 참조 관계가 없다. 연결 고리는 AMQP 결과 이벤트와 MinIO 키뿐이다
아티팩트는 파일로영상·리플레이·히트맵은 MinIO에 두고, PG에는 메타(키·크기·런 ID)만 적는다
원칙 영속은 견적, 휘발은 시뮬. 런이 끝나면 H2는 사라진다. 남겨야 할 것은 결과 이벤트로 PG에, 파일은 MinIO에 남긴다.
두 DB의 방언이 무관한 이유 — 펼쳐 보기
  • JPQL만 쓴다 — JPQL(Java Persistence Query Language)은 JPA 객체 질의어다. 시뮬 WMS는 네이티브 SQL 쿼리를 금지한다
  • PG 호환 모드 — H2를 PostgreSQL 호환 모드로 띄운다. 함수·타입 차이를 미리 줄인다
  • 프로파일 전환으로 승격 — Spring 프로파일만 바꾸면 H2 → 실물 PG로 승격된다. 코드 변경 없음
  • 참조 없음 — 견적 PG와 시뮬 H2는 조인하지 않는다. 방언이 달라도 서로 영향이 없다
SEC 07 · 런 오케스트레이터

런 하나는 상태 6개를 지나고, 어느 쪽으로 끝나든 파드는 지운다

EC2 k3s 위 단일 파드다. GPU 런 큐를 소비해 시뮬 스택을 띄우고, sim-runner에 시작·정지를 지시하고, 아티팩트 키를 모아 결과를 발행한다.

상자 위 회색 라벨이 각 상태에서 상대하는 인터페이스이고, 주황 점선이 실패 경로다.
