SEC 00 · 한눈에 보기

요청이 들어와, 견적서가 되어 나간다

"3PL(Third-Party Logistics, 제3자 물류)이 AMR(Autonomous Mobile Robot, 자율이동로봇) 도입을 결정할 수 있도록, 창고·물류 조건을 받아 시뮬레이션으로 권장 대수·기종, KPI, 검증 영상을 담은 견적서를 만들어 보내는 요청 접수형 서비스." — 제품 한 줄 정의

기준선 개정 (2026-09-03)기준선 v3에 맞춰 전면 개정. 셀프서브 SaaS를 기각하고 요청 접수형 비동기 서비스로 확정. 서비스 흐름은 8단계, 웹 인프라는 2층으로 분리, 경로계획은 PIBT 헤딩 모델 + AI 통행 규칙 θ의 2-트랙. 시뮬레이션 트랙은 T3 완료, T4 뼈대 완료. 상세 다이어그램은 TECH 02 시스템 아키텍처, 원본은 FMS-WMS 통합 아키텍처 v3.10.

SEC 01 · 제품 정의

셀프서브가 아니라 요청 접수형이다

요청은 큐에 쌓이고, 운영자가 검토·검수하며, 결과는 나중에 발송됩니다. 고객이 직접 시뮬레이션을 돌리는 제품이 아닙니다.

무엇을권장 대수·기종, KPI(핵심 성과 지표), 검증 영상을 담은 견적서
누구에게AMR 도입을 검토하는 3PL. 창고·물류 조건을 제출할 수 있는 사업자
어떤 형태로요청 접수형 비동기 서비스. 접수 시 큐 순번·예상 소요를 회신하고, 견적서는 이메일·다운로드로 발송
쉽게 말하면 창고 회사가 "이 창고에 로봇 몇 대가 맞나"를 물으면, 본 프로젝트가 그 창고를 시뮬레이션으로 돌려 보고 답을 문서로 보내 줍니다. 계산은 자동이지만, 입력 정리와 결과 검수는 사람이 합니다.

SEC 02 · 시스템 지도

영속은 견적 도메인, 휘발은 시뮬 도메인

기기 두 대에 웹 2층 + 계산 엔진 + GPU 실행 계층이 올라갑니다. 상시 층은 요청과 결과를 보관하고, 런 단위 층은 검증 런마다 기동·폐기됩니다.

파랑 실선 = EC2, 초록 실선 = GPU 서버, 주황 점선 = 런마다 기동·폐기되는 시뮬 도메인. 주황 화살표가 FMS 코어에서 EMQX를 거쳐 로봇 에이전트로 가는 VDA 5050 제어 경로입니다. 컴포넌트별 포트·토픽·상태 전이는 TECH 02 시스템 아키텍처, 원본 다이어그램은 FMS-WMS 통합 아키텍처 v3.10.

SEC 03 · FMS

결정 커널 하나를 DES와 Isaac이 공유한다

FMS는 ROS에 참여하지 않는 순수 Python입니다. 결정 커널 1개에 실행 셸 2종을 씌워 DES(④)와 Isaac 검증 런(⑤)이 같은 판단 로직으로 돕니다. 이 절은 인터페이스 수준만 다룹니다.

  • 미확정 — 회전 시간 상수는 Isaac 실측으로 확정해야 한다(SEC 06)
  • 미션 범위 — 입고(인바운드 버퍼 → 통로 입구 버퍼) + 출고(통로 입구 버퍼 → 패킹 직행). 멀티라인 주문은 같은 통로 라인 묶음이 토트 1개
  • 후속 — 배터리·적재 용량·피커 작업 시간 모델은 서빙 준비 단계 로드맵. SIL은 주행·혼잡 + 리프트 도킹 1장면

PIBT가 왜 대수–처리량 곡선을 꺾는지는 TECH 04 경로계획 이론 기반, 결정 항목 전수 목록은 TECH 05 구현 결정 인벤토리.

SEC 04 · 시뮬레이션 트랙

T3까지 완료, T4는 뼈대가 섰다

시뮬 파트의 SIL 트랙은 네 태스크입니다. 창고 씬과 자기위치까지 끝났고, FMS 틱을 VDA 5050으로 받는 에이전트는 Isaac 없이 E2E를 통과했습니다.

태스크상태한 줄
T1 텔레옵완료Isaac × ROS 2 브리지. 가감속 실측: 최고 0.835 m/s, 응답 즉답형(램프는 컨트롤러가 모델링)
T2 매핑·추종완료slam_toolbox 매핑(오차 평균 3.4 cm). 자체 추종기 20엣지 완주
T3 창고 씬완료도면 DXF → 그리드 → USD 씬(랙·화물·스테이션 46·충전 6). 물리 라이다 720빔 0.5° 0.4~20 m. nav2 AMCL 자기위치. Foxglove·MJPEG 관전
T4 에이전트뼈대 완료VDA 5050 브리지 + order executor + 그리드 프리미티브 컨트롤러(스팟턴·직진·후진) + fake robot/FMS. Isaac 없이 배리어 틱 E2E 통과

FMS 파트가 넘긴 Isaac 실행 요구 5건 중 스팟턴·경유점 오차·후진은 T4에서 구현됐고, 배리어 방식과 iw.hub 실측 2건은 확인 중입니다(SEC 06). 틱 매핑 표·실측 시간·다음 작업은 WORKING · T3 창고 씬 · T4 에이전트 진행.

SEC 05 · 큐잉·확장

GPU 추가는 큐 소비자 추가다

요청은 즉시 처리되지 않습니다. 큐에 쌓이고, 소비자 수만큼 순서대로 빠집니다. 큐가 두 단인 이유는 CPU 일과 GPU 일의 병목이 다르기 때문입니다.

위 줄이 CPU 스윕, 아래 줄이 GPU 검증입니다. 회색 점선 상자가 확장 경로입니다. 5080 1대는 그 그림의 N=1입니다.

큐브로커소비자목적
요청 잡 큐RabbitMQCPU 워커 ×N스윕 잡. 우선순위·DLQ·재시도
GPU 런 큐RabbitMQGPU 수 = 소비자 수Isaac 검증 런 직렬화. 큐 순번·ETA(예상 완료 시각) 회신의 근거

왜 큐인가

  • GPU 1대 — Isaac 검증 런은 실시간이라 동시에 여러 개를 돌릴 수 없다. GPU 런 큐가 직렬화한다
  • 순번·예상 소요 — ① 접수 시 회신하는 큐 순번과 ETA는 큐 깊이에서 나온다
  • 실패 처리 — 우선순위·재시도·DLQ. 런 ID 기준 멱등이라 재기동해도 같은 런을 두 번 돌리지 않는다
  • 스윕은 엔진 소유 — 스윕 루프와 정지 규칙(무릎 판정)은 계산 엔진이 갖는다. 견적 BE는 대수 n을 반복 호출하지 않고 스윕 범위만 잡에 싣는다. 팀 백엔드↔AI API 초안의 요청·응답 스키마(run_id·seed·warehouse·amr·orders → kpi)는 trial 단위 어댑터 계약으로 채택

확장 경로

  • GPU 노드 추가 = GPU 런 큐 소비자 추가 — 코드 변경 없이 소비자 프로세스만 늘린다
  • 임대 GPU(L40S 등) — Isaac을 컨테이너 Job으로 바꾸고, 시뮬 스택 파드를 GPU 노드로 옮기고, 큐 깊이 기반 오토스케일을 붙인다
  • CPU 워커 — 계산 엔진 Job은 이미 수평 확장. EC2 4 vCPU가 현재 상한
