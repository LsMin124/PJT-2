SEC 00 · 얻는 것

키 입력 하나가 가상 로봇을 움직이기까지의 전체 사슬

T1은 "텔레옵 데모"가 아니라 브리지 개통 공사다. 키보드 노드(ROS2) → DDS → Isaac 브리지 → 차동구동 물리 → 다시 DDS로 나오는 /odom까지, 이후 모든 태스크(T2~T4)가 딛고 설 파이프라인을 뚫고 검증했다. 이 가이드를 끝내면 아래 다섯 가지를 스스로 할 수 있어야 한다.

#학습 목표관련 절
1ROS2 토픽 그래프에서 Isaac이 "한 참여자"임을 설명하고 토픽 방향을 그릴 수 있다SEC 01·02
2Twist(v, ω)가 좌·우 바퀴 속도로 바뀌는 식을 손으로 계산할 수 있다SEC 01
3teleop_sim.py의 각 블록이 왜 그 순서로 놓였는지 말할 수 있다SEC 03
4시뮬을 기동해 토픽을 검증하고 키보드로 조종할 수 있다SEC 04
5가감속 실측이 왜 "명령 램프 모델링" 결론으로 이어졌는지 설명할 수 있다SEC 05

코드 위치: 저장소 sil/t1_teleop/ · 팀 레포 2_Simulation/t1_teleop/ (동일본)

SEC 01 · 선수 개념 5

이 다섯 개만 알면 코드가 전부 읽힌다

개념핵심T1에서 쓰인 곳
① 노드·토픽·DDSROS2에는 중앙 서버(roscore)가 없다. 프로세스들이 DDS 버스로 서로를 자동 발견하고, 이름 붙은 채널(토픽)에 발행/구독한다. 같은 호스트에선 공유메모리로 오간다teleop 노드와 Isaac이 서로의 존재를 모른 채 /cmd_vel로만 대화
② 시뮬레이션 시간시뮬 세계의 시계는 벽시계와 다르다. Isaac이 /clock으로 시뮬 시간을 발행하고, 다른 노드는 use_sim_time으로 그 시계를 쓴다. 시뮬이 실제보다 빠르거나(RTF>1) 느려도 시뮬 시간 기준 측정은 왜곡되지 않는다가감속 실측이 RTF와 무관하게 유효한 이유
③ 차동구동 기구학Twist의 선속 v·각속 ω가 바퀴 각속도로 변환된다: ωL=(v−ω·b/2)/r, ωR=(v+ω·b/2)/r. iw.hub은 r=0.115m, b=0.413m — v=0.6, ω=0이면 양쪽 5.22 rad/sDifferentialController.forward()가 하는 일 전부
④ OmniGraphIsaac 내부의 노드 배선 시스템. "매 프레임 틱" 노드가 실행 신호를 흘리고, 연결된 노드(ROS 구독·발행 등)가 순서대로 계산한다. 파이썬으로 그래프를 코드로 조립할 수 있다ROS2 I/O 전체 — SubscribeTwist·PublishClock·PublishOdometry
⑤ 쿼터니언 컨벤션회전을 4개 숫자로 표현하는데, 순서가 진영마다 다르다. Isaac 실험 API는 (w,x,y,z), ROS는 (x,y,z,w). 변환 없이 넘기면 회전이 뒤틀린다odom orientation 채울 때 재배열 1줄
한 가지 함정 지식Isaac 내장 파이썬은 3.12, Humble의 rclpy는 3.10용 바이너리다 — 그래서 Isaac 안에서 rclpy를 import할 수 없다. Isaac의 ROS 통신은 전부 C++ 레벨 브리지(OmniGraph 노드)가 담당하고, rclpy 코드는 항상 Isaac 밖(시스템 파이썬)에서 돈다. 기동 로그의 "Could not import rclpy" 경고가 무해한 이유다.

용어가 낯설면 용어사전 A(로보틱스)부터.

SEC 02 · 아키텍처

프로세스 두 개, 토픽 세 개 — 그리고 하이브리드 설계

왜 하이브리드인가 — ROS I/O는 OmniGraph, 구동은 파이썬

선택이유
ROS 통신 = OmniGraph 노드Isaac 안에서 rclpy가 불가하므로(SEC 01 함정 지식) C++ 브리지 노드가 유일한 정식 경로. 구독 노드는 "마지막 수신값"을 출력 핀에 유지한다
구동 = 파이썬 직접 호출WheeledRobot + DifferentialController는 08-24 창고 데모에서 이미 실증된 경로 — 검증된 것을 재사용하고 새 위험(그래프 배선 오류)을 통신부에만 한정
odom = 파이썬이 채워서 노드가 발행6.0에는 오도메트리 계산 노드가 없어, 매 프레임 로봇 pose·속도를 읽어 발행 노드의 입력 핀에 써 넣는다
SEC 03 · 코드 워크스루

teleop_sim.py — 블록 순서에 전부 이유가 있다

순서블록왜 이 자리인가
1SimulationApp(CONFIG)가장 먼저. 이게 kit 런타임을 띄우기 전에는 isaacsim.* 모듈 import가 실패한다 — Isaac standalone의 제1규칙
2확장 활성화 (livestream, ros2.bridge)브리지 확장이 켜져야 OmniGraph에 ROS2 노드 타입이 등록된다. 그래프를 만들기 전에 활성화
3씬 구성 (Grid env + iw.hub + 컨트롤러)Z-up·미터 단위 명시 후 클라우드 USD 레퍼런스. 로봇은 조인트명 2개(left/right_wheel_joint)로 바퀴를 지정
4SimulationManager.setup_simulation물리 씬 생성(dt=1/60, CPU). 로봇이 스테이지에 있어야 물리에 등록된다
5OmniGraph 조립 (og.Controller.edit)노드 생성 → 값 설정 → 연결의 3단. 틱 노드의 실행 신호를 구독·발행 노드 전부에 배선
6메인 루프simulation_app.update()가 물리 1스텝+그래프 1틱. 그 직후 파이썬이 명령을 읽고 구동하고 odom을 채운다

그래프 조립 핵심 — 노드 5개와 배선 규칙

og.Controller.edit({"graph_path": "/World/ros2_graph", "evaluator_name": "execution"}, {
    CREATE_NODES: [tick(OnPlaybackTick), ctx(ROS2Context),
                   sub_twist(ROS2SubscribeTwist), pub_clock, pub_odom],
    SET_VALUES:   [topicName·frameId 등 정적 설정],
    CONNECT:      [tick.outputs:tick → 각 노드.inputs:execIn,   # 실행 신호
                   ctx.outputs:context → 각 노드.inputs:context], # ROS 컨텍스트
})

배선은 두 종류뿐이다 — 실행 신호(매 틱 "일해라")와 컨텍스트(어느 ROS 도메인에 속하나). 데이터 값(타임스탬프·pose)은 연결 대신 파이썬이 매 프레임 입력 핀에 직접 써 넣는다.

메인 루프 — 다섯 줄로 요약되는 제어 사슬

lin = og.Controller.get(twist_lin)            # ① 구독 노드의 마지막 Twist
v, w = clip(lin[0]), clip(ang[2])             # ② 안전 클램프 (1.2 m/s · 1.5 rad/s)
robot.apply_wheel_actions(controller.forward([v, w]))  # ③ 기구학 → 바퀴 속도
p, q = robot.get_world_poses()                # ④ 물리 결과 pose 읽기
og.Controller.set(odom_ori, [q1,q2,q3,q0])   # ⑤ wxyz → xyzw 재배열 후 발행 핀에
추적 카메라 한 스푼카메라는 매 프레임 현재값 += α·(목표값 − 현재값)의 지수 평활(lerp, α=0.06)로 로봇을 따라간다. N프레임마다 순간이동시키면 화면이 뚝뚝 끊긴다 — 처음엔 그렇게 만들었다 고쳤다(SEC 06 ②).

measure_accel.py는 반대편 관점의 최소 rclpy 노드다: /odom 구독 → (t, x, y, speed) 누적 → CSV + 최고 속도·상승 시간 요약. 시스템 파이썬에서 돌며, 타임스탬프가 시뮬 시간이라 RTF 무관.

SEC 05 · 검증·실측

무엇을 쟀고, 왜 그 숫자가 중요한가

검증 항목실측 (2026-08-27)
토픽 주기/clock 185Hz · /odom 200Hz — 벽시계 기준이라 RTF에 따라 변동(정상)
직진 정확도0.8 m/s 명령 → 5.37m 주행, 횡편차 9mm

정지제로 Twist 1발로 정지

가감속 스텝 응답 — T1의 진짜 수확

항목실측해석
최고 속도0.835 m/s (1.2 명령에도)에셋 휠 조인트 한계 추정(휠 7.27 rad/s) — 공식 스펙과의 괴리 자체가 보정 루프의 첫 의제
가속 0→95%0.13초 (~6.0 m/s²)물리 응답이 즉답형 — 조인트 드라이브가 목표 속도로 사실상 즉시 점프. 실제 iw.hub의 완만한 가감속(≤1 m/s² 급)은 물리가 아니라 명령 램프(컨트롤러 수준 가속 제한)로 모델링해야 한다
감속 →00.12초 (~5.7 m/s²)
DES와의 연결이 결론이 견적 엔진에 주는 지침: DES의 가감속 파라미터는 "물리에서 측정하는 값"이 아니라 "우리가 설정하는 램프 값"이다. 그래서 T2 추종기부터 가속 램프가 필수 사양이 됐다 — 시뮬 트랙의 실측 하나가 DES 모델 구조를 정한 첫 사례.

측정 방법론: 스텝 명령(0→최대) 인가 + /odom의 시뮬 시간 스탬프 기준 속도 곡선 기록. RTF가 몇 배든 시뮬 시간 축에서는 같은 곡선이 나온다(SEC 01 ②).

SEC 06 · 삽질 사전

우리가 밟은 것들 — 증상·원인·해법

#증상원인해법·교훈
①스트리밍 접속 불가, 로그에 NVST_R_BUSY 연발시뮬 이중 기동 — 두 StreamSDK가 포트 49100 경합. 발단은 pgrep -x kit이 python.sh 실행(프로세스명 python3)을 못 잡아 "죽었다" 오판기동 전 pgrep -f teleop_sim.py. NVST_R_BUSY = 이중 기동 신호로 기억
②WebRTC는 붙는데 화면에 그리드만 보임렌더링 문제가 아니라 로봇이 카메라 프레임 밖 — 측정 주행으로 15m 이탈, 고정 카메라는 원점만 응시추적 카메라(지수 평활). "안 보인다 ≠ 안 그려진다" — /odom으로 위치부터 확인
③가감속 측정치가 뒤죽박죽(시간축 섞임)이중 기동 상태에서 두 시뮬의 /odom이 한 토픽에 섞임 — 클록 2개가 교차측정 전 인스턴스 개수 확인. CSV 시간축 단조성 검사를 분석에 포함
④기동 로그에 rclpy import 경고Isaac 파이썬 3.12 vs Humble rclpy 3.10 바이너리무해 — 브리지는 C++ 레벨(SEC 01 함정 지식)
⑤클라이언트 미접속인데 StreamSdk Fatal 로그세션 대기 중 상태 전이 소음무해 — 앱은 정상 지속
⑥(예고) 센서를 달았는데 로봇을 안 따라감articulation 루트 Xform에 부착 — 물리는 링크만 움직인다센서는 반드시 움직이는 링크(체시스 강체) 하위에. T2에서 실제로 밟고 해결한 건 — 상세는 T2 가이드에서
SIL 구현 로드맵T1의 위치와 다음 단계(T2 매핑·자율 추종)
