SEC 00 · 한눈에 보기

기기는 둘, 상시 프로세스는 EC2에 8개, 런마다 양쪽에서 N개가 뜬다

"EC2 한 대가 상시 견적 서비스를, GPU 서버 한 대가 물리 검증 런을 맡는다." 이 문서는 그 두 기기 위에서 실제로 무엇이 도는지만 다룬다.

기준선 개정 (2026-09-03)REV D는 기준선 v3 §3.2 기기 배치와 §3.3 큐잉을 따른다. 이전 REV C의 "시뮬 섬·서비스 섬" 구분, Nav2 설명, Kafka·Mosquitto, 외부 GPU 시세 표는 v2 잔재라 삭제했다. 구조와 흐름은 TECH 02 시스템 아키텍처가 단일 소스다. 이 문서는 운영 관점만 쓴다.

이 문서가 답하는 질문

  • ① 프로세스가 몇 개이고, 어느 기기에서, 상시인지 런마다인지, 파드인지 네이티브인지 · SEC 01
  • ② GPU 한 대에 Isaac을 둘 띄워도 되는가, 무엇을 보고 판단하는가 · SEC 02
  • ③ EC2와 네트워크의 제약(IAM 불가, 버스트 크레딧, 캠퍼스 UDP 차단)을 어떻게 다루고, 어디까지 늘릴 수 있는가 · SEC 03 · 04 · 05

SEC 01 · 프로세스 전수

EC2는 파드 11종, GPU 서버는 네이티브 5종. 무거운 것은 Isaac과 시뮬 WMS 둘뿐이다

전수 표다. 메모리는 수치 대신 관심도로 적는다. 실측 수치는 확보되는 대로 T3·T4 진행에 기록한다.

관심도: 높음 = 이 프로세스가 기기 메모리를 결정한다 · 중 = 설정값에 따라 달라진다 · 낮음 = 합산해도 작다.

쉽게 말하면 EC2에는 늘 켜져 있는 것 8개가 있고, 견적 요청이 들어오면 계산 Job이, 검증 런이 시작되면 시뮬 파드 3개가 잠깐 더 뜬다. GPU 서버에는 sim-runner 하나만 늘 켜져 있고, 런이 오면 Isaac과 로봇 수만큼의 에이전트가 떴다가 사라진다.
형태 기준 — 왜 EC2는 파드이고 GPU 서버는 네이티브인가 — 상세
기기이유
EC2 = k3s 파드IAM이 없어 관리형 서비스를 못 쓴다. 전부 자체 호스팅이라 기동·폐기·재시작을 k3s에 맡기는 편이 낫다. 런 단위 파드는 k8s API로 만들고 지운다
GPU 서버 = 네이티브Isaac Sim은 GPU 드라이버와 직접 붙는다. ROS 2 DDS는 같은 호스트 안에서 공유메모리로 도는 편이 단순하다. 컨테이너화는 임대 GPU로 갈 때 한다(SEC 05)
SEC 02 · GPU 슬롯

5080 한 대 = GPU 런 큐 소비자 하나. 둘 띄우기는 실측 후에만

GPU 수가 곧 동시 런 수다. 현재는 1이다. 한 GPU에 Isaac을 둘 띄우는 것은 "가능한가"가 아니라 "재 보고 결정한다"의 문제다.

기본 규칙GPU 1대 = 소비자 1. Isaac은 호스트당 동시 1인스턴스. 런은 직렬
둘 띄우기 조건nvidia-smi로 이용률·VRAM을 런 중에 재서 둘 다 여유가 확인될 때만
MIG 없음RTX 5080은 소비자용이라 하드웨어 분할(MIG)이 없다. 시간 분할만 가능

둘 띄우기 판단 기준

기준확인 방법판단
GPU 이용률nvidia-smi utilization.gpu, 런 중 주기 샘플단일 런에서 이미 높으면 둘 띄워도 총 처리량은 늘지 않는다. 각 런만 느려진다
VRAMnvidia-smi memory.used / 16 GB단일 런 사용량의 2배가 16 GB를 넘으면 불가
호스트 RAM런 중 free, 커널 OOM 로그Isaac은 호스트 메모리도 많이 쓴다. 둘 띄우기의 첫 실패 지점은 보통 여기다
NVENCMP4 인코딩 동시 세션 수관전·영상 인코딩이 Isaac 렌더와 같은 GPU를 쓴다. 런 수만큼 인코더 부하도 는다
실측 런 여부런 목적 확인회전 시간 상수·정지 오차 같은 실측 런은 단독 실행. 다른 런과 겹치면 수치가 오염된다
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 5
운영 규칙둘 띄우기가 통과해도 GPU 런 큐 소비자는 여전히 1로 둔다. 두 번째 인스턴스는 개발·리허설용이다. 소비자를 2로 올리는 것은 GPU 노드를 추가할 때다(SEC 05).
SEC 03 · EC2 제약

t3.xlarge 한 대, IAM 없음, 크레딧은 기관 제공 형태에 달렸다

EC2는 4 vCPU · 16 GB 한 대다. 세 가지 제약이 배치를 정한다.

제약내용대응
크기4 vCPU · 16 GB. 상시 서비스, 런 파드, 계산 Job이 전부 여기서 돈다계산 Job에 CPU limit을 걸어 상시 서비스 몫을 보존한다. 런 파드는 런이 끝나면 지운다
IAM 불가관리형 AWS 서비스를 하나도 못 쓴다S3 → MinIO 파드 · RDS → PostgreSQL 파드 · ECR → GHCR · ACM → certbot. 전부 k3s 자체 호스팅
버스트 크레딧t 계열은 베이스라인 이상으로 CPU를 쓰면 크레딧을 소모한다(AWS 문서). 실제 인스턴스 타입과 크레딧 모드(standard / unlimited)는 기관 제공 형태에 따라 다르다인스턴스 안에서 IMDS로 타입을 확인하고, 크레딧 모드는 기관에 확인한다(기준선 §9). 고갈돼도 느려질 뿐 멈추지 않는다. 요청 접수형이라 허용된다
외부 노출nginx :443 하나. 나머지는 tailscale 안에서만 보인다고객·운영자는 :443, GPU 서버는 tailscale 피어로 EMQX·MinIO에 붙는다

인스턴스 타입 확인 (IMDSv2)

TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-type

크레딧 모드는 IMDS에 없다. 콘솔 권한이 없으므로 기관 담당자에게 확인하고 결과를 SEC 06 표에 기록한다.

SEC 04 · 네트워크

홈서버가 EC2로 나가는 tailscale 한 줄. 캠퍼스가 UDP를 막으면 DERP로 돈다

GPU 서버는 인바운드가 없다. tailscale 아웃바운드 하나로 EC2에 붙고, 그 위로 MQTT · S3 · 관전 채널이 지나간다. 전부 TCP다.

실선 파랑 = 실제로 쓰는 경로, 회색 점선 = 캠퍼스에서 막히는 직결. 릴레이는 지연과 대역이 늘지만 제어 채널은 저대역이라 문제가 없다.

SEC 05 · 확장

확장은 GPU 노드를 붙이는 것으로 끝난다. 5080 한 대는 N=1이다

GPU 런 큐 구조 덕에 GPU를 붙이면 소비자가 하나 는다. 임대 GPU로 가면 실행 형태가 바뀐다.
