SEC 00 · 한눈에

주문은 워커 안에서 태어나 90초 뒤 사라진다 — 검증에 실을 주문이 없다

견적 워커는 BE가 outbound: []로 보내면 창고 정보(outbound_avg·출고 시간대·seed)로 주문을 자체 생성해 DES를 돌리고, 런이 끝나면 임시 파일을 지운다. sim.result에는 KPI 14개만 남는다. 검증 버튼이 보내는 sim.verify.request에는 scenario가 없어 fms-core가 재생할 주문이 빈 리스트다 — 로봇은 뜨는데 할 일이 0건, KPI 전부 0.

DB 주문 테이블 0 행orders·outbounds·inbounds — BE에 리포지토리 없음, 시드 SQL에 INSERT 없음
견적 1건 = 500 건 · 823 라인62 KB · 창고 7 · seed 101 · horizon 6 h · 출고창 13:00~18:00
재현 sha 7b4fd2308937…같은 입력 두 번 → 같은 sha. 마스터는 BE 시드 SQL에서 추출, 재추출해도 동일(products 132 · racks 132)
조건 하나 바뀌면 323 건outbound_avg 500 → 800 · sha 전혀 다름. 견적 당시 조건이 DB 어디에도 고정돼 있지 않다
것아키텍처 문서에서의 역할지금
시나리오 패키지② 검토·컴파일 → 견적 PG 저장. DES 워커는 잡 페이로드로, 검증 런은 주입으로 같은 것을 받는다 — 공유 매개없음 컴파일 단계도 저장도 없음
H2 인메모리시뮬 WMS(Spring)의 런 스코프 주문·재고 상태. 런과 함께 소멸 — 격리 장치없음 시뮬 WMS 자체가 미구현. 공유 매개가 아니라 지금 논의 대상이 아니다
결정견적 생성 시 주문을 한 번 만들어 PG에 견적 단위로 통째(JSONB) 저장 → DES 스윕 outbound[]와 검증 scenario.orders 양쪽에 그대로 싣는다. 견적당 1벌(스윕 28런 공유) · 통째 JSONB(쪼개면 순서 하나로 sha 깨짐) · 조건 스냅샷 동봉 · 기존 orders/outbounds는 쓰지 않는다.

SEC 02 · 메시지 순서

여섯 단계 — 워커 변경은 전부 하위 호환이라 먼저 배포해도 된다

#주체메시지내용
1BEsim.request · mode: "compile"견적을 만들면 1건 발행. run_id est_{id}_compile. 나머지 필드는 오늘의 스윕 요청과 같다
2워커sim.result주문을 생성하고 시뮬은 돌리지 않는다. orders(생성기 산출물 그대로) + orders_sha256, kpi: null
3BEsim.request × Nestimate_scenarios에 저장 → 스윕 발행. 각 요청의 outbound에 저장본 orders.outbound 배열을 그대로
4워커sim.result × N받은 outbound[]로 DES(-156 경로). 결과에 orders_sha256 에코 → BE는 저장본과 다르면 그 run 실패 처리
5BEsim.verify.request검증 버튼: scenario에 저장본 orders · orders_sha256 · window_start_s · amr
6GPUNCMD Start → sim.verify.resulthost-orch가 scenario를 Start에 실어 sim-runner·fms-core로(구현됨). fms-core가 orders_sha256 재계산, 다르면 거절, 같으면 재생. 결과 메시지는 오늘과 같다
BE가 놓치기 쉬운 것sim.result 리스너는 지금 findByRunId 실패 시 "모르는 run 무시"로 끝난다. compile 결과는 orders 유무로 run 조회 전에 저장 경로로 분기해야 한다.

orders_sha256 정의sha256( json.dumps(outbound, sort_keys=True, separators=(",",":"), ensure_ascii=False).encode("utf-8") ) — 키 정렬 · 공백 없음 · UTF-8, outbound 배열에 대해서만(meta 제외). host-orch · fms-core · sim-runner가 이미 같은 canonical_json을 쓴다. BE는 계산하지 않는다 — 받은 문자열을 저장하고 그대로 전달만. 저장본을 다시 실을 때 값(숫자·문자열)을 바꾸지 않으면 된다. JSONB가 키 순서를 바꾸는 건 정규형이 다시 정렬하므로 무관.
SEC 04 · DB

새 테이블 하나, 통째 JSONB — 기존 orders/outbounds는 자리가 아니다

-- V3__estimate_scenarios.sql
CREATE TABLE estimate_scenarios (
    scenario_id     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    estimate_id     BIGINT NOT NULL UNIQUE,      -- 견적당 1벌. 스윕 런 전부가 공유
    seed            BIGINT NOT NULL,
    outbound_avg    INTEGER NOT NULL,            -- 이하 4개 = 견적 당시 조건 스냅샷
    outbound_start  TIME NOT NULL,
    outbound_end    TIME NOT NULL,
    horizon_s       BIGINT NOT NULL,
    orders          JSONB NOT NULL,              -- compile 결과의 orders 객체 그대로 (meta + outbound, 62 KB)
    orders_sha256   CHAR(64) NOT NULL,
    created_at      TIMESTAMP NOT NULL DEFAULT now()
);
기존 테이블이 안 되는 이유내용
outbounds.task_id NOT NULL출고 라인을 넣으려면 로봇 태스크가 먼저 있어야 한다. 주문은 태스크보다 먼저 존재한다
견적 구분 컬럼 없음orders에 estimate_id가 없다. 견적 3개면 주문 1500건이 섞인다
시각 표현생성기는 ordered_at_s(초 오프셋), 테이블은 order_at TIMESTAMP
의미실제로 처리한 출고 기록(운영)과 앞으로 돌려볼 시뮬 입력을 섞으면 구분이 안 된다
새 테이블 규칙내용
단위run이 아니라 estimate. 스윕 28런이 같은 주문을 써야 대수 비교가 성립
형태통째 JSONB. 쪼개면 정렬 순서 하나로 sha가 깨지고 개별 조회할 일이 없다. 62 KB, TOAST 압축
스냅샷warehouses 행은 바뀔 수 있다. 500→800이면 323건·다른 sha
싣는 법스윕엔 orders->'outbound', 검증엔 orders 전체. meta는 안에 있어 별도 컬럼 없음. FK는 V1 관행대로 생략
SEC 05 · 역할 · 순서

워커 먼저, BE 다음, fms-core 대조와 재배포로 닫는다

시뮬 · FMS (우리)상태
워커 mode: "compile" — 생성만, orders+orders_sha256 반환미착수
모든 sim.result에 orders_sha256 에코미착수

웹팀 (BE)상태
Flyway V3 estimate_scenarios인계
견적 생성: compile 발행 → 결과 저장 → 스윕 발행(outbound[] 채움). 상태값 추가 없이 RUNNING 안에서인계
sim.result 리스너: orders 있으면 run 조회 전에 분기; 스윕 결과 sha ≠ 저장본이면 run 실패인계
검증 요청에 scenario — orders·orders_sha256·window_start_s·amr인계
compile 실패(status: failed)면 스윕 발행 없이 기존 실패 처리인계
순서내용확인
1워커 compile 모드 + sha 에코 — 하위 호환이라 먼저 배포--once로 compile 요청 1건 → orders 500건·sha 출력
2BE V3 + 저장·발행·검증 요청견적 생성 → estimate_scenarios 1행(500건, sha)
3fms-core sha 대조 + EC2 재배포스윕 결과 28건의 sha 전부 저장본과 일치
4E2E버튼 → sim.verify.result의 verify.fms에 주문 수 ≥ 1, KPI ≠ 0
같이 정할 값제안근거
window_start_s · window_s5400 · 600seed 101 · 창고 7 기준 40건. 첫 10분은 주문이 거의 없어 창을 뒤로 밀어야 한다(계약 §6 ①)
검증 run_idBE 변경 없음지금 verify_{id} 고정이라 한 번 실패하면 host-orch가 재실행하지 않는다(recent 캐시). host-orch 쪽에서 "실패한 run_id는 재실행 허용"으로 푼다(우리)
