SEC 00 · 한눈에

브로커 둘, 역할이 다르다. BE는 RabbitMQ만, GPU 서버는 EMQX만, host-orch만 둘 다

RabbitMQ는 잡 큐다 — DES를 CPU 워커에 나눠 주고(소비자 수 = 동시 실행 수), 최적 1건의 Isaac 검증을 GPU 러너에 직렬로 준다. EMQX는 런 내부 버스다 — 런이 도는 동안 에이전트·sim-runner·fms-core·WMS가 VDA 5050·Sparkplug·biz/v1로 말한다. 두 세계를 잇는 건 host-orch 하나다.

EMQX · 런 버스 · 검증 완료6.3.0 단일 노드. compose·emqx.conf·acl.conf, ACL 행렬 50항목 실브로커 통과 (09-08)

비어 있는 소비자 2DES 워커의 sim.request 소비 루프(3_FMS) · host-orch의 sim.verify.* 소비·발행
SEC 01 · 견적 1건의 흐름

DES 스윕은 병렬, 검증은 최적 1건만 직렬

단계채널발행 → 소비상태
1. DES 스윕 — 대수별 run N개RabbitMQ sim.request ×N → sim.resultBE → DES 워커 ×M → BE (KPI 저장)있음 명세서 §1, BE 발행·수신 코드 있음. 워커 소비 루프는 없음
2. 최적 1건 선정BE 내부 (권장 대수 로직)—있음 LOAD_TOO_LOW 판정 포함
3. Isaac 검증 요청RabbitMQ sim.verify.request ×1BE → host-orch (유일 소비자, prefetch 1 = GPU 직렬)정의 필요
4. 런 실행EMQX — NCMD Start · VDA · biz/v1host-orch ↔ sim-runner · 에이전트 · fms-core · WMS백본 가이드 05~07
5. 결과 회수RabbitMQ sim.verify.resulthost-orch → BE (KPI · 아티팩트 키)정의 필요
결정 2026-09-08 (A안)Isaac 큐의 소비자는 EC2의 host-orch다. GPU 서버의 sim-runner는 상시로 돌지만 AMQP가 아니라 EMQX NCMD로 깨어난다. 런의 절반(fms-core Job · 시뮬 WMS 파드)이 EC2에 있어 런 수명은 한 곳이 가져야 하고, 터널 위 프로토콜은 MQTT 하나로 족하며, k8s 자격증명이 집 서버로 가지 않는다. GPU가 늘면 host-orch가 IDLE 러너 표(NBIRTH · Runner/State)를 보고 NCMD 대상을 고르고 prefetch를 러너 수로 올린다.
아직 정하지 않은 것① 검증 런의 길이 — DES는 6 h 고정 실행인데 Isaac은 RTF ≈ 1.25라 그대로면 벽시계 5시간. 같은 도착 간격으로 10~20분 창만 돌리고 같은 창의 DES KPI와 비교하는 정의가 필요하다. ② 긴 런과 ack — RabbitMQ는 unacked 30분 뒤 소비자를 끊는다(consumer_timeout). sim.verify.*에 정책으로 늘리거나, 꺼내자마자 ack하고 재시도를 BE의 TIMEOUT → retry에 맡기거나. ③ 상태값 — 견적에 VERIFYING 추가, Isaac run 타임아웃은 30분이 아니라 요청의 timeout_s. ④ Start 멱등 — 재전달로 같은 run_id가 오면 RUNNING이면 무시하고 상태만 재보고.
SEC 02 · RabbitMQ

잡 큐 — 프로세스 하나, 큐 둘, 소비자 수가 곧 자원 관리

DES는 병렬 실행의 자원 관리를 위해 RabbitMQ에 붙는다. 워커 수가 동시 DES 수이고, prefetch 1이라 노는 워커가 다음 건을 가져간다. Isaac 검증은 같은 메커니즘을 GPU 풀에 쓴다 — 소비자 1개(host-orch), 곧 직렬. 브로커를 둘로 나누지 않는다: 트래픽이 견적 1건에 메시지 수십 개라 격리로 얻을 게 없고, BE의 커넥션·리스너와 관리 UI만 두 벌이 된다.

큐발행 → 소비본문상태
sim.requestBE → DES 워커 ×Mrun_id · seed · horizon_s · shifts · gap · warehouse · amr · inbound · outbound (명세서 §1-1)있음
sim.resultDES 워커 → BErun_id · status · kpi (명세서 §1-2)있음
sim.verify.requestBE → host-orchrun_id · source_run_id · estimate_id · scenario_pkg · n_robots · models[] · horizon_s · seed · timeout_s · priority신규 명세서 §1-6 초안 예정
sim.verify.resulthost-orch → BErun_id · status · error · kpi · artifacts{video, replay, heatmap}신규

자원 관리 — 같은 메커니즘, 다른 풀

병렬도워커 프로세스 수 = 동시 DES 수. --scale worker=Mhost-orch prefetch = IDLE GPU 러너 수 (지금 1)
1건당 자원워커 1개 = 1 vCPU (compose limit 1.0 · OMP 1 스레드, 이미 있음)GPU 1대 = 런 1개
상한t3.xlarge 4 vCPU − 상시 서비스 2 = 동시 2건. k3s Job이면 limit로 강제GPU 서버 추가 = 소비자 추가
벽시계≈ N × 60~90 s ÷ M부팅 80 s + 검증 창 ÷ RTF
백프레셔 · 순번큐 깊이로 대기 순번·ETA 회신, x-max-priority로 운영자 우선순위동일 (관리 API로 큐 깊이)
ack · 실패결과 후 ack. 재전달돼도 결정론이라 재실행 OK. DLQ 미구현결과 후 ack + consumer-timeout 정책, Start 멱등
영속durable 큐 + persistent 메시지 + 데이터 볼륨(명세서 §1-5 미구현). 웹 재배포에 큐가 날아가지 않게
비어 있는 자리DES 쪽 "트리거 소비자"는 워커 자체다. 명세서 §1-3이 prefetch 1 · 결과 후 ack로 규정했지만 3_FMS에는 Optuna 워커(run_study.py)만 있고 sim.request를 꺼내 sim_v2_tasks.py(SIM_RUN_CONTRACT)를 돌린 뒤 [SUMMARY]를 sim.result로 내는 루프가 없다. host-orch의 AMQP 쪽(소비 · 결과 발행)도 없다.
