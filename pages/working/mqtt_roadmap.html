SEC 01 · 전체 그림

브로커 둘, 레인 셋, 그리고 견적 한 건이 흐르는 길

왜 MQTT인가

로봇 에이전트는 GPU 서버(집)에서 돌고, FMS와 WMS는 EC2에서 돕니다. 서로 다른 기계의 프로세스들이 "누가 누구에게"를 몰라도 주제(토픽)만 맞추면 메시지를 주고받게 하는 것이 MQTT 브로커의 역할입니다. 게다가 AMR 제어에는 이미 업계 표준이 있습니다. VDA 5050은 FMS ↔ AMR 사이의 order/state 메시지 규격이고, Sparkplug B는 장비 세션(살았는지 죽었는지)과 텔레메트리를 다루는 규격입니다. 둘 다 MQTT 위에서 정의돼 있어서, 우리가 메시지 형식을 발명하지 않아도 됩니다.

브로커가 둘인 이유

브로커역할누가 붙나비유
RabbitMQ (EC2, 상시)잡 큐. "이 일을 해 달라"는 요청을 줄 세우고, 노는 워커가 하나씩 가져갑니다. DES는 CPU 워커 여러 개가 병렬로, Isaac 검증은 GPU가 하나라 직렬로견적 BE · DES 워커 · host-orch은행 번호표
EMQX (EC2, 상시)런 내부 버스. 런이 도는 몇 분 동안 에이전트·FMS·sim-runner·WMS가 실시간으로 말합니다에이전트 · sim-runner · fms-core · host-orch · 시뮬 WMS공장 안 무전기

견적 BE는 RabbitMQ만, GPU 서버는 EMQX만 압니다. 둘 다 아는 것은 host-orch 하나뿐이고, 그래서 host-orch가 "번호표를 뽑아 무전기로 지시하는" 다리가 됩니다. 이 결정(A안)의 근거는 접속 지점 문서 §01에 있습니다.

세 레인

견적 한 건이 흐르는 길

  1. DES 스윕. 견적 BE가 로봇 대수별로 요청 N개를 RabbitMQ sim.request에 넣습니다. DES 워커 M개가 나눠 돌리고 sim.result로 KPI를 돌려줍니다. (팀원이 진행 중)
  2. 최적 1건 선정. BE가 결과를 모아 권장 대수를 고릅니다.
  3. Isaac 검증 요청. BE가 그 1건을 sim.verify.request에 넣습니다. 소비자는 host-orch 하나라 GPU 런은 자연히 직렬입니다.
  4. 런 실행. host-orch가 EMQX로 sim-runner에 Start를 지시하고, EC2에 fms-core·WMS 파드를 띄웁니다. 에이전트들이 ONLINE·factsheet를 올리고, FMS가 order를 보내고, 로봇이 움직입니다.
  5. 결과 회수. host-orch가 KPI와 영상·리플레이 키를 sim.verify.result로 돌려주고 BE가 저장합니다.

이 중 지금까지 만든 것은 4번의 "에이전트가 브로커에 붙는 부분"과 브로커 자체입니다. 나머지 4·5번의 host-orch·sim-runner가 다음 일입니다.

3-1. 07 sim-runner — GPU 서버의 상시 데몬 다음

GPU 서버에서 systemd로 늘 떠 있으면서 "런 시작" 지시를 받으면 Isaac과 에이전트 N대를 띄우고, 끝나면 정리하는 프로그램입니다. Sparkplug B의 Edge Node 역할이라, 살아 있음을 NBIRTH로 알리고 죽으면 브로커가 NDEATH 유언을 냅니다. 처음에는 Isaac 대신 가짜 로봇을 띄우는 --fake 모드로 만들어 로컬에서 전 과정을 시험합니다.

의무구현
세션접속 시 Will = NDEATH(bdSeq) 등록 → NBIRTH(bdSeq, seq 0, 전 메트릭). 재접속마다 bdSeq +1
Start (NCMD)잔여 프로세스 정리 → WSIM_N=n ROS_DOMAIN_ID=d python.sh warehouse_sim.py → "[wsim] ready" 대기(타임아웃) → 에이전트 ×N(시리얼·제조사·계정) → DBIRTH ×N → Runner/State = RUNNING. 같은 run_id가 이미 RUNNING이면 무시하고 상태만 재보고(멱등)
텔레메트리uagv/v2/+/+/state를 구독해 로봇별 DDATA로 거울(변화 시만). RTF·RAM·VRAM 5 s 샘플, Heartbeat 5 s
Stop에이전트 SIGTERM(OFFLINE) → 2 s → DDEATH ×N → Isaac SIGTERM → 잔여 kill → IDLE
타임아웃timeout_s 경과 또는 Host STATE offline 15 s → 스스로 Stop
가짜 모드--fake = Isaac 대신 fake_robot:=true 에이전트. 리허설·CI용

산출물: 2_Simulation/sim_runner/runner.py + Sparkplug 인코딩(tools/spb_tap.py 관측 도구 포함) + systemd 유닛 + README. Sparkplug protobuf는 mqtt_practice에서 쓴 Tahu 정의를 재사용합니다. 확인: tap 창에서 NBIRTH → Start → DBIRTH ×2 → RUNNING → Stop → DDEATH → IDLE이 보이고, mosquitto_sub로 에이전트 ONLINE/OFFLINE이 같은 순서로 보이면 됩니다. 규모는 파일 3~4개, 하루 안팎입니다.

3-2. 06 host-orch — EC2의 오케스트레이터 예정

Sparkplug Primary Host이자 잡 큐 소비자입니다. 두 브로커에 모두 붙는 유일한 프로세스라 "AMQP ↔ MQTT 다리"라고 부릅니다.

  1. 접속하면 spBv1.0/STATE/host-orch에 online을 retained로 올립니다(Will = offline). Edge들은 이걸 보고 NBIRTH를 다시 냅니다.
  2. RabbitMQ sim.verify.request를 prefetch 1로 소비합니다. 하나 꺼내면 k8s API로 fms-core Job과 시뮬 WMS 파드를 띄우고(지금은 없으니 건너뜀), sim-runner에 NCMD Start를 보냅니다.
  3. Runner/State가 RUNNING이 되고 fms-core NBIRTH의 RunId가 맞으면 그제야 WMS에 REST로 시작 신호를 줍니다(주문 유실 방지, 결정 11).
  4. 런 동안 seq 갭이면 Rebirth를 요청하고, Heartbeat가 15 s 이상 끊기거나 fms-core NDEATH가 오면 런 실패로 Stop을 냅니다.
  5. 끝나면 KPI(지금은 접속·state 건수·lastNodeId ack 수 같은 연결성 지표)와 아티팩트 키를 sim.verify.result로 발행하고 ack합니다.

확인: 로컬에서는 --start '{…}' CLI로 NCMD만, AMQP는 RabbitMQ가 있는 EC2(또는 로컬 compose)에서. 규모는 하루~이틀.
