SEC 03 · PyPy

원리는 맞았지만 numpy 가 막았다

PyPy 는 추적 JIT 다. 같은 루프가 반복되면 그 경로를 한 줄기 기계어 트레이스로 기록하고 관측된 타입으로 특수화한다 — 박싱이 사라지고 프레임 생성이 인라인된다. 우리 병목(heapq + dict + float 순수 파이썬 루프)이 정확히 그 모양이라 기대가 컸다.

SEC 04 · Cython 이식

자료구조를 바꾼 순간 값이 났다

교훈 ①자료구조를 안 바꾸면 타입 지정은 의미가 없다. 어설프게 하면 오히려 느려진다.

SEC 06 · 자료 모델

세 번 시도해 세 번 다 느려졌다 — 전제가 틀렸다

왜 실패했나

cy10 — 부분 전환은 안 건드린 쪽에 세금을 물린다. 남은 62곳이 __getitem__ 을 거치게 됐고, 특히 rb["pos"] 20곳이 매번 튜플을 새로 할당하게 됐다.

cy11 — 호환 레이어 세금은 사라졌지만 rb 가 타입이 안 붙은 파이썬 객체라 rb.state 가 C 오프셋이 아니라 프로퍼티 디스크립터를 거친다.

cy12 — 타입을 붙여 진짜 구조체 접근으로 만들었는데도 이득이 없다.

전제가 틀렸다 — CPython 3.11 을 과소평가했다3.11 의 적응형 바이트코드는 rb["state"] 를 런타임에 특수화한다. 키가 인터닝된 문자열이고 dict 레이아웃이 반복되면 해시를 다시 계산하지 않고 슬롯을 직접 친다. 게다가 로봇 dict 들이 같은 키 집합이라 key-sharing dict 로 저장돼 메모리도 뭉쳐 있다. 이미 거의 구조체처럼 동작하고 있었다. 거기에 cdef class 를 얹으니 얻는 건 없고 타입 체크·디스크립터 비용만 붙었다.

되짚어 보면 신호가 있었다 — cy6 에서 core.py 를 통째로 컴파일했을 때도 1.03배뿐이었다. 그 시간은 dict 조회가 아니라 로직 자체(배차 판정 · 존 재타겟 · 상태 전이 · 카운터 갱신)에 있었다. 프로파일의 core.py 비중을 "dict 접근 비용"으로 읽은 것이 오류였다.

SEC 07 · 함정

이번에 밟은 함정 셋

① 어설픈 타이핑은 손해다

cy2(스칼라만 타입)가 cy1(그냥 컴파일)보다 느렸다. 자료구조가 파이썬 객체인 채로 지역 변수에만 C 타입을 붙이면 경계마다 박싱·언박싱이 추가된다. 타입은 자료구조와 함께 바꿔야 한다.

② cdivision=True 와 음수 modulo

cy5 에서 h 를 Py_ssize_t 로 타입한 순간 (h - 1) % 4 가 C 시맨틱스로 바뀌어 h=0 에서 3 이 아니라 -1 이 됐다. 로봇이 엉뚱한 방향으로 가 "시작 점유 겹침" AssertionError 가 났다.

(h - 1) % 4    →    (h + 3) % 4     # 피연산자가 항상 비음수 → C·파이썬 동일

cdivision=True 는 C 정수로 타입한 변수에만 적용된다. 1~4단계에서 같은 식이 멀쩡했던 이유는 그때 h 가 파이썬 객체라 파이썬 modulo 를 썼기 때문이다. 타입을 붙이는 순간 modulo 의미가 바뀐다.

하네스가 잡았다이번엔 크래시로 드러났지만 조용히 다른 경로를 낼 수도 있었다. [SUMMARY] 비트 비교가 안전망 역할을 했다 — 이걸 CI 에 넣어야 하는 이유가 실증됐다.

③ 프로파일 %를 원인으로 읽지 말 것

cProfile 은 호출당 1~2 µs 를 더해 호출 수가 많은 함수를 과대평가한다. dmap_h 가 16.7% 로 보였지만 실제 비중은 절반 이하였다. 그리고 core.py 의 큰 비중을 "dict 접근"으로 해석한 것이 SEC 06 의 헛발질로 이어졌다. 프로파일은 어디를 볼지 고르는 데 쓰고, 판단은 wall-clock 으로.
