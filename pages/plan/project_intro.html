SEC 00 · 한눈에 보기

창고 조건을 보내면, 로봇 대수와 기종의 근거가 담긴 견적서를 받는다

"3PL(제3자 물류)이 AMR 도입을 결정할 수 있도록, 창고·물류 조건을 받아 시뮬레이션으로 권장 대수·기종, KPI, 검증 영상을 담은 견적서를 만들어 보내는 요청 접수형 서비스." — 기준선 v3 §0의 한 줄 정의

기준선 개정 (2026-09-03)v2(2026-08-26)의 "셀프서브 견적 SaaS"를 v3에서 요청 접수형 비동기 견적 서비스로 바꿨다. 요청은 큐에 쌓이고, 운영자가 검토·검수하며, 결과는 나중에 발송된다. 이유는 SEC 02. 근거: 기준선 v3 §1, 상세 다이어그램 FMS-WMS 통합 아키텍처 v3.10.

서비스 흐름 한 장

주황 상자는 운영자가 개입하는 곳, 초록 상자는 고객이 받는 결과물입니다. 사이의 세 칸은 고객이 기다리는 동안 내부에서 돕니다. 8단계로 펼친 그림은 SEC 04.

SEC 01 · 문제

로봇 몇 대가, 어떤 기종이 맞는지 답해 주는 근거가 없다

3PL이 AMR 도입을 검토할 때 두 가지가 비어 있다. 대수·기종의 근거와 견적을 검증할 방법이다.

비어 있는 것지금 상황결과
대수·기종의 근거창고마다 통로·주문·작업대 조건이 다르다. 몇 대가 맞는지 계산해 본 적이 없다. 로봇을 늘리면 처리량이 늘다가 어느 지점부터 멈추는데, 그 지점을 모른다감으로 정하거나 결정을 미룬다
견적을 검증할 방법로봇 업체 견적은 파는 쪽의 계산이다. 가정과 계산 과정이 보이지 않는다. 다른 업체 견적과 같은 조건으로 비교할 수도 없다믿거나, 포기하거나

3PL 업계 구조와 고객층 근거는 RESEARCH 02 3PL 업계 구조, 로봇 방식 비교는 RESEARCH 01 물류로봇 지형 참조.

SEC 02 · 답

요청을 받아 검토하고, 시뮬레이션을 돌려 검수한 뒤 보내는 견적 서비스

본 프로젝트의 답은 요청 접수형 견적 서비스다. 고객이 직접 버튼을 눌러 결과를 즉시 받는 셀프서브 방식이 아니다. 접수 · 검토 · 시뮬 · 검수 · 발송의 다섯 단계를 거친다.

접수 · 검토고객 요청은 큐에 쌓인다. 운영자가 요청을 검토하고, 시뮬레이션이 읽을 수 있는 시나리오 패키지로 정리한다.
시뮬레이션대수·기종을 바꿔 가며 빠른 시뮬(DES)을 많이 돌린다. 상위 구성만 물리 시뮬(Isaac Sim)로 다시 검증한다.
검수 · 발송결과를 운영자가 검수한 뒤 견적서로 발송한다. 발송으로 요청이 끝난다.

왜 즉시 응답이 아니라 접수형인가

이유내용
GPU 서버가 1대다물리 시뮬은 GPU 서버 1대(RTX 5080)에서만 돈다. 요청이 겹치면 줄을 서야 한다. 그래서 접수할 때 큐 순번과 예상 소요를 알려 준다. 확장은 GPU 서버를 더 붙이는 것으로 한다
물리 검증은 분 단위로 걸린다Isaac Sim은 실시간으로 돈다. 하루치 운영을 그대로 재생할 수 없어 분 단위 미니 시나리오로 검증한다. 검증 런 하나가 실시간보다 느리다. 화면 앞에서 기다리게 할 수 없다
운영자 검수가 필요하다요청에는 빠진 조건이 있고, 결과에는 해석이 필요하다. 검토(②)와 검수(⑦) 두 곳에 사람이 들어간다. 짧게 돌린 시뮬을 즉시 보여 주는 방식은 근거가 약하다

v2(2026-08-26)까지는 셀프서브 SaaS였다. v3(2026-09-03)에서 위 세 이유로 접수형으로 바꿨다. 기준선 v3 §1.

SEC 03 · 고객 화면

넣는 것은 창고와 물류 조건, 받는 것은 근거가 붙은 견적서

고객이 보는 화면은 두 개다. 요청 화면과 견적서다. 그 사이의 계산은 고객에게 보이지 않는다.

쉽게 말하면 로봇 회사에 "몇 대 필요해요?"라고 물으면 파는 쪽의 답이 온다. 본 프로젝트는 고객의 창고를 컴퓨터 안에 지어 놓고 대수를 바꿔 가며 돌려 본다. 그리고 "이 대수부터는 더 넣어도 처리량이 안 늘어난다"는 지점을 찾아 준다. 그 계산 과정과 로봇이 실제로 도는 영상을 견적서에 같이 붙인다.

요청 화면에 넣는 것

항목내용
창고도면(레이아웃), 구역, 작업대·충전 위치
물류물동량, 주문 프로파일(시간대별 주문량·주문당 라인 수)
로봇기종 후보. 없으면 기준 기종(iw.hub)으로 계산한다
접수 회신접수 즉시 큐 순번과 예상 완료 시점을 받는다

견적서에서 받는 것

항목내용
권장 대수·기종시뮬레이션에서 처리량이 더 늘지 않는 지점(무릎)을 기준으로 권장한다
대수–처리량 곡선대수를 늘릴 때 처리량이 어떻게 변하는지. 시드를 바꿔 여러 번 돌린 분포로 본다
검증 영상물리 시뮬에서 로봇이 실제로 도는 장면. 배속 영상(MP4), 인터랙티브 리플레이(JSON), 궤적 히트맵(PNG)
견적서권장 구성·곡선·영상을 담은 문서. 이메일과 다운로드로 받는다

대수–처리량 곡선 읽는 법

파랑 곡선이 시뮬레이션 결과, 주황 점이 권장 대수입니다. 이 꺾이는 지점을 찾는 것이 계산 엔진의 정지 규칙(무릎 판정)입니다.

SEC 04 · 내부 8단계

접수부터 발송까지 8단계, 사람은 두 곳에만 들어간다

고객이 기다리는 동안 안에서는 8단계가 돈다. 운영자는 ② 검토와 ⑦ 검수에만 개입한다. ①과 ⑧ 사이는 전부 내부 배치다.

단계 번호는 기준선 v3 §2와 같습니다. 각 단계의 인터페이스·큐·저장소는 TECH 02 시스템 아키텍처, 원본 다이어그램은 FMS-WMS 통합 아키텍처 v3.10.

단계누가무엇을
① 견적 요청 접수고객 → 견적 BE창고·물류 조건 입력. 큐 순번·예상 소요 회신
② 운영 검토·시나리오 컴파일운영자 (웹 콘솔)요청을 정제해 시나리오 패키지로 컴파일
③ 스윕 잡 소비잡 큐(RabbitMQ, 메시지 큐) → 계산 엔진 워커잡 = 시나리오 패키지 + 스윕 범위(대수 범위). 워커는 여러 개로 늘릴 수 있다
④ 구성 탐색·θ 추론·DES계산 엔진 (EC2)대수마다 AI 모델이 통행 규칙 파라미터 θ를 추론 → FMS 커널로 가상 시간 실행 × 시드 반복
⑤ Isaac 물리 검증 런런 오케스트레이터 → 시뮬 스택 + GPU 서버상위 구성만 GPU 런 큐에 넣는다. 시뮬 WMS·FMS를 기동하고 Isaac·로봇 에이전트를 띄운다
⑥ KPI 집계·아티팩트sim-runner → MinIO(파일 저장소), 워커 → 견적 BE배속 영상·리플레이·히트맵을 저장한다. KPI와 파일 위치를 DB에 기록한다
⑦ 리포트 작성LLM(대형 언어 모델) 초안 + 운영자 검수권장 구성·곡선·영상을 담은 리포트
⑧ 견적서 발송견적 BE이메일·다운로드. 발송 후 요청 종료
웹 인프라가 두 층인 이유 — 상세

상시 가동하는 견적 서비스와 런마다 켰다 끄는 시뮬 스택을 분리한다(웹 인프라 2층). 원칙은 영속은 견적 도메인, 휘발은 시뮬 도메인이다.

공용EMQX(MQTT 브로커). 제어 채널이 런보다 먼저 있어야 한다상시

기기는 둘이다. EC2 t3.xlarge(k3s 자체 호스팅)에 견적 서비스·시뮬 스택·계산 엔진이 올라가고, GPU 서버 1대(RTX 5080)에 Isaac Sim과 로봇 에이전트가 올라간다. 기준선 v3 §3.1·§3.2.

SEC 05 · 두 시뮬레이션

빠른 시뮬로 많이 돌리고, 물리 시뮬로 상위 구성만 확인한다

계산은 두 종류다. 역할은 다르지만 같은 FMS 결정 커널과 같은 시나리오 패키지를 쓴다.

빠른 시뮬 (DES)물리 시뮬 (Isaac Sim)
단계④⑤
무엇을대수·기종 조합마다 가상 시간으로 실행. 시드를 바꿔 반복상위 구성만 3D 물리 세계에서 실제 로봇 소프트웨어(ROS 2)로 실행
시간가상 시계. 사건이 없는 시간은 건너뛴다실시간 이하. 분 단위 미니 시나리오
창고 소프트웨어(WMS)WMS 라이트: 주문 생성·배차·서비스 시간을 확률 모델로시뮬 WMS: 실제 Spring WMS
어디서EC2(k3s Job), CPUGPU 서버(RTX 5080) 1대
결과대수–처리량 분포 → 권장 대수(무릎)KPI 갭 보정 + 검증 영상·리플레이·히트맵

주황이 두 시뮬레이션이 공유하는 것(시나리오 패키지, FMS 커널)입니다. 초록 점선은 물리 시뮬 결과로 빠른 시뮬을 보정하는 방향입니다.

같은 두뇌를 쓴다는 것의 의미

  • FMS 결정 커널은 순수 함수다 — 시계와 난수를 밖에서 받고 입출력이 없다. 그래서 가상 시계로 부르는 하네스와 틱마다 부르는 MQTT 데몬, 두 실행 셸에 같은 코드를 꽂을 수 있다
  • 같은 커널, 같은 θ라서 보정이 성립한다 — 물리 시뮬에서 잰 차이(명령 반영 지연, 미끄러짐)를 DES에 되먹인다. 검증 대상 구성은 DES도 같은 시간창으로 다시 돌려 비교한다
  • WMS는 공유하지 않는다 — 측정 대상(FMS)은 공유하고 환경(WMS)은 모델링한다. 두 WMS는 하나의 시나리오 패키지를 읽는 두 소비자다. 골든 시나리오 패리티 테스트로 둘의 정합성을 지킨다

FMS의 경로계획 방식은 PIBT 헤딩 모델에 AI가 예측한 통행 규칙 θ 11개를 얹은 구조다. 이론은 TECH 04 경로계획 이론 기반, 담당은 팀 FMS 파트(팀 레포 3_FMS/docs/). 기준선 v3 §4.

SEC 07 · 자주 묻는 질문

발표와 검토에서 반복해서 나온 질문 세 가지

답은 전부 기준선 v3에 있는 결정에서 나온다. 펼쳐서 읽는다.

Q1. 왜 SaaS가 아닌가 — 펼쳐 보기
  • 셀프서브 SaaS는 고객이 직접 넣고 즉시 받는 방식이다. v2(2026-08-26)까지의 계획이었다
  • 기각 이유는 셋이다. GPU 서버가 1대라 물리 검증이 줄을 선다. 짧게 돌린 시뮬을 즉시 보여 주는 방식은 근거가 약하다. 요청 정제와 결과 해석에 운영자가 필요하다
  • 그래서 요청 접수형이다. 접수할 때 큐 순번과 예상 소요를 알려 주고, 결과는 나중에 보낸다
  • 확장은 GPU 서버를 추가해 GPU 런 큐 소비자를 늘리는 것으로 한다. 지금의 1대는 그 그림의 N=1이다
Q2. 숫자를 어떻게 믿나 — 펼쳐 보기
  • 반복 — 같은 조건을 시드를 바꿔 여러 번 돌려 분포로 본다. 한 번 돌린 값을 쓰지 않는다
  • 물리 검증 — 상위 구성은 물리 시뮬에서 실제 로봇 소프트웨어로 다시 돌린다. 차이는 DES를 같은 시간창으로 재실행해 비교하고 보정한다
  • 증거물 — 검증 영상·리플레이·히트맵(아티팩트)이 견적서에 붙는다. 로봇이 도는 장면을 고객이 직접 본다
  • 재현성 — 시나리오 해시 + 시드가 키다. 같은 입력이면 같은 결과가 나온다
  • 검수 — 운영자가 최종 검수한다. 자동 생성 리포트를 그대로 보내지 않는다
Q3. 실시간 관제(FMS)를 파는 건가 — 펼쳐 보기
  • 아니다. 파는 것은 견적서다
  • FMS는 견적 숫자를 만드는 내부 엔진이다. 시뮬레이션 안에서 로봇을 지휘한다. 고객 창고에 설치하는 제품이 아니다
  • 다만 물리 검증 런은 FMS와 시뮬 WMS가 실제 인터페이스로 붙는 구조라, 현장 배포 형태와 같은 모양이다. 근거는 FMS-WMS 통합 아키텍처의 설계 원칙 노트
