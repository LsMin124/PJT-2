SEC 00 · 한눈에 보기

창고 조건을 보내면, 로봇 대수와 기종의 근거가 담긴 견적서를 받는다

"3PL(제3자 물류)이 AMR 도입을 결정할 수 있도록, 창고·물류 조건을 받아 시뮬레이션으로 권장 대수·기종, KPI, 검증 영상을 담은 견적서를 만들어 보내는 요청 접수형 서비스." — 기준선 v3 §0

  • 무엇을 주나 — SEC 03
  • 어떻게 만들어지나 — 아래 그림 · SEC 05 · 상세는 TECH 02 시스템 아키텍처
  • 왜 시뮬레이션인가 — SEC 01 · SEC 07 Q2

서비스 흐름 한 장

주황 = 운영자가 개입하는 곳, 초록 = 고객이 받는 결과물. 사이 세 칸은 고객이 기다리는 동안 내부에서 돈다.

SEC 01 · 문제

로봇 몇 대가, 어떤 기종이 맞는지 답해 주는 근거가 없다

3PL이 AMR 도입을 검토할 때 두 가지가 비어 있다. 대수·기종의 근거와 견적을 검증할 방법이다.

비어 있는 것지금 상황결과
대수·기종의 근거창고마다 통로·주문·작업대 조건이 다르다. 몇 대가 맞는지 계산해 본 적이 없다. 로봇을 늘리면 처리량이 늘다가 어느 지점부터 멈추는데, 그 지점을 모른다감으로 정하거나 결정을 미룬다
견적을 검증할 방법로봇 업체 견적은 파는 쪽의 계산이다. 가정과 계산 과정이 보이지 않는다. 다른 업체 견적과 같은 조건으로 비교할 수도 없다믿거나, 포기하거나

3PL 업계 구조는 RESEARCH 02 3PL 업계 구조, 로봇 기종 비교는 RESEARCH 03 AMR 기종 선정.

SEC 02 · 답

요청을 받아 검토하고, 시뮬레이션을 돌려 검수한 뒤 보내는 견적 서비스

답은 요청 접수형 견적 서비스다. 고객이 버튼을 눌러 즉시 결과를 받는 셀프서브가 아니다. 즉시 응답을 접은 세 이유는 SEC 07 Q1.

접수 · 검토요청은 큐에 쌓인다. 운영자가 검토해 시뮬레이션이 읽는 시나리오 패키지로 정리한다.
시뮬레이션대수·기종을 바꿔 빠른 시뮬(DES)을 많이 돌리고, 상위 구성만 물리 시뮬(Isaac Sim)로 검증한다.
검수 · 발송운영자가 검수한 뒤 견적서로 발송한다. 발송으로 요청이 끝난다.
SEC 03 · 고객 화면

넣는 것은 창고와 물류 조건, 받는 것은 근거가 붙은 견적서

고객이 보는 화면은 요청 화면과 견적서 둘이다. 그 사이의 계산은 고객에게 보이지 않는다.

쉽게 말하면 고객의 창고를 컴퓨터 안에 지어 놓고 대수를 바꿔 가며 돌려 본다. "이 대수부터는 더 넣어도 처리량이 안 늘어난다"는 지점을 찾고, 그 계산 과정과 로봇이 실제로 도는 영상을 견적서에 같이 붙인다.

요청 화면에 넣는 것

항목내용
창고도면(레이아웃), 구역, 작업대·충전 위치
물류물동량, 주문 프로파일(시간대별 주문량·주문당 라인 수)
로봇기종 후보. 없으면 기준 기종(iw.hub)으로 계산한다
접수 회신접수 즉시 큐 순번과 예상 완료 시점을 받는다

견적서에서 받는 것

항목내용
권장 대수·기종시뮬레이션에서 처리량이 더 늘지 않는 지점(무릎)을 기준으로 권장한다
대수–처리량 곡선대수를 늘릴 때 처리량이 어떻게 변하는지. 시드를 바꿔 여러 번 돌린 분포로 본다
검증 영상물리 시뮬에서 로봇이 실제로 도는 장면. 배속 영상(MP4), 인터랙티브 리플레이(JSON), 궤적 히트맵(PNG)
견적서권장 구성·곡선·영상을 담은 문서. 이메일과 다운로드로 받는다

대수–처리량 곡선 읽는 법

파랑 곡선이 시뮬레이션 결과, 주황 점이 권장 대수. 이 꺾이는 지점을 찾는 것이 계산 엔진의 정지 규칙(무릎 판정)이다.

SEC 04 · 내부 8단계

접수부터 발송까지 8단계, 사람은 두 곳에만 들어간다

8단계 각각의 인터페이스·큐·저장소와 웹 인프라 2층(상시 견적 서비스 / 런 단위 시뮬 스택)은 TECH 02 시스템 아키텍처. 운영자는 ② 검토와 ⑦ 검수에만 개입한다.

SEC 05 · 두 시뮬레이션

빠른 시뮬로 많이 돌리고, 물리 시뮬로 상위 구성만 확인한다

  • 같은 두뇌 — 빠른 시뮬(DES, ④)과 물리 시뮬(Isaac Sim, ⑤)은 같은 FMS 결정 커널과 같은 θ를 쓴다. 커널은 시계·난수를 밖에서 받는 순수 함수라 두 실행 셸(가상 시계 하네스, MQTT 데몬)에 그대로 꽂힌다
  • 같은 입력 — 두 시뮬의 WMS(WMS 라이트 / 시뮬 WMS)는 하나의 시나리오 패키지를 읽는 두 소비자다. 골든 시나리오 패리티 테스트로 둘의 정합성을 지킨다
  • 보정 — 물리 시뮬에서 잰 차이(명령 반영 지연, 미끄러짐)를 DES에 되먹인다. 검증 대상 구성은 DES도 같은 시간창으로 다시 돌려 비교한다

경로계획은 PIBT 헤딩 모델 + AI가 추론한 통행 규칙 θ 11개. 이론은 TECH 04, 커널·실행 셸 구조는 TECH 02.

SEC 06 · 팀 구성

세 파트가 인터페이스로 만난다

웹 · FMS/AI · 시뮬 세 파트가 맡는 단계와 파트 사이 인터페이스(REST, trial 계약, MQTT/VDA 5050)는 TECH 02 시스템 아키텍처. 시뮬 파트 현황은 WORKING T3·T4 진행.

SEC 07 · 자주 묻는 질문

발표와 검토에서 반복해서 나온 질문 세 가지

Q1. 왜 SaaS가 아닌가 — 펼쳐 보기
  • 셀프서브 SaaS는 고객이 직접 넣고 즉시 받는 방식이다. v2(2026-08-26)까지의 계획이었다
  • 기각 이유는 셋이다. GPU 서버가 1대(RTX 5080)라 물리 검증이 GPU 런 큐에서 줄을 선다. 물리 검증은 분 단위 미니 시나리오라 화면 앞에서 기다리게 할 수 없다. 요청 정제(②)와 결과 해석(⑦)에 운영자가 필요하다
  • 그래서 요청 접수형이다. 접수할 때 큐 순번과 예상 소요를 알려 주고, 결과는 나중에 보낸다
  • 확장은 GPU 서버를 추가해 GPU 런 큐 소비자를 늘리는 것으로 한다. 지금의 1대는 N=1이다
Q2. 숫자를 어떻게 믿나 — 펼쳐 보기
  • 반복 — 같은 조건을 시드를 바꿔 여러 번 돌려 분포로 본다. 한 번 돌린 값을 쓰지 않는다
  • 물리 검증 — 상위 구성은 물리 시뮬에서 실제 로봇 소프트웨어(ROS 2)로 다시 돌린다. 차이는 DES를 같은 시간창으로 재실행해 비교하고 보정한다
  • 증거물 — 검증 영상·리플레이·히트맵(아티팩트)이 견적서에 붙는다
  • 재현성 — 시나리오 해시 + 시드가 키다. 같은 입력이면 같은 결과가 나온다
  • 검수 — 운영자가 최종 검수한다. 자동 생성 리포트를 그대로 보내지 않는다
Q3. 실시간 관제(FMS)를 파는 건가 — 펼쳐 보기
  • 아니다. 파는 것은 견적서다
  • FMS는 견적 숫자를 만드는 내부 엔진이다. 시뮬레이션 안에서 로봇을 지휘한다. 고객 창고에 설치하는 제품이 아니다
  • 다만 물리 검증 런은 FMS와 시뮬 WMS가 실제 인터페이스로 붙는 구조라, 현장 배포 형태와 같은 모양이다. 근거는 FMS-WMS 통합 아키텍처의 설계 원칙 노트
