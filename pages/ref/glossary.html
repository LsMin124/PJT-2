요청 접수형 서비스Intake Service — 요청을 받아 나중에 결과를 보내는 비동기 서비스

고객이 조건을 남기면 요청이 큐에 쌓이고, 운영자가 검토·검수한 뒤 결과를 나중에 발송하는 서비스 형태. 셀프서브 SaaS의 반대다.

이 프로젝트에서 — v3의 제품 형태 — GPU가 1대라 검증 런을 줄 세워야 하고, 영상·리플레이는 사람이 검수해야 한다. 8단계: ①접수→②운영 검토·시나리오 컴파일→③스윕 잡 소비→④θ 추론·DES→⑤Isaac 검증 런→⑥KPI·아티팩트→⑦리포트→⑧발송. 운영자 개입은 ②·⑦. 상세는 시스템 아키텍처, 제품은 Santa Factory·데모.

런Run — Isaac 검증 런 한 번

시뮬 WMS·FMS 파드를 띄우고 Isaac Sim에서 로봇을 움직여 KPI와 산출물을 얻는 실행 단위 하나. 런 ID로 식별하고 상태기로 관리한다.

이 프로젝트에서 — 분 단위 미니 시나리오다(Isaac은 실시간이라 하루치 재생은 불가). 상태는 QUEUED → PROVISIONING → LOADING → RUNNING → COLLECTING → DONE/FAILED. 런 ID 기준 멱등이라 재시도해도 두 번 세지 않고, 실패는 DLQ로 간다. 한 trial에 검증 런은 0..1개. 상태 전이는 런 오케스트레이터, GPU 쪽 실행은 sim-runner.

trialTrial — 스윕 안의 구성 하나

스윕 잡 안에서 "대수 n · 기종 · 시드" 한 조합을 DES로 돌린 단위. 요청 1:N 잡 1:N trial 1:0..1 검증 런 계층의 가운데 칸이다.

이 프로젝트에서 — trial마다 θ를 추론하고 FMS 커널이 가상 시간으로 돈다. KPI가 모여 대수–처리량 곡선이 되고, 무릎(포화점)을 정하는 정지 규칙은 계산 엔진 소유다. PostgreSQL 테이블 trial이 이 단위. 상위 trial만 GPU 런 큐로 넘어가 런이 된다. 백엔드↔AI API 스키마(run_id·seed·warehouse·amr·orders→kpi)가 trial 단위 계약.

시나리오 패키지Scenario Package — 컴파일된 시뮬 입력 묶음

운영자가 요청을 정제해 만든 시뮬 입력 묶음. zones.json · 맵 · 주문 분해 규칙 · 수요 프로파일 · rack_id↔시뮬 좌표 매핑으로 구성된다.

이 프로젝트에서 — 서비스 흐름 ②에서 만들어져 두 소비자가 읽는다 — DES의 WMS 라이트와 검증 런의 시뮬 WMS. 같은 입력을 쓰므로 두 결과를 비교할 수 있다. 재현성 키는 시나리오 해시 + 시드, 파일은 MinIO. zones.json·맵의 출처는 시뮬 파트의 T3 창고 씬(sil/t3_warehouse_map/).

시뮬 WMSSimulation WMS — 검증 런용 실제 창고관리 서버

Isaac 검증 런 동안 실제로 주문을 만들고 작업을 나눠 주는 Spring Boot 서버. H2 인메모리 DB를 쓰고, 런이 끝나면 함께 사라진다.

이 프로젝트에서 — 검증 런은 SIL이라 WMS도 확률 모델이 아닌 진짜 서버로 돈다. 테이블은 run_context·zone·location·station·sku·inventory·order·order_line·task. 작업 이벤트 로그는 H2 밖(JSONL → MinIO), 주문·이벤트는 biz/v1 JSON으로 EMQX에 발행. JPQL만 써서 프로파일만 바꾸면 PostgreSQL로 승격 가능. DES 쪽 짝은 WMS 라이트.

WMS 라이트WMS Lite — DES 안의 확률 모델 WMS

DES(④) 안에서 주문 생성·라인 합침·배차·서비스 타이머만 확률 모델로 흉내 내는 경량 WMS.

이 프로젝트에서 — DES는 수백 번 돌리므로 매번 Spring 서버를 띄울 수 없다. 원칙은 "측정 대상은 공유, 환경은 모델링" — FMS 결정 커널은 검증 런과 같은 코드, WMS는 모델이다. 같은 시나리오 패키지를 읽고 골든 시나리오 패리티 테스트로 시뮬 WMS와 맞춘다. 현재 DES의 실체는 틱 시뮬(sim_v2)이며 WMS 라이트도 그 안에 있다.

런 오케스트레이터Run Orchestrator — 검증 런의 생애를 관리하는 파드

GPU 런 큐를 소비해 시뮬 스택 파드를 띄우고, sim-runner에 start/go/stop을 보내고, 산출물 키를 모아 결과 이벤트를 발행한 뒤 파드를 지우는 단일 파드.

이 프로젝트에서 — 순서: 큐 소비→시뮬 WMS·FMS 파드 기동→시나리오 주입 대기→sim-runner에 start/go(MQTT sim/control, Sparkplug B)→하트비트·시뮬 시각 감시→stop→아티팩트 키 수집→결과 이벤트 발행→파드 삭제. 런 ID 기준 멱등, 실패는 DLQ. 재기동 시 떠 있는 파드와 큐 상태를 맞춘다. EC2 k3s 위 단일 파드.

GPU 런 큐GPU Run Queue — 검증 런을 줄 세우는 큐

Isaac 검증 런을 GPU 수만큼만 동시에 돌리도록 직렬화하는 RabbitMQ 큐. 소비자 수 = GPU 수다.

이 프로젝트에서 — 큐잉은 2단 — 1단 요청 잡 큐는 CPU 워커 N개가 스윕 잡을, 2단 GPU 런 큐는 검증 런만 받는다. 현재 GPU는 RTX 5080 1대라 소비자도 1개. 큐 깊이가 곧 대기 순번이고 런 평균 시간을 곱하면 ETA — 접수 시 회신하는 순번·예상 소요의 근거다. 실패 처리는 DLQ.

DLQDead Letter Queue — 처리 실패 메시지 보관 큐

정해진 횟수만큼 재시도해도 실패한 메시지를 따로 모아 두는 큐. 실패를 버리지 않고 사람이 보게 남긴다 — "문제를 숨기지 말고 드러내라"는 Andon의 사상이다.

이 프로젝트에서 — 소비자가 nack하거나 TTL이 지나면 dead-letter 교환기로 넘어간다. 요청 잡 큐와 GPU 런 큐 둘 다 DLQ를 둔다. 재시도를 넘긴 스윕 잡·파드 기동에 실패한 런이 남고, 운영자가 웹 콘솔에서 재투입하거나 종료한다. 런 ID 멱등과 짝이라 재투입해도 두 번 세지 않는다. 공식 문서: RabbitMQ DLX.

아티팩트Artifact — 런이 남기는 산출 파일

검증 런이 만드는 파일들 — 배속 영상(MP4) · 리플레이(JSON) · 히트맵(PNG) · 로그. MinIO에 저장하고, 메타는 PostgreSQL artifact 테이블에 둔다.

이 프로젝트에서 — 견적서에 들어가는 실물. 영상은 고객이 눈으로 확인하는 용도, 리플레이는 브라우저에서 다시 돌려 보는 용도, 히트맵은 정체 구간을 보는 용도다. 시나리오 파일과 작업 이벤트 로그(JSONL)도 같은 저장소에 둔다. 업로드는 sim-runner가 presigned URL로 직접 하고, 리포트(⑦)에 임베드된다. 저장소는 MinIO.

presigned URLPre-signed URL — 기한부 서명 업로드·다운로드 주소

서버가 미리 서명해 준 S3 호환 주소. 가진 쪽은 자격 증명 없이 정해진 시간 동안 특정 키에 PUT/GET 할 수 있다.

이 프로젝트에서 — GPU 서버의 sim-runner에 MinIO 계정을 심지 않기 위해 쓴다. 견적 BE가 런 ID별 키로 PUT용 URL을 발급 → sim-runner가 파일을 직접 올림 → 결과 이벤트에 키를 실어 보냄. 고객 다운로드도 GET용 URL로 같은 방식. S3 API를 그대로 따르므로 MinIO를 S3로 바꿔도 코드가 같다.
02 · 경로계획 · FMS — 다중 로봇 경로 문제와 그것을 돌리는 커널·셸
MAPFMAPF 계열 비교PIBTθ헤딩 모델스윙 예약배리어 틱결정 커널실행 셸

MAPFMulti-Agent Path Finding — 다중 로봇 경로 탐색

여러 로봇의 경로를 서로 충돌하지 않도록 한꺼번에 찾는 문제. 한 대의 최단 경로(A*)를 넘어 "전체가 함께 빨라지는" 조합을 찾는다. 로봇이 늘면 통로 정체·교차로 대기가 급증한다("로봇을 늘려도 처리량이 안 느는" 원인).

이 프로젝트에서 — 견적 엔진의 핵심. 틱 시뮬 안에서 정체·대기가 나타나고, 그 결과가 "몇 대가 적정인가"의 근거다. 기준선 v3(2026-09-03)부터 v1의 이동 계층은 PIBT 헤딩 모델이다. CBS·RHCR·TAPF는 MAPF 계열 비교, 이론 배경은 경로계획 이론 기반.

MAPF 계열 비교CBS · RHCR · TAPF

CBS는 충돌마다 "그 시각 그 칸 금지" 제약을 걸어 재탐색하는 최적 알고리즘(로봇이 늘면 계산 폭발), RHCR은 앞의 W스텝만 풀고 h스텝마다 재계획하는 연속 운영(lifelong) 프레임, TAPF는 할당과 경로를 한 문제로 묶는 결합 최적화다.

이 프로젝트에서 — v1은 PIBT다. 매 틱 다음 한 칸만 정하므로 CBS식 전체 탐색도, RHCR식 윈도우 재계획도 없다. CBS는 품질 기준으로만 남는다. 할당(디스패처)과 경로는 분리하되 정체 페널티가 든 경로 비용을 할당 비용에 넣는 절충(TAPF의 발상)이다.

PIBTPriority Inheritance with Backtracking

여러 로봇의 "다음 한 칸"을 매 틱 우선순위 순으로 정하는 MAPF 알고리즘. 높은 우선순위 로봇이 가려는 칸의 낮은 로봇이 우선순위를 물려받아 먼저 비키고, 비킬 곳이 없으면 되돌아가 다른 칸을 고른다. 틱당 계산이 가벼워 수백 대에도 맞지만 전역 최적은 아니다.

이 프로젝트에서 — v1의 이동 계층(FMS 파트, 2026-09-02). 1.0 m 격자 위에서 헤딩 모델로 확장해 회전을 틱에 반영하고, 거리장은 θ 가중 다익스트라다. 원 논문: Okumura et al. (AIJ 2022).

θTraffic-rule Parameters — 통행 규칙 파라미터 11개

창고 구조·짐 흐름·운영 조건에서 AI 모델이 추론하는 통행 규칙 값 11개(연속 8·범주 3). θ는 경로가 아니라 통로별 가중치·통행 규칙이며, from_theta가 통행 비용으로 바꿔 PIBT 거리장에 들어간다.

이 프로젝트에서 — 2-트랙 — A안(AI)이 θ를 예측하고 B안(알고리즘)이 받아 이동 계층을 돈다. 계약은 3_FMS/contracts/guidance_types.py(스키마 v2). trial마다 θ를 한 번 추론하고 DES(④)와 Isaac 검증 런(⑤)이 같은 θ를 쓰므로 두 결과를 비교할 수 있다. 미합의 항목은 구현 결정 인벤토리에서 추적.

헤딩 모델Heading Model — 방향을 상태에 넣은 격자 모델

로봇 상태를 (칸, 방향)으로 두고 회전도 틱을 쓰는 동작으로 계산하는 격자 모델. 차체가 셀보다 길어 자기 칸과 뒤 칸 2칸을 점유한다. 액션은 대기·전진·좌/우 회전·후진 다섯 가지.

이 프로젝트에서 — 1.0 m 격자에 1.44 m 차체(iw.hub)를 올리면 회전 중 옆 로봇과 부딪히는 것이 Isaac에서 실측되어 바꾼 모델이다(FMS 파트, 2026-09-02). 회전은 틱을 쓰고 스윙 칸을 예약하며, 그만큼 권장 대수의 포화점이 달라진다. 회전 시간 상수는 Isaac 실측(시뮬 파트, 미완)으로 확정한다.

스윙 예약Swing Reservation — 회전 시 쓸고 지나가는 칸 예약

제자리 회전 때 차체가 쓸고 지나가는 옆 칸(스윙 칸)을 그 틱 동안 예약해 다른 로봇의 진입을 막는 규칙.

이 프로젝트에서 — 헤딩 모델의 일부. PIBT는 회전 액션을 고를 때 스윙 칸이 비었는지 확인하고 회전 틱 동안 함께 잠근다. 통로 폭 1칸에서는 회전이 막힐 수 있어 교차로·버퍼 칸 배치가 중요하다. 스윙 반경은 iw.hub 앞축 위치 실측 후 확정. 로봇 쪽 동작은 스팟턴.

배리어 틱Barrier Tick — 전원 완료 후 다음 틱

FMS가 틱 하나의 명령을 모든 로봇에 내리고, 전원의 완료 보고(ack)가 모이면 다음 틱을 계산하는 동기 방식. 가장 늦은 로봇을 기다리므로 Isaac(실시간)에서는 틱이 FMS 가정(1 s)보다 길어진다.

이 프로젝트에서 — 가짜 로봇 E2E 실측은 1 m 전진 2.2 s, 90° 회전 2.3 s(램프 1.0 m/s², 최고 0.8 m/s) — Isaac 런은 실시간의 절반 이하다. T4 에이전트는 state.lastNodeId가 바뀌는 즉시 ack를 낸다. lockstep인지 고정 주기 틱인지는 FMS 파트가 확인 중.

결정 커널Decision Kernel — I/O 없는 순수 FMS 코어

시계와 난수를 밖에서 주입받고 파일·소켓·스레드를 전혀 쓰지 않는 FMS 코어. 호출 형태는 step(world, now, events) → decisions 하나이며, 시드만 같으면 결과가 같다.

이 프로젝트에서 — 같은 커널을 DES(④)와 Isaac 검증 런(⑤)이 공유한다 — "측정 대상은 공유, 환경은 모델링" 원칙에서 공유되는 쪽. 안에는 PIBT 이동 계층, 배차, 미션 상태기가 들어가고 ROS에 참여하지 않는 순수 Python이다. 커널을 감싸는 껍데기는 실행 셸 2종.

실행 셸Execution Shell — 커널을 돌리는 껍데기 2종

결정 커널에 시계·사건을 넣고 결과를 밖으로 내보내는 바깥 층. 가상 시계용 하네스와 MQTT 데몬 두 가지가 있다.

이 프로젝트에서 — 하네스(④)는 DES 안에서 커널을 함수처럼 동기 호출한다. MQTT 데몬(⑤)은 EMQX에서 로봇 상태를 받아 events로 넣고 커널의 decisions를 VDA 5050 order로 바꿔 발행한다. 셸이 달라도 커널은 같으므로 DES와 Isaac 결과의 차이는 환경 모델의 차이로 좁혀진다. 로봇 쪽 대응물은 T4 에이전트의 VDA 5050 브리지, 틱 동기는 배리어 틱.

ROS 2Robot Operating System 2

로봇 소프트웨어의 사실상 표준 프레임워크. OS가 아니라 로봇의 각 기능을 독립 노드로 쪼개고 토픽 발행/구독으로 통신을 표준화한 미들웨어(DDS 기반, QoS 설정 가능). 하드웨어 추상화(ros2_control)·모션 플래닝(MoveIt2)이 그 위의 생태계다.

이 프로젝트에서 — T4 에이전트(amr-agent)가 ROS 2 Humble 노드 묶음이다 — VDA 5050 브리지, order executor, 그리드 프리미티브 컨트롤러, (선택) AMCL 위치 추정. 토픽 이름·메시지 타입이 곧 계약이라는 원칙은 웹의 REST 계약과 같다. 코드는 sil/t4_agent/. 로봇팔(ros2_control·MoveIt2) 실습 기록은 아카이브.

Nav2 · AMCL(위치 추정만)Navigation 2 — 위치 추정만 사용

ROS 2의 표준 자율주행 패키지 묶음. 지도→위치 추정(AMCL, 내부적으로 EKF 등 센서 융합)→전역 경로→지역 제어(행동 트리 구성)→속도 명령의 플러그인 파이프라인이며, 로봇 한 대의 주행을 다룬다.

이 프로젝트에서 — 팀은 nav2_map_server + nav2_amcl로 위치 추정만 쓴다(에이전트 설정 pose_source: odom | amcl). 경로는 FMS(PIBT)가 VDA 5050 노드·엣지로 내리고 구간 주행은 그리드 프리미티브가 하므로 Nav2의 플래너·컨트롤러는 쓰지 않는다. 여러 대의 경로는 MAPF.

URDFUnified Robot Description Format

로봇의 뼈대를 기술하는 XML 파일. 어떤 링크가 어떤 조인트로 연결되고 길이·질량·가동 범위가 얼마인지 담는다. 시뮬레이터·플래너가 같은 파일을 공유하므로 URDF가 틀리면 모든 게 틀린다.

이 프로젝트에서 — 검증 기종의 모델이 URDF/USD 형태로 Isaac Sim에 올라간다. iw.hub는 Isaac 내장 에셋, MiR 250은 공개 URDF가 있어 서브 기종으로 선정됐다 — 기준 기종 선정. UR5e URDF를 직접 뜯어본 실습 기록은 아카이브.

그리드 프리미티브Grid Primitive — 격자 이동의 기본 동작 단위

로봇이 실행할 수 있는 고정 동작 3종(스팟턴·직진 1칸·후진 1칸). VDA 5050 노드·엣지를 이 단위로 분해해 실행한다. 전진은 "헤딩 정렬(스팟턴)→직진→셀 중심 정지"로 풀린다.

이 프로젝트에서 — T4 에이전트의 컨트롤러 계층. 곡선 추종기(T2의 Pure Pursuit) 대신 격자에 맞는 동작만 남겨 정지·헤딩 오차를 작게 유지한다 — 가짜 로봇 E2E에서 정지 오차 4 mm, 헤딩 1.2°. FMS 파트 요구 4건(스팟턴·오차 0.1 m 이하·배리어 틱·후진)을 이 컨트롤러로 채운다. T2 추종기는 SIL 가이드.

스팟턴Spot Turn — 제자리 회전

바퀴 두 개를 반대로 돌려 차체 중심을 움직이지 않고 방향만 바꾸는 동작. 차동 구동 로봇의 가장 작은 회전이며, 홀로노믹(옴니휠) 구동과 달리 회전에 시간이 든다.

이 프로젝트에서 — 격자 이동에서는 옆 칸을 크게 침범하는 곡선 회전 대신 스팟턴을 쓴다. 순서는 "셀 중심 정지→제자리 회전→헤딩 정렬 확인→직진". 실측은 90° 회전 2.3 s(가짜 로봇), Isaac 각속도 실측은 미완. PIBT의 "회전 ±90°"가 VDA 5050에서는 "같은 좌표 노드+새 theta"로 내려오고 에이전트가 스팟턴으로 수행한다. 스윙 예약과 짝.

스티칭Stitching — VDA 5050 order update로 경로 이어 붙이기

같은 orderId에 orderUpdateId를 올려 새 노드를 뒤에 붙이는 VDA 5050 방식. 앞부분(base)은 released로 주행이 확정되고 뒷부분(horizon)은 예고이며, 다음 update는 이전 order의 마지막 노드로 시작해야 한다 — 이 겹치는 노드가 이음매다.

이 프로젝트에서 — FMS가 틱마다 다음 1칸을 released로 내리면 로봇은 멈추지 않고 계속 달린다. T4 에이전트의 order executor가 담당하며, 배리어 틱에서는 ack 후 다음 update가 오므로 1틱 = 1 update. 규격: VDA 5050 (GitHub).

Isaac Sim · USDNVIDIA Omniverse 물리 시뮬레이터

NVIDIA의 고정밀 로봇 시뮬레이터. RTX 레이트레이싱 렌더링과 정밀 물리를 제공하고, 씬은 픽사의 3D 표준 포맷 USD로 기술한다. 가벼운 대안이 Gazebo, 같은 생태계의 합성 데이터 도구가 Replicator, 강화학습 프레임워크가 Isaac Lab.

이 프로젝트에서 — 검증 런(⑤)의 본체. T3 창고 씬(USD) 위에 amr-agent를 N대 스폰해 DES 결과가 실제 스택에서 성립하는지 확인한다. RTX 5080에서 구동하며 규모 상한은 RTF 실측으로 정한다. 셋 다 v1에서는 쓰지 않는다(비전 AI·물리 RL 없음). 병렬 실행 실측은 Isaac 병렬 실측.

RTFReal-Time Factor — 실시간 배율

시뮬레이션 속 시간이 현실 시간보다 얼마나 빠르게 또는 느리게 흐르는지의 비율(시뮬 경과 ÷ 실제 경과). 로봇·센서를 많이 넣을수록 떨어지고, 너무 낮으면 실시간을 가정한 상위 시스템(관제·타임아웃)이 오작동한다.

이 프로젝트에서 — RTX 5080 기준 "RTF ≥ 0.9를 유지하는 최대 AMR 대수"를 실측해 검증 런 규모를 정한다. 수백 조합 스윕은 DES가, 소수 정밀 검증은 Isaac이 맡는 분업의 근거가 되는 숫자다. 배리어 틱은 가장 늦은 로봇을 기다리므로 RTF가 떨어지면 틱 길이도 늘어난다.

SILSoftware-in-the-Loop — 실제 소프트웨어를 루프에 넣은 검증

실물 없이 배포될 소프트웨어 스택을 시뮬레이터에 그대로 물려 돌리는 검증 방식. "테스트한 코드가 곧 배포되는 코드"라 sim-to-real 전환 때 소프트웨어를 안 바꾼다.

이 프로젝트에서 — 검증 런(⑤)의 정체성. 결정 커널+MQTT 데몬이 VDA 5050 order를 내리면 T4 에이전트(ROS 2)가 Isaac 속 가상 AMR을 실제 스택 그대로 구동한다. VDA 5050 경계 위 코드는 가상↔현실 전환 시 불변 — v1에 실물이 없으므로 정확히는 sim-to-sim(DES↔Isaac 정합성 비교)이다. 안내는 SIL 가이드, 현황은 T3·T4 진행.

sim-runnerSim Runner — GPU 서버의 검증 런 실행 데몬

GPU 서버에 상주하며 런 오케스트레이터의 start/go/stop 명령을 받아 Isaac Sim과 로봇 에이전트를 띄우고, 끝나면 산출물을 올리는 데몬.

이 프로젝트에서 — EC2의 오케스트레이터는 GPU 서버에 직접 들어갈 수 없어 EMQX의 sim/control(Sparkplug B)로 명령을 보낸다. sim-runner가 Isaac 씬을 열고 amr-agent(ROS 2)를 N대 스폰하며, 런 중 하트비트·시뮬 시각을 보고하고, 종료 후 MP4·리플레이·히트맵을 presigned URL로 MinIO에 올려 키를 돌려준다. 홈서버는 tailscale 아웃바운드로 EC2에 붙는다. 시뮬 파트 담당, 미완.

풀필먼트 프로세스Fulfillment — 입고에서 출고까지

주문을 받아 상품이 고객에게 나가기까지 물류센터 안의 전 과정. 입고 → 적치 → 보관 → 피킹 → 검수 → 패킹 → 분류 → 출고. 파생 용어: SKU(재고 관리 최소 단위), 웨이브(주문 묶음 배치 단위), 슬로팅(상품–로케이션 배치 전략).

이 프로젝트에서 — 이 흐름 가운데 입고·출고 반송과 피킹 보조 구간이 v1 견적 대상이다(기준선 v3 §4.5). 고객 WMS의 주문 로그(주문시각/주문ID/SKU/수량)에서 뽑은 수요 프로파일이 시나리오 패키지의 일부(②)가 된다. 선반이 사람에게 오는 방식은 GTP.

WMS · WES · WCS물류센터의 소프트웨어 계층

물류센터 소프트웨어의 3층 — WMS는 "무엇이 어디에 얼마나"(재고·주문 장부), WES는 "지금 누가 무엇을"(작업 오케스트레이션), WCS는 "설비를 어떻게"(컨베이어·소터 제어). 제조의 ISA-95 계층·MES 실행 기능에 대응하는 물류 버전이다.

이 프로젝트에서 — 고객 WMS는 주문 로그의 출처(입력원)다. 프로젝트 안의 WMS는 둘 — 검증 런용 시뮬 WMS(Spring + H2)와 DES용 WMS 라이트(확률 모델). 배차(WES 역할)는 FMS 결정 커널 안에 있다. 고객 WMS API 직접 연동과 ISA-95/OPC UA 통합은 후속.

AMR vs AGVAutonomous Mobile Robot · Automated Guided Vehicle

AGV는 바닥의 자기 테이프·QR 등 정해진 선로만 따라가는 운송 로봇(기차), AMR은 지도와 센서로 스스로 경로를 계획하는 운송 로봇(택시). 레이아웃 변경에 유연하고 사람과 공존해 AGV를 대체 중이며, 소프트웨어 비중이 크다.

이 프로젝트에서 — v1 견적 대상은 반송/피킹 보조 AMR — 인프라 변경 없이 3~15대를 점진 도입하는 세그먼트라 "견적 의사결정"이 실제로 일어난다. 검증 기종은 iw.hub 메인+MiR 250 서브(기준 기종 선정). 경로 문제는 MAPF, 관제–로봇 통신은 VDA 5050.

GTPGoods-to-Person — 물건이 사람에게 오는 방식

작업자가 선반으로 걸어가는 대신 로봇이 선반·토트를 작업자 앞까지 가져다주는 창고 자동화 방식(원형은 Amazon Kiva). 전용 선반·스테이션·관제까지 통째로 새로 까는 대규모 공사라 벤더 턴키 거래로 이뤄진다.

이 프로젝트에서 — v1 범위 밖 카테고리(기준선 v3 §4.5). 시장 매출 1위 세그먼트(약 38%)이지만 턴키 구매 구조 때문에 제3자 중립 견적이 끼어들 틈이 좁다 — "왜 시장 1위를 안 했나"의 답이 이 논리다. GTP가 더 맞는 고객은 검토 단계(②)에서 운영자가 사유와 함께 안내한다.

이산사건 시뮬레이션 · SimPyDiscrete Event Simulation

시간을 연속으로 흘리지 않고 "사건에서 다음 사건으로 점프"하며 대기열·처리량·병목을 계산하는 시뮬레이션(SimPy는 그 Python 라이브러리). 물리 시뮬이 "로봇이 어떻게 움직이는가"에 답한다면 DES는 "센터 전체가 얼마나 잘 흘러가는가"에 답한다.

이 프로젝트에서 — 서비스 흐름 ④의 계산 엔진. 기종 × 대수 × 시드 스윕을 trial 단위로 수백 번 돌려 대수–처리량 곡선을 만든다. 현재(기준선 v3, 2026-09-03) DES의 실체는 팀의 틱 시뮬(sim_v2)이고 이동 계층은 PIBT 헤딩 모델이며, SimPy 전환은 후속이다. 검산 짝은 Little's Law.

Little's Law리틀의 법칙 — L = λW

안정 상태의 어떤 시스템이든 "안에 머무는 평균 개수(L) = 도착률(λ) × 평균 체류시간(W)". 시간당 100건 도착·평균 0.5시간 체류면 안에는 언제나 평균 50건이 처리 중이어야 한다. 분포·정책과 무관하게 성립하므로 세 숫자가 안 맞으면 모델에 버그가 있는 것이다.

이 프로젝트에서 — 시뮬레이션 검증(V&V)의 1차 관문. DES 결과에서 재공 수량·처리율·리드타임을 뽑아 등식 성립을 확인하는 것이 VDI 3633 verification 활동의 구체적 실행이다.

VDI 3633시뮬레이션 프로젝트의 절차·검증 지침

물류·생산 시스템 시뮬레이션의 절차와 검증 방법을 정리한 독일엔지니어협회(VDI) 지침. 모든 가정을 명시하고, 모델을 올바르게 구현했는지(Verification)와 현실을 닮았는지(Validation)를 별도 활동으로 검증하며 문서로 남기라는 것이다.

이 프로젝트에서 — "투명한 견적" 주장의 표준 준거. 보존 법칙 체크와 Little's Law 검산이 Verification, MAPF 공개 벤치마크 대조와 DES vs Isaac 검증 런 오차 비교가 Validation이다. 가정 명세서를 리포트 부록으로 공개하는 것이 이 지침의 실천.

디지털 트윈Digital Twin

실제 설비·센터의 상태를 반영하는 가상 복제본. 단순 3D 모형과의 차이는 데이터 동기화 — 현실의 측정값으로 계속 보정되고, 트윈의 실험 결과가 현실 의사결정에 반영되는 양방향 고리(감지 → 판정 → 조치의 폐루프)가 있어야 트윈이다.

이 프로젝트에서 — Isaac 검증 런(⑤)의 실측 — 회전 시간 상수·구간 주행 시간 — 을 DES(④) 모델에 되먹이는 보정 루프가 이 구조다. 물리 시뮬과 틱 시뮬이 서로를 보정하는 2계층이 본 프로젝트의 디지털 트윈 해석이며, 산업계의 물리 + DES 하이브리드 구조와 같다.

TCO · ROITotal Cost of Ownership · Return on Investment

TCO는 구매비에 운영·유지보수·충전 인프라까지 합친 총소유비용, ROI는 투자가 언제 얼마나 돌아오는지의 수익률. TCO 곡선을 겹치면 "목표 처리량의 최소 대수"와 "ROI 최대 대수" 두 최적점이 드러난다.

이 프로젝트에서 — 리포트(⑦)의 핵심 화면. 대수–처리량 곡선에 TCO를 중첩해 ROI 최적점을 표시하고, 곡선을 클릭하면 그 구성의 상세 리포트가 열린다. 둘 다 제시하고 선택은 고객에게 맡긴다 — "선택은 고객이, 근거는 시스템이". 중심 지표는 시간당 처리량·주문 리드타임·로봇 가동률(ISO 22400 준거, OEE는 참고 배경).

웹 인프라 2층Two-tier Web Infrastructure — 상시 층과 런 단위 층

늘 떠 있는 견적 서비스 층과, 런마다 만들었다 없애는 시뮬 스택 층으로 나눈 구조. 원칙은 "영속은 견적 도메인, 휘발은 시뮬 도메인".

이 프로젝트에서 — 상시 층: React 웹 콘솔·nginx(:443 단일 인그레스)·견적 BE(Spring Boot)·PostgreSQL·RabbitMQ·MinIO·EMQX. 런 단위 층: 시뮬 WMS(Spring+H2)·FMS 코어(Python)·수요 생성기 — 런이 끝나면 파드째 삭제. 런 하나가 죽어도 견적 데이터는 안전하다. 두 층 모두 EC2 t3.xlarge의 k3s 위. 다이어그램 원본은 FMS-WMS 통합 아키텍처 v3.10.

k3sk3s — 경량 Kubernetes

단일 노드에서도 가볍게 도는 Kubernetes 배포판. EC2 t3.xlarge 한 대 위에서 상시 서비스와 런 단위 파드를 모두 돌린다.

이 프로젝트에서 — 기관 EC2는 IAM이 없어 관리형 AWS 서비스를 못 쓰므로 전부 자체 호스팅이다. k3s 위에 견적 서비스 파드, EMQX, RabbitMQ, MinIO, 시뮬 스택 파드, 계산 엔진 Job, 런 오케스트레이터가 올라간다. 이미지는 GHCR, 인증서는 certbot. 실행 환경 상세는 시스템 아키텍처 — 실행 환경. 공식 문서: k3s Docs.

EMQXEMQX — MQTT 브로커

본 프로젝트의 MQTT 브로커. 런 제어·텔레메트리(Sparkplug B), AMR 제어(VDA 5050), 주문·이벤트(biz/v1 JSON)가 지나가는 상시 채널이다.

이 프로젝트에서 — 메시징은 두 갈래 — RabbitMQ(AMQP)는 잡과 결과 이벤트를, EMQX(MQTT)는 제어와 상태를 맡는다. Kafka는 쓰지 않는다. EMQX는 상시 파드로, 런이 뜨기 전에 제어 채널이 먼저 있어야 한다. FMS 쪽 소비자는 실행 셸의 MQTT 데몬. 구축 절차는 MQTT 백본 구축 가이드. 공식 문서: EMQX Docs.

MQTT경량 발행/구독 메시징 프로토콜

IoT·제조 현장의 표준 메시징 프로토콜. 모든 참여자가 중앙 브로커에 연결해 토픽 이름으로 발행·구독한다. HTTP가 "요청하면 응답"(1:1)이라면 MQTT는 "일어난 일을 방송"(1:N). 페이로드는 정하지 않으므로 그 위에 Sparkplug B·VDA 5050 같은 표준이 얹힌다.

이 프로젝트에서 — 검증 트랙의 전송 계층(브로커는 EMQX, MQTT 3.1.1). 페이로드는 셋으로 나뉜다 — 런 제어·텔레메트리·세션은 Sparkplug B, AMR 제어는 VDA 5050 JSON, 주문·이벤트는 biz/v1 JSON. 상세는 MQTT 백본 구축 가이드.

Sparkplug BSparkplug B 3.0 — MQTT 위의 산업 텔레메트리 규약

MQTT 위의 산업 텔레메트리 규약. spBv1.0 네임스페이스, protobuf 페이로드, NBIRTH/NDEATH 세션·STATE로 "어느 노드가 지금 살아 있는가"를 프로토콜 차원에서 답한다.

이 프로젝트에서 — 런 제어(sim/control)·sim-runner 텔레메트리·세션 수명에만 쓴다. AMR 제어는 VDA 5050, 주문·이벤트는 biz/v1 JSON. 상세는 MQTT 백본 구축 가이드.

VDA 5050AMR 군집 통신 표준

중앙 관제와 AMR들이 주고받는 메시지를 표준화한 규격(독일 자동차공업협회). 관제가 경로를 노드·엣지 그래프로 내려주고(order) AMR이 상태를 보고한다(state). 관제는 "어디로", 로봇은 "어떻게"로 책임이 나뉜다. IT(관제)와 OT(로봇)를 잇는 경계 표준.

이 프로젝트에서 — 실행 셸의 MQTT 데몬이 커널의 decisions를 order로 발행하고, T4 에이전트의 브리지가 그리드 프리미티브로 실행한 뒤 state를 보고한다(v2.0, order/state/connection+instantActions). 틱마다 다음 1칸을 released로 내리는 스티칭 방식. 이 경계 위 코드는 가상↔현실 전환 시 불변 — v2 실관제 확장이 아키텍처에 내장된다는 주장의 근거.

MinIOMinIO — S3 호환 오브젝트 저장소

S3 API를 그대로 쓰는 자체 호스팅 오브젝트 저장소. 아티팩트(MP4·리플레이·히트맵·로그)와 시나리오 파일을 보관한다.

이 프로젝트에서 — 기관 EC2는 IAM을 못 써 관리형 S3 대신 k3s 파드로 올렸다. 클라이언트 코드는 S3 SDK 그대로라 계정 제약이 풀리면 버킷만 S3로 옮기면 된다. 상시 층 소속. 업로드는 presigned URL, 내용물은 아티팩트. 공식 문서: MinIO Docs.

H2H2 Database — 자바 인메모리 DB

JVM 안에서 도는 경량 관계형 DB. 시뮬 WMS가 런 스코프 데이터를 여기에 두고 런이 끝나면 함께 버린다.

이 프로젝트에서 — 런마다 깨끗한 DB가 필요한데 PostgreSQL을 런마다 만들고 지우는 것보다 인메모리가 간단하다. 조건은 JPQL만 쓰고 네이티브 쿼리 금지, PG 호환 모드 — 그래야 프로파일만 바꿔 PostgreSQL로 승격할 수 있다. 영속이 필요한 이벤트 로그는 H2 밖(JSONL → MinIO). 사용자는 시뮬 WMS 하나, 영속 데이터는 PostgreSQL(견적 도메인)에만 둔다. 공식 문서: H2 Database.
