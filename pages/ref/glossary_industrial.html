IT/OT 융합Smart Factory · Smart Logistics Convergence

설비·로봇이 만드는 현장 데이터(OT)와 기업 정보 시스템(IT)을 연결해, 현장이 스스로 상태를 보고하고 지시를 받는 체계. 공장이든 물류센터든 "IT와 OT의 융합"이 본질이다.

OT(Operational Technology)는 물리 세계를 직접 움직이는 기술이고, IT는 정보를 다루는 기술이다. 두 세계는 쓰는 프로토콜·시간 단위·안정성 요구가 완전히 달라서 오랫동안 분리되어 있었다. 스마트팩토리·스마트 물류센터는 이 사이에 표준화된 데이터 파이프라인을 놓아 "현장에서 일어나는 일"을 실시간으로 위(경영·분석)까지 올리고, "위의 결정"을 현장까지 내리는 것이다.

이 프로젝트에서 — IT(견적 서비스의 웹·백엔드·계산 엔진)와 OT(가상 AMR·Isaac Sim)를 VDA 5050(MQTT 위 JSON) 표준으로 잇는다. 물리 계층만 가상일 뿐 그 위의 소프트웨어는 실제 배포될 스택 그대로다. 이것이 검증 트랙(SIL)의 요지다(기준선 v3 §5).

풀필먼트 프로세스Fulfillment — 입고에서 출고까지

주문을 받아 상품이 고객에게 나가기까지 물류센터 안에서 일어나는 전 과정. 입고 → 적치 → 보관 → 피킹 → 검수 → 패킹 → 분류 → 출고로 이어진다.

핵심 파생 용어: SKU(Stock Keeping Unit — 재고 관리의 최소 단위, "품목 한 종류"), 웨이브(주문 여러 건을 묶어 한 번에 처리하는 배치 단위), 슬로팅(어떤 상품을 어느 로케이션에 둘지 정하는 배치 전략 — 잘 하면 이동 거리가 급감), Goods-to-Person(작업자가 선반으로 걸어가는 대신 AMR이 선반/토트를 작업자·로봇 앞으로 가져오는 방식 — Amazon Kiva가 대중화).

이 프로젝트에서 — 고객 창고의 이 흐름 가운데 반송/피킹 보조 구간이 v1 견적 대상이다(개괄 §2). 고객이 올린 주문 로그(엑셀 템플릿)에서 이 흐름의 수요 프로파일을 자동 추출하는 것이 인테이크 T2다(개괄 §5).

ISA-95제조 시스템의 계층 표준

공장의 소프트웨어를 5개 층(L0~L4)으로 나누는 국제 표준. 아래로 갈수록 물리에 가깝고 빠르며(마이크로초), 위로 갈수록 경영에 가깝고 느리다(일 단위).

웹의 프론트–백–DB 계층처럼, 제조 SW에도 표준 계층이 있다. 각 층은 바로 위·아래하고만 대화하는 것이 원칙이며, 이 규율이 시스템을 교체 가능하게 만든다. 면접·실무에서 제조 IT를 논할 때의 공용어이기도 하다.

이 프로젝트에서 — 계층적 사고의 참고 틀. v1 제품은 실시간 통합이 아닌 분석 서비스라 ISA-95/OPC UA 통합은 v2 백로그다(개괄 §10). 검증 트랙에서는 L1~2 자리에 Isaac Sim + Nav2가, 그 위에 VDA 5050 경계가 놓인다.

WMS · WES · WCS물류센터의 소프트웨어 계층

물류센터 소프트웨어의 3층 구조. WMS는 "무엇이 어디에 얼마나"(재고·주문의 장부), WES는 "지금 누가 무엇을"(작업 오케스트레이션), WCS는 "설비를 어떻게"(컨베이어·소터 제어)를 담당한다.

제조의 MES(별도 항목)가 하던 역할이 물류에서는 WMS(장부)와 WES(실행)로 나뉜다. 최근 로봇 도입이 늘며 WES의 비중이 커지는 추세다 — 사람·AMR·소터에게 실시간으로 일을 나눠주는 계층이기 때문이다.

이 프로젝트에서 — v1은 WMS를 구현하지 않는다. 고객 WMS가 내보낸 주문 로그(자체 엑셀 템플릿: 주문시각/주문ID/SKU/수량)를 읽어 수요 프로파일을 추출하는 입력원이며(인테이크 T2), WMS API 직접 연동은 T3 로드맵이다(개괄 §5).

MESManufacturing Execution System — 생산 실행 시스템

"오늘 무엇을 몇 개 만들지"(작업지시)를 받아 현장에 배분하고, 실제로 몇 개가 만들어졌는지(실적)를 집계하는 공장 운영의 두뇌.

이커머스의 주문 관리 시스템(OMS)과 구조가 유사하다. 주문(작업지시)이 들어오면 → 처리 가능한 자원(스테이션·로봇)에 할당하고 → 진행 상태를 추적하고 → 완료 실적을 집계한다. 실무 MES는 거대한 패키지 소프트웨어지만, 핵심 로직(작업지시 라이프사이클 + 자원 할당 + 실적 집계)은 웹 백엔드 기술로 충분히 구현 가능하다.

이 프로젝트에서 — 제조 도메인의 개념 참고용 항목. 본 프로젝트는 물류센터 대상 분석 서비스라 MES가 직접 등장하지 않지만, "지시 접수 → 자원 할당 → 실적 집계"라는 구조는 시뮬레이션이 흉내내는 창고 운영의 뼈대와 같다.

디지털 트윈Digital Twin

실제 공장·설비의 상태를 반영하는 가상 복제본. 현실을 관찰하는 거울이자, "이렇게 바꾸면 어떻게 될까"를 미리 실험해 보는 공간이다.

단순 3D 모형과의 차이는 데이터 동기화다. 진짜 디지털 트윈은 현실의 측정값(사이클 타임·고장률)으로 계속 보정되고, 반대로 트윈에서의 실험 결과(배차 정책 변경, 설비 증설)가 현실 의사결정에 반영된다. 산업계에서는 물리 시뮬레이션과 통계 모델(이산사건 시뮬레이션)을 결합한 하이브리드 구조가 표준적이다.

이 프로젝트에서 — Isaac 에뮬레이션에서 실측한 엣지 주행시간을 SimPy 모델의 유효속도 계수로 되먹이는 보정 루프(개괄 §4)가 정확히 이 구조다. 물리 시뮬과 통계 시뮬이 서로를 보정하는 2계층이 본 프로젝트의 디지털 트윈 해석이다.

이산사건 시뮬레이션 · SimPyDiscrete Event Simulation

시간을 연속으로 흘리지 않고 "사건에서 다음 사건으로 점프"하며 공장의 흐름(대기열·처리량·병목)을 계산하는 시뮬레이션. SimPy는 이를 위한 Python 라이브러리다.

물리 시뮬레이션이 "로봇이 어떻게 움직이는가"에 답한다면, DES는 "센터 전체가 얼마나 잘 흘러가는가"에 답한다. AMR을 3대에서 4대로 늘리면 처리량이 얼마나 오르는지, 어느 스테이션이 병목인지 같은 질문은 DES로 수천 번 돌려 통계로 확인한다. 물류센터는 DES의 대표 적용 분야다. 창고 설계·운영 분석의 표준 방법론이 바로 이것이다. 시뮬레이션 결과가 말이 되는지 검산하는 짝꿍 도구는 Little's Law다.

이 프로젝트에서 — SimPy DES가 견적 엔진의 본체다. 기종 × 대수 × 시드 스윕을 K8s에서 수백 런 병렬 실행하고, 내장 경량 MAPF(틱 기반, 1틱=1셀)가 경합을 만들어 대수–처리량 곡선의 모양을 결정한다(개괄 §4·8). 현재(기준선 v3, 2026-09-03) DES의 실체는 팀의 틱 시뮬(sim_v2)이고, SimPy는 후속 계획이다.

Little's Law리틀의 법칙 — L = λW

안정 상태의 어떤 시스템이든 "안에 머무는 평균 개수(L) = 도착률(λ) × 평균 체류시간(W)"이 성립한다는 대기행렬 이론의 기본 법칙.

숫자로 보면 단순하다. 주문이 시간당 100건 도착하고(λ=100건/시간) 주문 하나가 창고 안에 평균 0.5시간 머문다면(W=0.5시간), 창고 안에는 언제나 평균 L = 100 × 0.5 = 50건이 처리 중이어야 한다. 분포·순서·정책과 무관하게 거의 모든 안정 시스템에 성립하기 때문에, 시뮬레이션이 뱉은 세 숫자(재공 수량·처리율·리드타임)가 이 등식을 만족하는지만 봐도 모델의 버그를 즉시 잡아낼 수 있다.

이 프로젝트에서 — 시뮬레이션 검증(V&V)의 1차 관문. SimPy 결과에서 L·λ·W를 뽑아 등식 성립을 확인하는 것이 VDI 3633 verification 활동의 구체적 실행이다(TECH 04 I1).

VDI 3633시뮬레이션 프로젝트의 절차·검증 지침

물류·생산 시스템 시뮬레이션을 어떤 절차로 수행하고 어떻게 검증해야 하는지를 정리한 독일엔지니어협회(VDI)의 공학 지침.

핵심 요구는 단순하다 — 모든 가정을 명시하고, 모델을 올바르게 구현했는지(Verification)와 모델이 현실을 닮았는지(Validation)를 별도 활동으로 검증하며, 그 과정을 문서로 남겨라. "시뮬레이션 결과를 왜 믿어야 하나"라는 질문에 표준의 언어로 답하게 해주는 장치다.

이 프로젝트에서 — "투명한 견적" 주장의 표준 준거(개괄 §10·11). 보존 법칙 체크와 Little's Law 검산이 Verification, MAPF 공개 벤치마크 대조와 SimPy vs 에뮬레이션 오차 비교가 Validation이다. 가정 명세서를 리포트 부록으로 공개하는 것이 이 지침의 실천이다.

MQTT경량 발행/구독 메시징 프로토콜

IoT·제조 현장의 표준 메시징 프로토콜. 모든 참여자가 중앙 브로커에 연결해, 토픽 이름으로 메시지를 발행(publish)하고 구독(subscribe)한다.

HTTP가 "요청하면 응답"(1:1, 클라이언트가 물어봐야 함)이라면, MQTT는 "일어난 일을 방송"(1:N, 상태가 바뀌면 즉시 전파)이다. 헤더가 몇 바이트로 극단적으로 가볍고, 불안정한 네트워크를 견디도록 설계되어 제조·IoT의 사실상 표준이 됐다. 메시지 안에 뭘 담을지는 정하지 않기 때문에, 그 위에 Sparkplug B나 VDA 5050 같은 페이로드 표준이 얹힌다.

이 프로젝트에서 — 검증 트랙의 전송 계층. FMS의 VDA 5050 order·state가 MQTT(EMQX 브로커) 위로 흐르고, 런 제어(sim/control)도 같은 브로커를 쓴다(기준선 v3 §3.1·§5.1). Sparkplug B는 쓰지 않는다.

Sparkplug B설비 텔레메트리 페이로드 표준

MQTT 위에서 "설비 데이터를 어떤 토픽 구조와 형식으로 보낼 것인가"를 정한 산업 표준. 설비의 탄생·데이터·사망을 생애주기로 관리한다.

본 프로젝트에서는 쓰지 않는다(2026-08-20 폐기. 페이로드는 VDA 5050 JSON으로 통일). 참고용 설명만 남긴다. MQTT만 쓰면 팀마다 토픽 구조와 JSON 형식을 제각각 정하게 된다. Sparkplug B는 네임스페이스(spBv1.0/그룹/메시지타입/노드/디바이스), 데이터 형식(Protobuf), 상태 관리(BIRTH/DEATH)를 표준화해서, 처음 보는 설비도 구독만 하면 바로 해석할 수 있게 만든다. "설비가 지금 온라인인가"라는 제조 현장의 핵심 질문에 프로토콜 차원에서 답하는 것이 특징이다.

이 프로젝트에서 — 가상 AMR 텔레메트리에 적용한다. 제품 정체성이 "로봇을 움직이는 시스템"에서 "신뢰할 수 있는 분석"으로 이동하면서 역할은 얇아졌지만(개괄 §10, '축소'), 검증 트랙의 상태 스트림 표준으로 유지된다.

VDA 5050AMR 군집 통신 표준

중앙 관제(마스터 컨트롤)와 AMR들이 주고받는 메시지를 표준화한 규격. 관제가 경로를 노드·엣지 그래프로 내려주고(order), AMR이 상태를 보고한다(state).

독일 자동차공업협회(VDA)가 만든 표준으로, 서로 다른 제조사의 AMR을 하나의 관제로 묶기 위해 만들어졌다. 본래 물류·창고의 AMR 관제가 주 용도라, 물류센터 도메인에서는 중심 표준이다. 관제와 로봇의 책임 분리가 명확하다: 관제는 "어디로 갈지"(경로 그래프)를 정하고, 로봇은 "어떻게 갈지"(실제 주행·회피)를 알아서 한다. 공식 JSON 스키마가 공개되어 있어 웹 개발자에게도 친숙한 형태다. 관제가 내려줄 경로 자체를 계산하는 알고리즘 계열은 MAPF 참조.

이 프로젝트에서 — 플랫폼 코어가 order(노드/엣지 경로)를 발행하고, ROS2 어댑터가 이를 Nav2 구간 주행으로 실행한 뒤 state를 보고한다(v2.0, order/state/connection + instantActions). 이 경계선 위의 코드는 가상↔현실 전환 시 불변 — v2 실관제 확장이 아키텍처에 내장된다는 주장의 근거다(개괄 §4).

AMR vs AGVAutonomous Mobile Robot · Automated Guided Vehicle

AGV는 바닥의 자기 테이프·QR 등 정해진 선로만 따라가는 운송 로봇, AMR은 지도와 센서로 스스로 경로를 계획하고 장애물을 피하는 운송 로봇이다.

AGV는 기차(선로 이탈 불가), AMR은 택시(목적지만 주면 알아서 감)에 비유된다. AMR은 레이아웃 변경에 유연하고 사람과 공존할 수 있어 물류·제조 현장에서 빠르게 AGV를 대체하는 중이다. 그만큼 소프트웨어(위치 추정·경로 계획·군집 관제)의 비중이 압도적으로 커진다. 여러 대의 경로를 부딪히지 않게 함께 푸는 문제는 MAPF, 관제와 로봇 사이의 통신 표준은 VDA 5050 참조.

이 프로젝트에서 — v1 견적 대상이 반송/피킹 보조 AMR 카테고리다(개괄 §2). 인프라 변경 없이 3~15대를 점진 도입하는 세그먼트라 "견적 의사결정"이 실제로 일어난다. 검증 기종은 iw.hub 메인 + MiR 250 서브이며, 시뮬레이션 안에서 여러 대의 경합이 대수–처리량 곡선의 모양을 만든다.

GTPGoods-to-Person — 물건이 사람에게 오는 방식

작업자가 선반으로 걸어가는 대신, 로봇이 선반·토트를 작업자 앞까지 가져다주는 창고 자동화 방식. Amazon Kiva 시스템이 원형이다.

사람의 이동 시간을 없애 피킹 생산성을 크게 올리지만, 전용 선반·스테이션·관제 소프트웨어까지 통째로 새로 까는 대규모 공사가 필요하다. 그래서 GTP 도입은 벤더가 설계부터 견적까지 도맡는 턴키(turn-key) 거래로 이뤄진다. 시장 매출 1위 세그먼트(약 38%)이지만, 바로 그 구매 구조 때문에 제3자 중립 견적이 끼어들 틈이 구조적으로 좁다.

이 프로젝트에서 — v1 범위 밖 카테고리(기준선 v3 §4.5: 입고·출고 반송과 피킹 보조가 범위). GTP가 더 맞는 고객은 검토 단계(②)에서 운영자가 사유와 함께 안내한다. "왜 시장 1위를 안 했나"라는 발표 예상 질문의 답이 이 구매 경로 논리다. GTP 전용 공정 모델은 후속.

Andon안돈 — 이상 알림 체계

생산 라인에 이상이 생기면 즉시 불빛·알림으로 알려 대응을 촉구하는 체계. 도요타 생산방식에서 나온 용어로, 현장 위 신호등이 원형이다.

핵심 사상은 "문제를 숨기지 말고 그 자리에서 드러내라"다. 현대의 스마트 공장·물류센터에서는 물리적 경광등을 넘어 대시보드 알림·모바일 푸시로 확장됐다. 웹 서비스의 장애 알림(PagerDuty·Slack 알림)과 정확히 같은 역할이다.

이 프로젝트에서 — 직접 구현 범위 밖의 참고 개념. 스윕 실행 화면에서 잡 실패·부분 실패를 숨기지 않고 "미완료 조합"으로 드러내는 정책(TECH 04 E3)이 같은 사상 — 문제를 숨기지 말고 그 자리에서 보여라 — 을 따른다.

OEEOverall Equipment Effectiveness — 설비종합효율

설비가 "이론상 최대치 대비 실제로 얼마나 가치를 만들었나"를 하나의 숫자로 나타내는 제조업 대표 KPI. 가용성 × 성능 × 품질로 계산한다.

예를 들어 가용성 90% × 성능 85% × 품질 95% = OEE 72.7%. 세계적 수준의 공장이 85% 정도다. 단순 가동률보다 강력한 이유는 "돌고는 있는데 느리게 돈다", "빨리 도는데 불량을 만든다" 같은 숨은 손실이 다 드러나기 때문이다.

이 프로젝트에서 — 리포트 KPI의 참고 배경. 본 서비스 리포트의 중심 지표는 시간당 처리량·주문 리드타임·로봇 가동률이며, KPI 정의는 ISO 22400을 준거로 삼아 용어 혼선을 막는다(개괄 §10).

TCO · ROITotal Cost of Ownership · Return on Investment

TCO는 구매비뿐 아니라 운영·유지보수·충전 인프라까지 합친 총소유비용. ROI는 그 투자가 언제, 얼마나 이익으로 돌아오는지의 수익률이다.

로봇을 더 넣으면 처리량은 늘지만 체감하며 늘고, 비용은 대수에 거의 비례해 늘어난다. 처리량 곡선 위에 TCO 곡선을 겹치면 서로 다른 두 최적점이 드러난다 — "처리량 목표를 만족하는 최소 대수"와 "ROI가 최대가 되는 대수". 어느 쪽을 고를지는 고객의 경영 판단이다.

이 프로젝트에서 — 리포트의 핵심 화면(개괄 §7). 대수–처리량 곡선에 TCO를 중첩해 ROI 최적점을 표시하고, 곡선 위를 클릭하면 그 구성의 상세 리포트가 열린다. 두 최적점을 모두 제시하고 선택은 고객에게 맡긴다 — "선택은 고객이, 근거는 시스템이".

폐루프 품질관리Closed-Loop Quality

검수 결과가 사람 손을 거치지 않고 곧바로 물류 흐름의 변화(예외품 격리·재피킹 지시)로 이어지는 구조. "감지 → 판정 → 조치"의 고리가 자동으로 닫힌다.

많은 데모가 "AI가 문제를 찾았다"에서 끝난다(열린 루프). 진짜 스마트 물류센터의 가치는 그 판정이 자동으로 조치까지 이어지는 데 있다. 시스템 전 계층(비전 → AI → WMS → 배차 → 로봇)이 실제로 연결되어야만 가능하므로, 통합 완성도의 증명이기도 하다.

이 프로젝트에서 — 품질관리 자체는 범위 밖이지만, "감지 → 판정 → 조치"가 자동으로 닫히는 구조는 본 프로젝트의 보정 루프와 동형이다: 에뮬레이션 실측(감지) → SimPy 유효속도 계수 갱신(판정) → 재스윕(조치)의 고리가 자동으로 닫힌다(개괄 §4).

요청 접수형 서비스Intake Service — 요청을 받아 나중에 결과를 보내는 비동기 서비스

고객이 조건을 남기면 요청이 큐에 쌓이고, 운영자가 검토·검수한 뒤 결과를 나중에 발송하는 서비스 형태. 즉시 계산해 보여 주는 셀프서브 SaaS의 반대다.

본 프로젝트가 v3에서 택한 제품 형태다. 이유는 세 가지다. GPU가 1대라 검증 런을 줄 세워야 한다. 5분 숏런으로는 결과를 믿기 어렵다. 영상·리플레이를 견적서에 넣으려면 사람이 검수해야 한다. 흐름은 8단계다. 접수 → 운영 검토·시나리오 컴파일 → 스윕 잡 소비 → 구성 탐색·θ 추론·DES → Isaac 물리 검증 런 → KPI·아티팩트 → 리포트 작성 → 발송. 운영자가 개입하는 곳은 ②와 ⑦ 두 곳이다. 접수 시 큐 순번과 예상 소요를 회신한다.

이 프로젝트에서 — 기준선 v3 §0·§2. 제품 페이지는 PRODUCT Santa Factory 랜딩, 브라우저 체험판은 데모. 흐름 상세는 TECH 02 시스템 아키텍처.

웹 인프라 2층Two-tier Web Infrastructure — 상시 층과 런 단위 층

늘 떠 있는 견적 서비스 층과, 런마다 만들었다 없애는 시뮬 스택 층으로 나눈 구조. 원칙은 "영속은 견적 도메인, 휘발은 시뮬 도메인".

상시 층에는 React 웹 콘솔, nginx(:443 단일 인그레스), 견적 BE(Spring Boot), PostgreSQL, RabbitMQ, MinIO가 있다. 런 단위 층에는 시뮬 WMS(Spring + H2 인메모리), FMS 코어(Python), 수요 생성기가 있고, 런이 끝나면 파드째 사라진다. EMQX는 상시다. 제어 채널이 런보다 먼저 있어야 하기 때문이다. 이렇게 나누면 런 하나가 죽어도 견적 데이터는 안전하고, 런 상태가 영속 DB를 더럽히지 않는다.

이 프로젝트에서 — 기준선 v3 §3.1. 두 층 모두 EC2 t3.xlarge의 k3s 위에 올라간다(§3.2). 다이어그램 원본은 FMS-WMS 통합 아키텍처 v3.10.

런Run — Isaac 검증 런 한 번

시뮬 WMS·FMS 파드를 띄우고 Isaac Sim에서 로봇을 움직여 KPI와 산출물을 얻는 실행 단위 하나. 런 ID로 식별하고 상태기로 관리한다.

런은 분 단위 미니 시나리오다. Isaac이 실시간이라 하루치를 재생할 수 없다. 상태는 QUEUED → PROVISIONING → LOADING → RUNNING → COLLECTING → DONE 또는 FAILED로 흐른다. 런 ID 기준으로 멱등하게 처리해 재시도해도 두 번 세지 않는다. 실패는 DLQ로 보낸다. 한 trial에 검증 런은 0개 또는 1개다. 상위 구성만 GPU 런 큐에 올라가기 때문이다.

이 프로젝트에서 — 기준선 v3 §6·§8. 상태 전이는 런 오케스트레이터가 맡고, GPU 쪽 실행은 REF A sim-runner가 맡는다. 재현성 키는 시나리오 해시 + 시드.

trialTrial — 스윕 안의 구성 하나

스윕 잡 안에서 "대수 n · 기종 · 시드" 한 조합을 DES로 돌린 단위. 요청 1 : N 잡 1 : N trial 1 : 0..1 검증 런 계층의 가운데 칸이다.

요청 하나가 잡 여러 개로, 잡 하나가 trial 여러 개로 갈라진다. trial마다 AI 모델이 θ를 추론하고 FMS 커널이 가상 시간으로 돌며 시드를 바꿔 반복한다. trial의 KPI가 모여 대수–처리량 곡선이 된다. 곡선의 무릎(포화점)을 정하는 정지 규칙은 계산 엔진이 소유한다. 견적 BE는 대수 n을 반복 호출하지 않고 스윕 범위만 잡에 싣는다. 팀 백엔드↔AI API 초안의 요청·응답 스키마(run_id·seed·warehouse·amr·orders → kpi)는 trial 단위 어댑터 계약으로 채택했다.

이 프로젝트에서 — 기준선 v3 §3.3·§7. PostgreSQL 테이블 trial이 이 단위다. 상위 trial만 GPU 런 큐로 넘어가 런이 된다.

시나리오 패키지Scenario Package — 컴파일된 시뮬 입력 묶음

운영자가 요청을 정제해 만든 시뮬 입력 묶음. zones.json · 맵 · 주문 분해 규칙 · 수요 프로파일 · rack_id↔시뮬 좌표 매핑으로 구성된다.

서비스 흐름 ②에서 만들어진다. 이 묶음 하나를 두 소비자가 읽는다. DES의 WMS 라이트와 검증 런의 Spring 시뮬 WMS다. 같은 입력을 쓰므로 두 결과를 비교할 수 있다. 정합성은 골든 시나리오 패리티 테스트로 지킨다. 재현성 키는 시나리오 해시 + 시드다. 파일은 MinIO에 둔다.

이 프로젝트에서 — 기준선 v3 §4.4·§6. 시뮬 파트의 T3 창고 씬(sil/t3_warehouse_map/)이 zones.json·맵의 출처다. 소비자 둘은 WMS 라이트와 시뮬 WMS.

시뮬 WMSSimulation WMS — 검증 런용 실제 창고관리 서버

Isaac 검증 런 동안 실제로 주문을 만들고 작업을 나눠 주는 Spring Boot 서버. H2 인메모리 DB를 쓰고, 런이 끝나면 함께 사라진다.

검증 런은 실제 소프트웨어를 루프에 넣는 SIL이다. 그래서 WMS도 확률 모델이 아닌 진짜 서버로 돈다. 테이블은 run_context, zone, location, station, sku, inventory, order, order_line, task다. 작업 이벤트 로그는 H2 밖(JSONL → MinIO)에 쓴다. JPQL만 쓰고 네이티브 쿼리를 금지해, 프로파일만 바꾸면 PostgreSQL로 승격할 수 있다.

이 프로젝트에서 — 기준선 v3 §3.1·§7. 런 단위 층의 파드다. DES 쪽 짝은 WMS 라이트. 일반 WMS 개념은 WMS · WES · WCS.

WMS 라이트WMS Lite — DES 안의 확률 모델 WMS

DES(④) 안에서 주문 생성 · 라인 합침 · 배차 · 서비스 타이머만 확률 모델로 흉내 내는 경량 WMS.

DES는 수백 번 돌린다. 그때마다 Spring 서버를 띄울 수 없다. 그래서 WMS의 결정만 남기고 서버는 뺐다. 원칙은 "측정 대상은 공유, 환경은 모델링"이다. 측정 대상인 FMS 커널은 검증 런과 같은 코드이고, 환경인 WMS는 모델이다. 같은 시나리오 패키지를 읽고, 골든 시나리오 패리티 테스트로 시뮬 WMS와 맞춘다.

이 프로젝트에서 — 기준선 v3 §4.4(C안). 현재 DES의 실체는 팀의 틱 시뮬(sim_v2)이며 WMS 라이트도 그 안에 있다. SimPy 전환은 후속(§6). 커널 쪽은 REF A 결정 커널.

런 오케스트레이터Run Orchestrator — 검증 런의 생애를 관리하는 파드

GPU 런 큐를 소비해 시뮬 스택 파드를 띄우고, sim-runner에 start/go/stop을 보내고, 산출물 키를 모아 결과 이벤트를 발행한 뒤 파드를 지우는 단일 파드.

순서는 정해져 있다. 큐 소비 → 시뮬 WMS·FMS 파드 기동(k8s API) → WMS 시나리오 주입 완료 대기 → sim-runner에 start/go(MQTT sim/control) → 하트비트·시뮬 시각 감시 → stop → 아티팩트 키 수집 → 결과 이벤트 발행·ack → 파드 삭제. 런 ID 기준 멱등이다. 실패는 DLQ로 보낸다. 재기동하면 조정 단계에서 떠 있는 파드와 큐 상태를 맞춘다.

이 프로젝트에서 — 기준선 v3 §8. EC2 k3s 위 단일 파드. GPU 쪽 짝은 REF A sim-runner. 런 상태기는 런 항목.

GPU 런 큐GPU Run Queue — 검증 런을 줄 세우는 큐

Isaac 검증 런을 GPU 수만큼만 동시에 돌리도록 직렬화하는 RabbitMQ 큐. 소비자 수 = GPU 수다.

큐잉은 2단이다. 1단 요청 잡 큐는 CPU 워커 N개가 스윕 잡을 소비한다. 2단 GPU 런 큐는 검증 런만 받는다. 현재 GPU는 RTX 5080 1대라 소비자도 1개다. 큐 깊이가 곧 대기 순번이고, 런 평균 시간을 곱하면 ETA가 된다. 접수 시 회신하는 큐 순번·예상 소요의 근거가 이 큐다. GPU 노드를 늘리면 소비자를 늘리면 된다.

이 프로젝트에서 — 기준선 v3 §3.3. 확장 시나리오(임대 GPU, 큐 깊이 기반 오토스케일)는 §3.2. 실패 처리는 DLQ.

DLQDead Letter Queue — 처리 실패 메시지 보관 큐

정해진 횟수만큼 재시도해도 실패한 메시지를 따로 모아 두는 큐. 실패를 버리지 않고 사람이 볼 수 있게 남긴다.

RabbitMQ에서 소비자가 메시지를 거부(nack)하거나 TTL이 지나면 dead-letter 교환기로 넘어간다. 본 프로젝트는 요청 잡 큐와 GPU 런 큐 둘 다 DLQ를 둔다. 재시도 횟수를 넘긴 스윕 잡, 파드 기동에 실패한 런이 여기에 남는다. 운영자는 웹 콘솔에서 DLQ를 보고 재투입하거나 요청을 종료한다. 공식 문서: RabbitMQ Dead Letter Exchanges.

이 프로젝트에서 — 기준선 v3 §2③·§3.3·§8. 런 ID 멱등과 짝을 이룬다. 재투입해도 두 번 세지 않는다.

아티팩트Artifact — 런이 남기는 산출 파일

검증 런이 만드는 파일들. 배속 영상(MP4) · 리플레이(JSON) · 히트맵(PNG) · 로그. MinIO에 저장하고, 메타는 PostgreSQL artifact 테이블에 둔다.

견적서에 들어가는 실물이다. 영상은 고객이 결과를 눈으로 확인하는 용도, 리플레이는 브라우저에서 다시 돌려 보는 용도, 히트맵은 정체 구간을 보는 용도다. 시나리오 파일도 같은 저장소에 둔다. 작업 이벤트 로그(JSONL)도 여기로 온다. 업로드는 sim-runner가 presigned URL로 직접 한다.

이 프로젝트에서 — 기준선 v3 §2⑥·§7. 리포트(⑦)에 임베드된다. 저장소는 MinIO, 업로드 방식은 presigned URL.

presigned URLPre-signed URL — 기한부 서명 업로드·다운로드 주소

서버가 미리 서명해 준 S3 호환 주소. 이 주소를 가진 쪽은 자격 증명 없이 정해진 시간 동안 특정 키에 PUT 또는 GET을 할 수 있다.

GPU 서버의 sim-runner에 MinIO 계정을 심지 않기 위해 쓴다. 흐름은 세 단계다. 견적 BE가 런 ID별 키로 PUT용 URL을 발급한다. sim-runner가 그 URL로 파일을 직접 올린다. 결과 이벤트에 키를 실어 보낸다. 고객 다운로드도 GET용 URL로 같은 방식이다. S3 API를 그대로 따르므로 MinIO를 S3로 바꿔도 코드가 같다.

이 프로젝트에서 — 기준선 v3 §2⑥. 기관 EC2는 IAM을 못 써 S3 대신 MinIO를 쓴다. 올리는 쪽은 REF A sim-runner.

EMQXEMQX — MQTT 브로커

본 프로젝트의 MQTT 브로커. 런 제어(sim/control)와 로봇 상태·VDA 5050 메시지가 지나가는 상시 채널이다.

메시징은 두 갈래다. RabbitMQ(AMQP)는 잡과 결과 이벤트를, EMQX(MQTT)는 제어와 상태를 맡는다. Kafka는 쓰지 않는다. 도메인 이벤트는 AMQP 결과 이벤트로 충분하기 때문이다. EMQX는 상시 파드다. 런이 뜨기 전에 제어 채널이 먼저 있어야 한다. 공식 문서: EMQX Docs.

이 프로젝트에서 — 기준선 v3 §1·§3.1. MQTT 개념은 MQTT, 메시지 규격은 VDA 5050. FMS 쪽 소비자는 REF A 실행 셸의 MQTT 데몬.

MinIOMinIO — S3 호환 오브젝트 저장소

S3 API를 그대로 쓰는 자체 호스팅 오브젝트 저장소. 아티팩트와 시나리오 파일을 보관한다.

기관 EC2는 IAM을 못 쓴다. 관리형 S3 대신 k3s 파드로 MinIO를 올렸다. 클라이언트 코드는 S3 SDK 그대로다. 임대 GPU나 계정 제약이 풀리면 버킷만 S3로 옮기면 된다. 저장 대상은 MP4·리플레이·히트맵·로그·시나리오 파일이다. 공식 문서: MinIO Docs.

이 프로젝트에서 — 기준선 v3 §1·§7. 상시 층 소속. 업로드는 presigned URL, 내용물은 아티팩트.

H2H2 Database — 자바 인메모리 DB

JVM 안에서 도는 경량 관계형 DB. 시뮬 WMS가 런 스코프 데이터를 여기에 두고, 런이 끝나면 함께 버린다.

런마다 깨끗한 DB가 필요하다. PostgreSQL을 런마다 만들고 지우는 것보다 인메모리가 간단하다. 조건이 있다. JPQL만 쓰고 네이티브 쿼리를 금지하며 PG 호환 모드로 돈다. 그래야 프로파일만 바꿔 PostgreSQL로 승격할 수 있다. 영속이 필요한 이벤트 로그는 H2 밖(JSONL → MinIO)에 쓴다. 공식 문서: H2 Database.

이 프로젝트에서 — 기준선 v3 §3.1·§7. 사용자는 시뮬 WMS 하나다. 영속 데이터는 PostgreSQL(견적 도메인)에만 둔다.

k3sk3s — 경량 Kubernetes

단일 노드에서도 가볍게 도는 Kubernetes 배포판. EC2 t3.xlarge 한 대 위에서 상시 서비스와 런 단위 파드를 모두 돌린다.

기관 EC2는 IAM이 없어 관리형 AWS 서비스를 쓸 수 없다. 전부 자체 호스팅이다. k3s 위에 견적 서비스 파드, EMQX, RabbitMQ, MinIO, 시뮬 스택 파드, 계산 엔진 Job, 런 오케스트레이터가 올라간다. 이미지는 GHCR, 인증서는 certbot이다. 다이어그램의 Docker 배지는 k3s 파드를 뜻한다. 공식 문서: k3s Docs.

이 프로젝트에서 — 기준선 v3 §3.2·§3.4. 실행 환경 상세는 WORKING 실행 환경과 리소스.
