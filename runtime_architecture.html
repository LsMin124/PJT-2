SEC 00 · 한눈에

이 문서가 답하는 세 가지 질문

① 시스템이 실제로 몇 개의 프로세스로 구성되는가. ② 어느 경계에서 갈라 어느 기기에 배치하는가. ③ 그래서 RAM과 비용이 얼마나 드는가. 인프라·견적 논의를 하려면 팀 전원이 이 세 답을 같은 그림으로 공유해야 한다.

구조시뮬 섬(Isaac+ROS2)과 서비스 섬(FMS 이하) — 절단선은 VDA 5050/MQTT 하나뿐
견적서비스 경로는 GPU 없이 16GB 인스턴스 1대에 수용(추정 5~8GB)
물리Isaac+ROS는 홈서버 32GB 한 덩어리 — 갈라서 얻는 것이 없다

먼저, 자주 생기는 오해 세 가지

오해정정
"시뮬 안에서 ROS2 프로세스가 돈다"포함 관계가 아니라 동등한 참여다. Isaac은 ROS2 그래프에 붙는 프로세스 하나이고, Nav2·에이전트는 그 옆의 별도 프로세스다 → SEC 01
"FMS의 경로계획 = Nav2"경로계획은 두 층이다. 함대 조정(MAPF)은 자체 구현이 담당하고, Nav2는 로봇 1대의 추종·국지 회피만 담당한다 → SEC 02
"로봇을 컨테이너로 띄우면 무겁다"컨테이너·k8s의 격리 비용은 수 MB 수준으로 거의 0이다. 무게는 컨테이너 안에 넣는 스택이 결정한다 → SEC 04
SEC 01 · 프로세스 기초

ROS2에는 "안"이 없다 — 마스터 없는 피어들의 그래프

ROS2에는 ROS1의 roscore 같은 중심 런타임이 없다. 여러 개의 평범한 리눅스 프로세스가 DDS라는 공용 버스로 서로를 자동 발견하고 토픽·서비스로 통신할 뿐이다(ROS 2 Concepts). 그래서 무언가가 무언가 "안에서" 도는 그림 자체가 성립하지 않는다.

────────────── DDS 버스 (토픽 / 서비스 / TF) ────────────── │ │ │ [Isaac Sim 프로세스] [Nav2 프로세스들 ×N] [에이전트 프로세스 ×N] 물리·센서 담당 노드 경로 추종·국지 회피 VDA 5050 어댑터 (브리지 확장 내장) (로봇 1대당 1묶음) (로봇 1대당 1개)
참여자정체
Isaac SimROS2 그래프에 참여하는 프로세스 하나. 내부의 ROS2 브리지 확장이 노드 역할로 /clock·TF·센서 토픽을 발행하고 조인트 명령을 구독한다. 6.0은 브리지가 ROS2 라이브러리를 자체 내장해 시스템에 ROS2가 없어도 DDS로 통신한다(Isaac Sim Docs)
Nav2 · 에이전트Isaac 바깥의 별도 OS 프로세스. Isaac이 죽어도 살아 있다(토픽만 끊김) — 장애 격리와 리소스 합산이 별도로 성립하는 이유
올바른 문장"Isaac이 ROS2 그래프의 한 참여자(물리·센서 노드)로 붙고, 제어 스택은 별도 프로세스로 같은 호스트에서 돌며 DDS로 통신한다." 다이어그램을 그릴 때도 포함 박스(시뮬 ⊃ ROS)가 아니라 버스에 매달린 동등한 노드로 그린다.
SEC 02 · 경로계획 두 층

FMS의 최적화는 자체 구현, Nav2는 로봇 1대의 실행기

FMS 레벨 (함대)로봇 레벨 (개체)
하는 일작업 할당(디스패칭) + 다중 로봇 경로 조정 — MAPF, RHCR 윈도우, 충돌·교착 회피받은 경로의 물리적 수행 — 경로 추종, 국지 장애물 회피, 속도 명령 생성
구현자체 구현 이 프로젝트의 코어 자산 — DES 스윕과 SIL 검증이 같은 로직을 공유Nav2 SIL 검증 트랙에서만 등장
다루는 단위로봇 N대 전체 · 1m 셀 그리드 · 고정 틱로봇 1대 · 연속 공간 · 센서

Nav2는 태생이 로봇 1대의 내비게이션 스택이라 다중 로봇 조정 개념이 없다. 네임스페이스로 여러 대를 띄울 수는 있으나 서로의 경로를 모른 채 각자 계획할 뿐이어서, 교차로 교착·협로 양보를 풀지 못한다 — 그것이 FMS/MAPF 층이 존재하는 이유다.

VDA 5050이 이 분업을 프로토콜로 강제한다

VDA 5050의 order 메시지는 경로 자체(노드·엣지 시퀀스)를 담아 하달된다. "경로를 정하는 것은 중앙, 따라가는 것은 로봇"이 표준 수준에서 갈리며, 우리 설계의 중앙 하달 원칙(개괄)과 일치한다. 상용 AMR도 동일 구조다 — 온보드 내비와 FMS 트래픽 관리는 분리되고, 그 경계가 VDA 5050이다.

SIL 구현 주의Nav2의 글로벌 플래너를 살려두면 자체 최단 경로를 다시 계산해 FMS가 하달한 MAPF 경로와 충돌한다(중앙이 일부러 우회시킨 경로를 로봇이 질러가면 조정이 깨짐). FMS 경로를 웨이포인트로 주입(NavigateThroughPoses / FollowPath)하고 Nav2는 컨트롤러+로컬 코스트맵만 담당시킨다. 경로가 막히는 상황은 로봇이 재계획하지 않고 FMS에 보고해 중앙이 다시 푼다.
SEC 03 · 통신 경계

기기를 갈라도 되는 경계는 하나뿐이다

경계프로토콜트래픽 특성기기 분리
ROS2 ↔ IsaacDDS (공유메모리)/clock·TF·조인트 명령·라이다·카메라 — 고빈도·대용량(카메라 raw는 수백 Mbps급)금지 같은 호스트
로봇 어댑터 ↔ FMSVDA 5050 / MQTT주기 상태 보고 + order 하달 — 저대역·비동기절단선 ✂ WAN 가능
FMS 내부AMQP(RabbitMQ)·Kafka스윕 잡 큐·도메인 이벤트 — 서비스 섬 내부섬 내부에 유지
프론트 ↔ 백엔드REST / WebSocket견적 요청·결과 조회가능
DDS를 WAN에 태우면 안 되는 이유내용
디스커버리멀티캐스트 기반 상호 발견이라 tailscale·VPN 너머로는 그냥 붙지 않는다(디스커버리 서버 별도 구성 필요). 참가자 수가 늘면 디스커버리 트래픽이 O(N²)로 증가
대역폭센서 토픽이 회선을 포화시킨다. 같은 호스트에서는 공유메모리 전송으로 이 비용이 사라진다
시각 동기/clock 지터가 제어 품질을 흔든다
CPU 경합은 치명적이지 않다Isaac과 Nav2가 한 기기에서 CPU를 다투면 시뮬이 실시간보다 느려질 뿐이다. SIL은 use_sim_time으로 전부 /clock에 물려 있어 RTF가 0.5×로 떨어져도 결과의 정합성은 유지된다 — 검증 트랙에 실시간성은 요구사항이 아니다.

SEC 05 · 배치 토폴로지

시뮬 섬은 홈서버에 뭉치고, 서비스 섬만 클라우드로

[홈서버 32GB · RTX 5080] 개발 전용 · 시뮬 섬 Isaac Sim + Nav2×3~5 + VDA 5050 어댑터 점유 20~24GB │ │ MQTT (VDA 5050) — 유일한 절단선, WAN 통과 가능 ▼ [EC2 16GB] 상시 서비스 · 서비스 섬 FMS·백엔드·RabbitMQ·Kafka·MQTT·DB + 경량 에이전트 + 간이 DES 점유 ~8GB │ │ AMQP 잡 큐 — 워커는 어디서 붙어도 무방 ▼ [옵션 워커] 스윕 잡 있을 때만 기동 (c계열 EC2 or RunPod)
머신역할비고
홈서버 32GB+5080개발·SIL 검증·라이브 시연 1순위(tailscale 스트리밍 검증 경로)서비스 트래픽은 받지 않음
EC2 16GB상시 서비스 본체 — 도메인·HTTPS가 물리는 곳~8GB 사용, 8GB 여유
옵션 워커전체 스윕 잡 전용, 큐에서 수령발표 주간만 기동

분리를 재검토할 조건: SIL 대수를 3~5대 이상으로 늘리고 전부 Nav2를 물릴 때. 그때도 해법의 순서는 ① SIL 대수 축소(스케일은 DES 담당) ② 일부를 경량 추종기로 대체 ③ 그래도 부족하면 외부 GPU — "ROS만 다른 기기로"는 SEC 03의 이유로 마지막까지 선택지가 아니다.
