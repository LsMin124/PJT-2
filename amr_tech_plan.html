핵심 구조 — 2계층 시뮬레이션과 보정 루프

두 계층 모두 같은 VDA 5050 경계 위에서 동작합니다. 경로는 중앙에서 하달하고 Nav2는 구간 주행만 맡아야 두 계층이 "같은 시스템"을 시뮬레이션하게 됩니다 — 오차 비교가 성립하는 조건입니다.

SEC 01

아키텍처 상세 — 흐름과 결정

전체 그림은 DOC 01 SEC 00의 시스템 지도에 있습니다. 여기서는 그 그림을 성립시키는 기술 결정 세 가지를 설명합니다.

  • 단일 내부 표현이 계약 — 인테이크가 어떤 형태(에디터·엑셀·설문)로 들어와도 어댑터 계층이 "시맨틱 그리드 + 수요 프로파일 JSON" 하나로 변환한다. 이후 모든 컴포넌트는 이 표현만 바라본다
  • 스윕은 K8s Indexed Job — 스윕 1회 = 잡 1벌, 인덱스 = (기종 × 대수 × 시드) 조합. Kafka → TimescaleDB로 집계가 흐르고, Redis → WebSocket으로 진행률이 흐른다
  • 경로 지시는 중앙 하달 — 플랫폼 코어가 VDA 5050 노드/엣지 경로를 내려보내고 Nav2는 구간 주행만. 로봇이 스스로 경로를 고르면 두 시뮬레이션 계층이 서로 다른 시스템이 되어 정합성 비교가 무너진다
의사결정 여정 — 왜 이 제품이 되었나 디스패처 비교 연구 → 인력 배치 전환 검토 → 관제탑 포장(ROS 조연화 모순 발견) → FMS 제품화 → 견적 서비스 → 최종: 견적 서비스(v1) + SIL 에뮬레이션 검증 계층, 실시간 관제(FMS)는 v2 백로그.
교훈 세 가지 — ① 로봇 데모는 웹 서비스로 포장되어야 임팩트가 생긴다 ② 제품 카테고리를 로봇 도메인 안에서 고르면 "서비스 포장 vs ROS 주연"이 양립한다 ③ v1에서 ROS의 정직한 역할은 검증 계층이다.
SEC 02

이론 기반 요약 — 경합이 곡선의 모양을 결정한다

견적의 헤드라인인 대수–처리량 곡선이 꺾이는 이유는 경로 경합이고, 그 수학이 MAPF입니다. 전체 이론은 DOC 06에 풀어 두었고, 요약만 적습니다.

  • MAPF 계보 — A* → 시공간 예약 테이블 → Prioritized Planning(v1 플래너) → CBS/ECBS → Lifelong MAPF/RHCR(직접 기반 문헌, Li et al. AAAI 2021)
  • TAPF 절충 — 할당과 경로를 따로 풀되, 경합 페널티를 할당 비용행렬에 피드백
  • 데드락 이론 — Zone Control, Banker's Algorithm 계열
  • 집계 이론 — Little's Law 검산, M/M/c 대기행렬, 교통류 fundamental diagram(포화의 이론적 설명)
  • SimPy 계층 결정 — 경량 MAPF 내장(고정 틱, 1틱=1셀 이동). 매 틱 CBS는 배속을 파괴하므로 배제
SEC 03

AI 파트 — 디스패처 3단 비교와 RL 리스크 관리

"어느 로봇이 어느 작업을"을 정하는 디스패처를 세 단계로 만들어 같은 조건에서 비교합니다 — 이것이 서비스의 연구적 차별점이자, 유일하게 실패 가능성이 있는 요소입니다.

단계방식역할
규칙FIFO + 최근접기준선(baseline). 주 1~2차 E2E 루프의 기본
휴리스틱헝가리안 배치 매칭제품 기본 탑재 후보 — 안정적이고 설명 가능
RLPPO + Stable-Baselines3연구 요소 — 성능 상한 탐색
  • 학습·검증 분리(sim-to-sim) — RL 학습은 SimPy-Gymnasium 환경에서, Isaac은 검증만
  • 평가 규칙 — 동일 시드 쌍대 비교, 학습/평가 시나리오 완전 분리
최대 연구 리스크 — RL 맵 일반화 견적 서비스는 고객마다 맵이 다릅니다. 특정 맵에서만 통하는 정책이면 제품이 성립하지 않습니다. 대응: 맵 불변 관측(작업까지의 경로비용·구역 혼잡도) 설계 + 랜덤 레이아웃 학습. 실패 시 후퇴선(사전 합의): "RL은 연구 항목, 제품 기본은 휴리스틱".
SEC 04

표준 스택 — 프로토콜에서 방법론 중심으로

제품 정체성이 "로봇을 움직이는 시스템"에서 "신뢰할 수 있는 분석"으로 이동하면서, 따르는 표준도 통신 프로토콜 중심에서 방법론(검증·KPI·안전) 중심으로 재편했습니다.

표준역할채택 수준
VDI 3633DES 절차·V&V — 투명성 주장의 표준 준거필수
ISO 22400KPI 정의 — 리포트 용어집의 출처필수
ISO 3691-4안전 거동 → 시뮬 파라미터 출처 (낙관 편향 방지)강추

SEC 05

V&V 체계 — 이 숫자를 왜 믿어야 하는가

"투명한 견적"이라는 주장은 검증 체계가 있어야 실체가 됩니다. Verification은 "모델을 올바르게 구현했는가", Validation은 "모델이 현실을 닮았는가"입니다.

  • Verification — 보존 법칙(생성 주문 수 = 완료+미완료), Little's Law 검산, 로봇 1대 극한 케이스의 해석해 대조
  • Validation — MAPF 공개 벤치마크 대조, SimPy vs 에뮬레이션 정합성(엣지 주행시간 → 사이클타임 → 처리량 3단 오차), 예측 오차 N% 공개
  • 문서화 — 모든 가정·분포·보정 계수를 리포트 부록의 "가정 명세서"로 — 투명성 주장의 실체

SEC 07

로드맵 — 8주와 생존 원칙

타임라인 그림은 DOC 01 SEC 08에 있습니다. 여기서는 주차별 산출물과 순서의 이유를 적습니다.

주차산출물이 순서인 이유
주 1–24대 계약 동결 + SimPy DES + 규칙 디스패처 (E2E 최소 루프) + RTF 실측계약이 동결돼야 4트랙이 병렬로 출발. RTF 실측이 검증 스코프의 상한을 정한다
주 3Kafka→DB→차트 + Scenario API + 에디터 골격데이터가 끝까지 흐르는 배관을 먼저 뚫는다
주 4–5휴리스틱+RL 디스패처, K8s 스윕, 곡선/리포트 화면, 카테고리 게이트견적 본체의 완성 — 여기까지가 "최악에도 남는 데모"
주 6–7에뮬레이션 검증 트랙 + 보정 루프 1회전 + 오차 분석완성된 견적을 검증으로 보강. Isaac이 마지막인 이유
주 8통합, VDI 3633 준거 리포트, 발표—
생존 원칙 ① Plan(견적) 먼저 완성 — 최악의 경우에도 완결된 데모가 남는다 ② Isaac은 마지막 — 검증은 보강이지 본체가 아니다 ③ what-if 라이브는 사수, 나머지(스윕·에뮬레이션)는 캐시·녹화 폴백을 준비한다.
