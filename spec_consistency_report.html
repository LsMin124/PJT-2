AI는 병행이다: 3단 비교는 지키고, 회귀 예측을 신설한다

A · 개괄 §9 / 인벤토리 C4★"디스패처 3단 비교: 규칙(FIFO+최근접) / 휴리스틱(헝가리안 배치 매칭) / RL(PPO+SB3)" · "최대 연구 리스크 = RL 맵 일반화 … 실패 시 'RL은 연구 항목, 제품 기본은 휴리스틱'으로 후퇴 (사전 합의)"
B · 스펙 §4 AI / 결정표"강화학습은 사용하지 않는다"(3개 명세에서 반복 명시) · AI = Supervised Regression으로 Fleet Size별 KPI 예측 (Linear 베이스라인 + XGBoost/LightGBM/RF/MLP, MAE·RMSE·R²) · 디스패처는 Rule/Heuristic/간단 Optimization

적용 결과 — 기존 논의 유지 원칙에 따라 디스패처 3단 비교(규칙/헝가리안/RL PPO+SB3)와 C4★ 후퇴선은 그대로 산다. 스택 유지 원칙에 따라 스펙의 지도 회귀 예측(XGBoost/LightGBM/RF/MLP)도 산다 — 초판이 "축소+신설의 조합일 가능성"으로 짚었던 해석이 공식 방향이 된 셈이다. 개정 대상: 스펙 AI 명세의 "강화학습은 사용하지 않는다" 3곳을 "RL은 디스패처 연구 항목(후퇴선 기합의), 예측 모델은 회귀"로 수정하고, 개괄 §9에 서러게이트 예측 신설을 추가. AI_MODEL/AI_PREDICTION ERD는 그대로 유효하다. 잔여 확인 ①: 두 역할 병행은 AI 트랙 부하를 늘린다 — 서러게이트를 주 4~5 일정에 편입할지, 스트레치 골로 둘지는 팀 일정 판단.

적용 결과 — 기존 논의 유지: VDA 5050 order/state/connection 서브셋(F2), 경로 중앙 하달(F1★), vda5050_connector 이식(F9), 검증 기종 iw.hub+MiR 250(F4)을 스펙에 편입한다. 핵심은 스택과의 관계인데, VDA 5050은 원래 MQTT 위에서 동작하는 표준이라 스펙이 이미 세워 둔 Mosquitto 브로커를 그대로 쓴다 — 토픽만 order/state(검증 트랙)와 telemetry(실시간 화면)로 나뉜다. 즉 스택 축소 없이 경계가 복원된다. 개정 대상: 스펙에 VDA 서브셋·어댑터·기종 명세를 추가하고, "가능한 한 동일 Telemetry Schema" 서술을 "텔레메트리는 공용 스키마, 명령 경계는 VDA 5050"으로 강화. 발표 메시지("경계 불변")와 데모 HUD의 VDA 5050 라벨은 유지된다.

정리 · C-4

인프라만 명세서가 이긴다: RabbitMQ 워커 큐와 PostgreSQL 확정

A · 인벤토리 E2★ / 개괄 §4·§12 / 사이트 기술 계획"Scenario API가 K8s Indexed Job 생성(스윕 1개=Job 1벌, 인덱스=기종×대수×시드). 별도 큐 시스템 추가는 과잉" · 사이트: "스윕 = K8s Indexed Job … Kafka→TimescaleDB 집계"

적용 결과 — 스택 유지 원칙이 적용되는 유일한 중대 충돌. RabbitMQ 작업 큐(simulation.task/result/failed + DLQ, Manual ACK, 재시도 3회) + 상주 Worker Pod × N + k3s Scale-out을 확정하고, K8s Indexed Job 안은 폐기한다. 스펙 방식이 장애 복구(ACK 재전달·DLQ)와 상시 서비스형 운영에 유리해 기술적으로도 손해가 아니다. DB는 순정 PostgreSQL — E6의 hypertable이 필요해지면 TimescaleDB가 PostgreSQL 확장이라 축소 없이 얹을 수 있다(선택). 개정 대상(이번에는 기존 논의 쪽): 인벤토리 E2★ 결정문("별도 큐는 과잉") 갱신, E6·E7 문구 조정, 개괄 §4 아키텍처(RabbitMQ·MQTT 편입)와 §12 크리티컬 패스 5번, 사이트 기술 계획·전체 조망의 "K8s Indexed Job … Kafka→TimescaleDB" 서술.

스펙 신규

개괄이 비워 뒀던 곳을 스펙이 채운 항목 — 충돌이 아니라 진전이다

  • 메시징 3종 역할 분리: RabbitMQ(작업)/Kafka(도메인 이벤트)/MQTT(텔레메트리) + WebSocket. 개괄엔 Kafka만 있었다. C-4에서 채택 확정 — 역할 분리 원칙이 그대로 설계 자산이 된다.
  • 장애 정책 전반: Manual ACK·재시도 3회·DLQ·부분 실패 격리·Pod 재생성 — E3의 한 줄 권고를 실행 수준으로 구체화.
  • ERD 14테이블: Layout 버전 관리, Job–Task–Result 계층, 관계 카디널리티까지 명세. E6의 골격과 호환(단 hypertable 제외).
  • REST API 명세: 자원 경로·상태코드·비동기 202 패턴 — 개괄 "다음 액션 1(입력 JSON 스키마 확정)"의 상당 부분을 선반영.
  • 에너지 소비 KPI + 전력비 견적 반영: 개괄에 없던 축. AMR_SPEC의 energy_consumption_rate와 일관.
  • Telemetry 스키마·2Hz 샘플링·Mosquitto·QoS 0: 텔레메트리 계층의 구체화(시간 기준 정의만 H-4로 남음).
  • AI 모델 버저닝·독립 서비스 배포: NFR-10(모델 교체 용이)의 실행 설계.
