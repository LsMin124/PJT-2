SEC 01

비전과 서비스 정의

쉽게 말하면우리는 '가상의 물류센터'와 그것을 운영하는 '진짜 웹 서비스'를 함께 만듭니다. 화면 속 3D 창고에서 로봇이 상품을 나르고, 운영자는 우리가 만든 웹사이트에서 주문을 넣고 로봇을 지켜보고 문제가 생기면 알림을 받습니다. 물리 세계만 가상일 뿐, 쿠팡 물류센터의 축소판이라고 생각하면 됩니다.
WHAT WE BUILDAMR 플릿 + 피스 피킹 매니퓰레이션 시뮬레이션 물류센터 위에, 산업 표준 데이터 플로우·AI 검수·운영 관제 웹 서비스까지 통합한 스마트 물류 솔루션

단순 로봇 데모가 아니라 운영자가 실제로 쓰는 서비스가 최종 산출물. 물리 세계만 시뮬레이션일 뿐, 데이터 플로우·백엔드·서비스는 실제 스마트 물류센터와 동일한 구조로 구축한다.

이 문서가 처음이라면 안내 문서(DOC 00)를 먼저 읽는 것을 권합니다. 처음 보는 용어는 용어사전에서 그래픽과 함께 설명 — A 로보틱스·시뮬레이션 · B 물류센터·표준 · C AI·데이터·서비스

  • 시연 철학 — "정상 동작"보다 "고장에서 스스로 복구"(장애 주입)와 "미래를 예측"(What-if)이 기억에 남는다. 두 하이라이트는 신규 개발이 거의 없고(주입 버튼 + 화면 1개) 이미 만든 시스템의 능력을 드러내는 장치다
  • (스트레치) 키팅 스테이션 — 수직 슬라이스가 5주차 전 안정되면 착수: 로봇팔이 복수 SKU를 세트 상품으로 조립하는 경공정. BOM·작업지시·생산 실적까지 붙이면 MES 기능이 문자 그대로 실체화됨 (필수 아님 — WMS/WES가 이미 물류 도메인의 L3/MES 계층)
  • Grafana는 엔지니어용 내부 관측 도구로 분리 — 서비스는 "데이터를 본다"가 아니라 "물류센터를 운영한다"
  • 모바일은 네이티브 앱 대신 PWA(반응형 + 웹 푸시 불량 알림)로 충족

SEC 03

팀 구성과 오너십 (6명 — 1인 1트랙 · 1겸임)

쉽게 말하면여섯 명이 각자 하나의 큰 덩어리(트랙)를 책임지고, 추가로 팀 전체를 위한 역할(일정 관리, 문서 관리 등)을 하나씩 겸합니다. "보조"는 없습니다 — 전원이 시연 화면에 자기 결과물을 하나씩 올립니다. 누가 어느 자리를 맡을지는 킥오프에서 정합니다.

특정 개인을 전제하지 않는 역할 설계도. 전원이 ① 데모에 보이는 수직 트랙 하나를 소유하고 ② 횡단 역할(PM·아키텍트·통합 등) 하나를 겸임한다. "보조" 역할은 없다 — 실제 배정은 킥오프 때 각자의 강점·지망으로 결정.

배치 원칙

  • 크리티컬 패스 보호: Nav2·MoveIt2·Isaac 통합 소유자(R1·R2)에게 일정성 겸임(PM)을 걸지 않는다
  • 도구 시너지로 겸임 배치: mock publisher는 SimPy 오너(B1)에게, 시뮬 CI는 headless 배치를 다루는 A1에게
  • "프론트 전담 0명"은 성립, "프론트 오너 0명"은 불성립 — 검수 없는 에이전트 코드는 데모 직전 수정 불가 리스크
  • 월드·에셋·레퍼런스 설정은 오픈소스 기성품 우선 — 직접 만드는 것은 각 트랙의 차별화 지점뿐

거버넌스 — 2-키 구조

  • 아키텍트(R2): 데이터 계약·아키텍처 결정의 승인권 (기술 타당성 판단)
  • PM(B2): 일정·리소스·범위 조정의 승인권 (일정 영향 판단)
  • 계약 변경 요청 = 두 키 모두 통과해야 반영. "필드 하나만 추가"로 계약이 조용히 부식되는 것을 차단
  • 버스 팩터 완화: 주요 결정은 ADR로 짧게 기록 — 서기는 주간 순환
SEC 04

데이터 계약 — 파트를 병렬로 달리게 하는 장치

쉽게 말하면여섯 명이 서로를 기다리지 않고 동시에 개발하려면, "주고받을 데이터의 형식"을 먼저 약속하고 얼려두면 됩니다. 약속만 지키면 로봇이 완성되기 전에도 웹·서버 파트는 가짜 데이터(mock)로 개발을 시작할 수 있습니다. 이 약속 문서가 이 프로젝트 협업의 헌법입니다.

4개 파트가 서로를 기다리지 않는 유일한 방법: 1~2주차에 인터페이스 계약을 동결하고, 각 파트는 계약만 보고 개발한다.

Mock Publisher — 시뮬레이터 이전의 시뮬레이터

  • SimPy 기반 가짜 공장이 표준 토픽 스키마 그대로 가상 AMR/설비 이벤트를 발행 — B1 담당 (SimPy 오케스트레이터와 동일 도구체인), 1~2주차 최우선 납품물
  • 백엔드·AI·프론트는 실물 로봇 완성 전부터 "움직이는 데이터"로 개발 시작
  • Gazebo → Isaac으로 소스가 교체되어도 소비자 코드는 한 줄도 변경 없음 — 표준 준수의 가치를 팀 개발 속도로 증명

인프라 셀프서비스

  • docker compose up 한 번으로 전 스택(EMQX + TimescaleDB + PostgreSQL + mock publisher) 로컬 기동 — 1~2주차 구축
  • 인프라 요청은 이슈로만 접수, 하루 한 타임 일괄 처리 (긴급 기준: 데모 임박·전원 블로킹만 예외)
  • 각 파트는 자기 서비스의 컨테이너/CI 파이프라인을 직접 소유 — "인프라 분담"의 실제 정의

통합 캘린더 — 빅뱅 금지

쉽게 말하면마지막 주에 한꺼번에 합치면 반드시 사고가 납니다. 그래서 2~3주에 한 번씩 전체를 미리 연결해보는 날을 정해두고, 그날마다 "실제로 돌아가는 모습"을 확인합니다. 중반 이후로는 언제 시연 요청이 와도 보여줄 수 있는 상태를 유지하는 게 목표입니다.

SEC 06

협업 규칙 요약

쉽게 말하면위 내용 전체를 여섯 줄 규칙으로 압축한 표입니다. 일하다 헷갈리면 이 표만 다시 보면 됩니다.
규칙내용
계약 우선파트 간 소통은 동결된 계약(스키마/API)이 기준. 변경은 2-키(아키텍트 R2 + PM B2) 승인
mock 우선어떤 파트도 다른 파트의 완성을 기다리지 않는다 — mock publisher가 대역
오너십 명시모든 컴포넌트에 오너 1인. "전원 분담" 영역(인프라)도 플랫폼 오너(B2) + 파트별 배포 책임으로 분해
AI 에이전트 운용프론트는 에이전트 산출물 허용, 단 발주 오너가 스펙·검수·연동 책임. 검수 없는 머지 금지
기성품 우선월드·에셋·레퍼런스 설정·컴포넌트 라이브러리는 가져다 쓴다. 직접 만드는 것은 각 파트의 차별화 지점뿐
기록 습관주요 결정은 ADR/Decision Log로. 버스 팩터 1 완화 + 발표 자료의 원천
